# 知見の置き場

実装や振り返りで得た知見を、残すかどうか、どこに置くかの考え方です。Hikyaku は「どの文書に書くか」ではなく「いつ読み込まれる場所に置くか」で決めます。読まれる頻度が、その知見が使われる頻度を上回る場所には載せません。

落とし穴の記録を1つの文書に溜めていくと、たまにしか使わない知見のために、毎セッションで一定のコンテキストを使うことになります。逆に置き場を持たないと、同じ落とし穴を次のビルドがもう一度踏みます。この2つを同時に避けるために、重要度で残すものを絞り、置き場を読み込まれ方で選びます。

## 重要度

重要度は、害がどこに出るかで決まります。

| 重要度 | 害が出る場所 | どういうものか |
|---|---|---|
| 高 | 成果物 | テストも lint も通ったまま、誤りが成果物に残る。本番でだけ壊れる。情報が漏れる、データが壊れる。エラーメッセージに素直に従うと誤った修正になる |
| 中 | セッション | 失敗として気づけるので成果物は守られるが、原因の特定や正しい直し方に時間がかかり、今後も起きる見込みがある |
| 低 | ほぼ無し | すぐ失敗して、メッセージや数分の調査で直せる。一般的な知識。一回限りの事象 |

高は必ず残します。成果物に残る害は、セッションの側では防ぎようがないためです。中は、機械で防げるか、狭い範囲の rule にできるときだけ残します。守りたいのがセッションの時間とコンテキストなので、読ませるコストがそれを上回っては意味がありません。低はどこにも書きません。

判定は「既に直っているか」ではなく「次に同じ種類のものを足す人が踏むか」で行います。既存のテストが正しく書かれていても、新しいテストを書く人が同じ罠を踏むなら、防がれてはいません。

## 置き場

上から順に当てはめ、最初に合ったものを使います。上にあるものほど、読むコストがかかりません。

| 知見の性質 | 置き場 | 読み込まれるとき | 書くのは |
|---|---|---|---|
| 機械で防げる | コード（lint・テスト・型・共通ヘルパー・設定・その場のコメント） | 読まれない。違反したときに落ちる | builder（見つけたビルドの PR） |
| 一部のファイル群を触るときだけ効く | パス指定の rule（`.claude/rules/`） | 一致するファイルを読み書きしたとき | builder（見つけたビルドの PR） |
| 決まった手順を踏む作業 | スキル（`.claude/skills/`）。既存の手順書があればそこ | 説明文は常時、本文は起動したとき | close-cycle |
| Hikyaku の進め方への、このリポジトリ固有の指示 | `{HIKYAKU_ROOT}/instructions.md` | Hikyaku の各フェーズ | close-cycle |
| リポジトリのどの領域でも、知らないと一貫性を壊す取り決め | `conventions` | 常時（AGENTS.md に無ければ、各フェーズが読む） | close-cycle |
| 構造・設計判断・設計を縛る条件 | `overview` / `decisions` / `constraints` | architect が読み、ビルドには必要な節だけが渡る | close-cycle（ADR の追記は architect） |
| エージェントの操作そのものを止める必要がある | フック（`.claude/settings.json`） | 読まれない。操作のたびに実行される | close-cycle が別の PR にする |

コードと rule を builder が書くのは、見つけたビルドの PR に含めれば、同じサイクルの後続ビルドに間に合うためです。落とし穴の再発は、同じ領域を続けて触るビルドのあいだで最も起きます。それ以外を close-cycle が書くのは、複数のビルドの知見を束ねて判断する必要があることと、走行中の他サイクルが読む文書をフェーズの途中で動かさないためです。

個人の実行環境に固有の事象（そのマシンのスリープや、サンドボックスの書き込み範囲）はリポジトリには書きません。各自の設定の領分です。Hikyaku 自体の不具合と思われるものは、close の PR の本文に報告として並びます。

## rule の広さと大きさ

rule は、`paths` の glob に一致するファイルを読み書きしたときに読み込まれます。glob が広くて本文が長いと、関係のない作業でも毎回読み込まれ、常時読み込みと変わらなくなります。広いが短い rule、長いが狭い rule は問題になりません。

```bash
hikyaku rules check
```

rule ごとに、一致する追跡ファイルの数、一致率、本文の文字数と、掛け合わせた読み込み量を返します。読み込み量が目安を超えた rule を知らせるので、glob を狭めるか、狭い glob のファイルに分けてください。生成物（[`[diff] exclude`](config-file.md#diff) に当たるファイル）は分母から除きます。どのファイルにも一致しなくなった rule はもう読み込まれていないので、エラーとして報告されます。

Hikyaku が rule を書くときは、glob ごとにファイルを分け、1件を再現条件・起きること・回避策の2〜3文で書きます。既存の広い rule には追記しません。

## 消すこと

足すだけでは、文書は必ず膨らみます。そのため各ビルドの振り返りで、読み込まれた記述のうち役に立たなかったものを、理由と一緒に記録します。

| 理由 | 意味 | close-cycle の扱い |
|---|---|---|
| 古い | コードや他の記述と食い違っている | コードと照合して、削除か置き換えを提案する |
| 自明 | 知らなくても、すぐ気づいて直せた | 削除を提案する。ただし重要度が高の記述は消さない |
| 無関係 | 読み込まれたが、触った範囲に関係がなかった | 消さない。複数のビルドで挙がったら、glob を狭めるか分ける |

使った本人の証言なので、文書を読み直して判定するより確かです。複数のビルドが同じ記述を挙げれば、消す根拠として十分です。重要度が高の記述を「自明」だけで消さないのは、テストが通ってしまう類の罠は、踏まなかったセッションには役に立たなかったように見えるためです。

close-cycle が削除や置き換えを提案できるのは、そのサイクルの記録（handoff と振り返り）に根拠があるものと、そのサイクルのビルドが書いた rule に限ります。根拠の無い記述の正否は、そのサイクルの知識では判断できません。気づいた点は、手を入れずに PR の本文に書き残されます。

振り返りを省くプロファイル（`economy`）では、この記録が集まりません。掃除が進まないだけで、害はありません。
