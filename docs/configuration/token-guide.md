# 予測ピークと見積もりのガイド（token-guide/）

Hikyaku は、ビルドを1つのセッションで実装から PR まで進めたとき、メインセッションのコンテキストがどこまで膨らむか（予測ピーク）を見積もって、ビルドの大きさを決めます（[BUILD](../workflow/build.md#予測ピーク)）。見積もり方を書いたものが見積もりのガイドで、プラグインに標準のガイドが同梱されています。`{HIKYAKU_ROOT}/token-guide/guide.md` を置くと、それが標準を置き換えます。

同じ規模の実装でも、フレームワークの定型量、既存コードの結合度、リポジトリのルールファイルの大きさによって、セッションの重さは変わります。そのため Hikyaku は見積もり方を固定せず、各リポジトリの実績で補正できるようにしています。補正は、サイクルを終えるときの昇格（close-cycle）か、`/hikyaku:token-guide` で行います。

## 見積もりの分担

予測ピークは5つの成分の和です。固定費（セッションの開始時と手順の進行で載る分）、読み込み（読むドキュメントとコード）、実装（テストを除くコードの生成と編集）、テスト（テストコードと実行結果）、未知の領域（環境構築・デバッグ・外部ライブラリの調査・検証と修正のループ）に分けて見積もります。コンテキストは一度載ると減らないので、成分は足し算で効きます。

各成分のトークンとその根拠は、build-manager と builder がガイドに沿って見積もります。それを `hikyaku tokens estimate` に渡すと、合計・判定・記録の表をコマンドが返します。判定は `.hikyaku.config` の [`[context]`](config-file.md#context) の帯で決まり、既定では 300k 未満が統合の検討、300k〜450k が狙いの帯、450k 超が分割の検討です。係数や段階表を持たず LLM に見積もらせているのは、リポジトリごとに重くなる作業が違い、表で決めきれないためです。同じ入力でも予測は揺れますが、その揺れの大きさは実測との突き合わせで確かめます。

5つの成分はすべて渡す必要があります。該当しない成分には 0 を渡します。未指定と 0 を区別するのは、「考えなかった」と「考えたうえで無いと判断した」を記録の上で分けるためです。

## ガイドの版

ガイドの先頭には版（`version`）と本文のハッシュ（`hash`）が書かれ、プロジェクトのガイドにはどの標準の版から作ったか（`based_on`）も入ります。

```markdown
---
version: 3
based_on: 標準 v1
hash: 1a2b3c4d
---

# 予測ピークの見積もりガイド
...
```

`tokens estimate` が返す表の最後の行には、見積もりに使ったガイドの版とハッシュが残ります。補正の前と後の予測を混ぜて比べると、補正が効いたのかどうかが分からなくなるためです。`hikyaku tokens history --group-by guide` で、版ごとに分けて当たり方を比べられます。

本文を変えたら、`hikyaku tokens stamp` で版を上げます。このコマンドは、ガイドが無ければ標準の本文をコピーして version 1 で作り、本文が変わっていれば version を1つ上げてハッシュを合わせます。版を上げずに本文だけを変えると、ハッシュが本文と合わなくなり、`hikyaku validate` と、ガイドを書き込むステップの完了の条件がそれを止めます。先頭の宣言は手で直さないでください。

今有効なガイドとその版は `hikyaku tokens guide` で確認できます。

## 実測と振り返り

予測と突き合わせる実測は、ホストが残すセッションの記録から取ります。`hikyaku tokens session` は Claude Code のトランスクリプト（`~/.claude/projects/` の下）と Codex の rollout（`~/.codex/sessions/` の下）を読み、ピーク・開始時の固定分・API 呼び出し回数・出力トークン・コンパクション回数・モデル・ホストの版を返します。測るのはメインセッションだけです。サブエージェントはコンテキストウィンドウが別なので、コンパクションの判断に関わらないためです。1つのビルドにはレビュー用の別プロセスや中断後の再開など複数のセッションが対応付くことがあるので、そのブランチでの API 呼び出しが最も多いセッションを本体として選び、どれを選んだかと他の候補を出力に出します。どちらの記録も公開された仕様ではないため、読めないときは推測で埋めず「計測不可」とその理由を返します。Codex のクラウドでは rollout が保存されないので、常に計測不可になります。

ビルドの振り返りでは、予測ピーク（architect 段階と builder 段階）、セッションの実測、差分の集計、乖離（実測 − builder 段階の予測）とその要因が `retrospective.md` の「予測ピークの振り返り」に残ります。差分の集計は `hikyaku tokens history build-NN` が PR の base からの差分を数えたもので、新規ファイル数・変更ファイル数・追加行数（実装とテストの内訳）・削除行数です。ロックファイル・スナップショット・生成コードは書いた量ではないので数えず、どのパスを生成物とし、どれをテストとするかは [`[diff]`](config-file.md#diff) で変えられます。差分の集計は予測の算出には使いません。乖離の要因を考えるときに、書いた量が想定と違ったのかを確かめる素材です。

`hikyaku tokens history` は全サイクルの振り返りを読み、予測と実測・乖離・比率・区切りでのコンテキストを並べます。予測の当たり方はモデルの世代やホスト、ガイドの版で変わるので、`--group-by model`（または `hikyaku`・`host`・`guide`）で分けて比べてください。

## 誰が、いつガイドを書き換えるか

| 状況 | 誰が | 何が起きるか |
|---|---|---|
| 初期化 | `/hikyaku:init` | ガイドは作らない。標準のガイドで見積もる |
| サイクルを終える | `/hikyaku:close-cycle` → `/hikyaku:token-guide` | そのサイクルで、予測が同じ向きに大きく外れたビルドが複数あれば、close-cycle が token-guide を呼ぶ。変更は別のブランチの PR になり、採るかどうかはマージで決める |
| 人が校正する | `/hikyaku:token-guide` | `tokens history` を素材に、モデルの世代が変わったときや補正が溜まったときにガイドを見直す。変更案を提示して承認を得る |

close-cycle が token-guide を呼ぶかどうかは、`hikyaku tokens history {cycle}` が決めます。同じガイドの版で、実測が予測から 20% を超えて同じ向きに外れたビルドが2件以上あるときです。1件だけのぶれでは呼びません。偶然の外れに合わせると、次のビルドで逆向きに外れるためです。実測の無いビルドは数えません。

このとき token-guide は承認を求めません。採否を PR のマージで決められるよう、対象のビルドごとの予測・実測・比率、どの成分をどちらへ読み違えたか、変更前後の文面を PR の本文に載せます。偏りがはっきりしなければ、変更案を作らず PR も作りません。未マージの token-guide の PR が残っているときは、ブランチが衝突するので close-cycle は呼び出しを見送ります。

`/hikyaku:token-guide` は、ブランチの確認、素材の収集、変更案、承認、書き込みと版の更新、PR の順に進みます。この順序は `hikyaku step next token-guide` が1手ずつ返し、進み具合は `token-guide/progress.jsonl` に記録されます。調整は何度も行うので、前の回の記録は PR と一緒にデフォルトブランチに残ります。次に実行すると、スキルは前の回が終わっていることを読み取り、`hikyaku step restart token-guide` で区切って新しい回として始めます。

ガイドを書き換えるのは `/hikyaku:token-guide` だけです。build-manager と builder は読むだけです。ガイドはワークスペース全体に効くので、ほかに走行中のサイクルがあれば、その残りのビルドは補正後の版で見積もられます。それでも見直しは止めません。各予測の表には見積もりに使ったガイドの版が残るので、補正の前と後は `hikyaku tokens history --group-by guide` で分けて比べられます。止めて待つより、早く補正したほうが以降の見積もりの精度が上がります。

## v2 の BP 基準表からの移行

v2 の BP（ビルドポイント）と、その基準表（`{HIKYAKU_ROOT}/bp-guide/` の `rules.toml`・`README.md`・`cases.toml`）は v3 で廃止しました。BP の段階表と予測ピークは別の量で、換算できないため、基準表は自動では移行しません。`bp-guide/README.md` にリポジトリ固有の数え方の注意を書いていた場合は、`/hikyaku:token-guide` でガイドの言葉に書き直してから、`bp-guide/` を削除してください。残っているあいだは `hikyaku doctor` が注意を出します。手順は [v2 → v3 移行ガイド](../migration/v2-to-v3.md) にあります。
