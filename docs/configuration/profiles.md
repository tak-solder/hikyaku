# プロファイル

プロファイルはサイクルの属性です。`create-cycle` で必ず明示的に選択し、`cycles.md` に記録されます。作成後は変わりません（変える場合は `cycles.md` を直接編集します）。

サイクルに属さない [patch](../workflow/patch.md) は、ルートの `.hikyaku.config` の `profile`（無ければ standard）でレビューの回数などを決めます。サイクルに属す patch は、そのサイクルの profile に従います。

|  | 人間の承認回数 | AIレビュー |
|---|---|---|
| express | 少 | 有 |
| economy | 多 | コードのみ |
| standard | 多 | 有 |
| thorough | 最多 | 全部 |

## 何を節約するか

express は人間の時間を節約します。承認は減らしますが、AI には見させます。economy は AI 実行コストを節約します。中間成果物のレビューを起動しませんが、人間は見ます。

つまり express と economy は「何を省くか」が違うだけの兄弟です。品質の担保を AI に寄せるのが express、人間に寄せるのが economy で、どちらも担保そのものは手放しません。「承認少 + レビュー無」の組み合わせは意図的に用意していません。

thorough は判定基準が厳しくなるわけではありません。standard で不合格になるものが thorough で通る、という関係ではなく、変わるのはチェックポイントの細かさです。standard は完成した成果物の単位で（user-stories / 設計ドキュメント / plan + test-spec）、必要なときに確認します。thorough はその手前の作りかけの段階でも止まり（codebase-survey だけ、plan だけ、各ステップごと）、やるかどうかの判断を挟まず常に実行します。手戻りの巻き戻し幅が、フェーズ単位からステップ単位になると考えてください。

## 承認ゲート

| # | フェーズ | ゲート | 承認 | express | economy | standard | thorough |
|---|---|---|---|---|---|---|---|
| G1 | planner | user-stories 承認 | 同意 | ✓ | ✓ | ✓ | ✓ |
| G2 | architect | codebase-survey 確認 | 確認 | ✗ | ✗ | ✗ | ✓ |
| G3 | architect | 設計案の選択 | 確認（差し戻しからの再設計の回と、上限を超える案がある回は同意） | ✗ | ✓ | ✓ | ✓ |
| G4 | architect | 設計ドキュメント承認 | 確認（差し戻しからの再設計の回と、設計が G3 の申告に無い重い領域・外との境界に触れる回は同意） | ✗ | ✓ | ✓ | ✓ |
| G6 | build-manager | tasklist / issue 変更承認 | 確認 | ✓ | ✓ | ✓ | ✓ |
| G7 | builder | plan 単独の承認 | 確認 | ✗ | ✗ | ✗ | ✓ |
| G8 | builder | plan + test-spec 承認 | 確認 | ✓ | ✓ | ✓ | ✓ |
| G10 | close-cycle | 永続ドキュメント昇格の承認 | 確認（decisions・constraints の変更を含む回は同意） | ✗ | ✓ | ✓ | ✓ |
| P1 | patch | 対応方針の合意 | 同意 | ✓ | ✓ | ✓ | ✓ |
| P2 | patch | 永続ドキュメントの更新の承認（サイクルに属さない patch で、残すものがあるときだけ） | 同意 | ✓ | ✓ | ✓ | ✓ |

プロファイルで省略できるのは確認であって、同意ではありません。同意のゲートは、どのプロファイルでも、個別キーで外そうとしても、conductor のもとでも省かれず、ユーザーが判断します。この区別の理由は [概念と設計思想](../concepts.md#承認ゲートは確認と同意を分ける) にあります。G6 / G8 は確認ですが、プロファイルの管轄外で常に有効です。conductor のもとでは、確認のゲートは監督が答え、同意のゲートはユーザーに上がります。

G1 は要件の合意なので、どの設定でも止まります。v2 までの `user_stories_gate` は廃止し、書かれているとエラーになります。

G3 と G4 は、ふだんは確認でプロファイルに従います。ただし、ビルドから architect へ差し戻されたあとの再設計の回は、委任の前提が崩れたあとなので同意になり、express でも、`design_choice_gate` や `architecture_gate` を外していても止まります。

ルート設定で [`[app]`](config-file.md#app-と-boundaries) を宣言していると、G3 と G4 は AI に任せてよい害の上限でも同意になります。architect は設計案を作るときに、提示する案のうち最も重い害と、全案が触れるパスを申告します。その害が上限を超えるか、パスが重い領域に当たるか、申告が欠けていれば、G3 は同意です。G4 では、`design-delta.md` とこのサイクルの ADR が触れるパスを重い領域と照合し、G3 で申告されていなかった領域に触れていれば同意になります。AI の申告は、ユーザーに上げる向きにしか効きません。上限を決める基準の宣言を読めないときも、上限が分からないので同意になります。`[app]` を宣言していなければ、これまでどおりプロファイルで決まります。

[`[boundaries]`](config-file.md#app-と-boundaries) で外との境界を宣言していると、`design-delta.md` とこのサイクルの ADR が外との境界に触れる回の G4 も同意になります。`[app]` の宣言の有無には関わらず、事後同意を選んでいても後に回しません。内部の境界の変更は、G4 の提示に確かめる変更として示されるだけで、G4 は確認のままです。

サイクル設定で [事後同意](config-file.md#consent) を選び、それが有効なら、G3 と G4 が上限を超えるリスクの受け入れで同意になる回は、その場では止まりません。受け入れは、拠り所の前提（上限を決めた軸と当たった重い領域）と失うものを添えて未決事項の記録に積まれ、PR を作る直前の同意ゲートでユーザーがまとめて同意します。その回の G3・G4 は確認として扱われ、プロファイルに従います。積んだあとに設計の文書が変わって、積んだ事項に無い重い領域に触れれば、G4 はその場の同意に戻ります。ゲートで唱えた異議のうち上限を超えるものも、ユーザーが選べば同じように積めます。事後同意に回るのは上限を超えるリスクの受け入れだけです。G1、G10 の `decisions`・`constraints` の変更、外との境界の変更、差し戻しからの再設計の回、基準の宣言を読めない回、申告が欠けた回は、事後同意が有効でもその場で同意を取ります。

G10 は、昇格する中身で種類が決まります。`decisions`（ADR）と `constraints` は外の前提と受け入れたリスクを持つ文書なので、その変更を含む回は同意になり、どのプロファイルでも、`promotion_gate` を外していても止まります。ただし、このサイクルの ADR を `accepted` から `implemented` にするだけの書き換えは実装状態の記録なので、同意に数えません。それ以外の昇格（`overview`・`conventions`・rule など）だけの回は確認で、express では省かれます。省いた回に書き込みの途中で `decisions` や `constraints` を変えると、G10 に戻ってユーザーの同意を求めます。

express は「要件（G1）と実装直前（G8）だけユーザーが見て、その間は AI に任せる」という形です。G3 を外しても採用理由と退けた案は ADR に残り、PR 本文にも出るので、判断を後から追えなくなることはありません。

## レビュー

| レビュー | express | economy | standard | thorough |
|---|---|---|---|---|
| user_stories_review | ✓ | ✗ | ✓ | ✓ |
| architecture_review | ✓ | ✗ | ✓ | ✓ |
| tasklist_review | ✓ | ✗ | ✓ | ✓ |
| plan_review | ✓ | ✗ | ✓ | ✓ |
| test_spec_review | ✓ | ✗ | ✓ | ✓ |
| code_review | ✓ | ✓ | ✓ | ✓ |
| security_review | 推奨時のみ確認 | 推奨時のみ確認 | 推奨時のみ確認 | on |
| code / security の max_rounds | 1 | 1 | 2 | 3 |
| retrospective | auto | skip | auto | auto |
| validate | 手動のみ | 手動のみ | 各フェーズ末 | 各ステップ |

`plan_review` と `test_spec_review` は既定値こそ同じプロファイルに従いますが、別々のキーです。plan.md だけレビューして test-spec.md は省く、といった組み合わせは個別キーの上書きで作れます。

`code_review` はどのプロファイルでも行います。中間成果物（user-stories / 設計 / tasklist・issue / plan）のレビューは人間の承認で代替できますが、コードは差分が大きく、人間の承認ゲートが拾える粒度を超えるためです。economy で省くのはこの中間成果物のレビューです。

`security_review` もどのプロファイルでも `off` にはしません。「承認を減らしたから」「実行コストを削ったから」で落としてよい観点ではないためです。既定は `recommended`（判定基準に該当したときだけ起動を確認）で、thorough だけが該当判定を挟まず `on` です。明示的に切りたい場合は `security_review = "off"` で上書きできます。

`max_rounds` はコードとセキュリティのレビューを何回まで回すかの既定値で、`[review]` で上書きできます（[設定](config-file.md#review)）。thorough ほど多いのは、チェックポイントを細かくする方針と同じで、指摘を直したあとにもう一度確かめる機会を増やすためです。

`retrospective` を economy だけ `skip` にしているのは、振り返りがサブエージェントの実行コストそのものだからです。承認を省く express では逆に、改善の材料をセッション内から自動で拾い上げる必要があります。

各レビューを担うものは [内部スキルとエージェント](../reference/agents-and-skills.md) にまとめてあります。

## 選び方

standard から始めて、回してみた感触で変えるのが確実です。express と economy は要件が固まっていて手戻りが小さいサイクルに向きます。thorough は影響範囲が広い変更や、途中で気づかないまま進むと巻き戻しが大きい変更に向きます。

## 個別に上書きする

プロファイルの既定値はキー単位で上書きできます。書く場所は `.hikyaku.config`（リポジトリ全体、またはサイクルディレクトリ）です。キーの一覧は [.hikyaku.config](config-file.md#承認ゲートとレビューの個別指定) にあります。

```toml
# standard のままだが、このリポジトリでは設計ドキュメントの承認を省く
architecture_gate = false
```

サイクル単位で変えたい場合は `{HIKYAKU_ROOT}/cycles/{NNN}-{slug}/.hikyaku.config` に書きます。ただし `profile` 自体はここに書けません（`cycles.md` が唯一の正のため）。

展開結果は `hikyaku config` で確認できます。
