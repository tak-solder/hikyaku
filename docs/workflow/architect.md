# ARCHITECT — 設計

```
/hikyaku:architect [{cycle}]
```

企画成果物と既存コードを入力に、このサイクルの設計差分とビルド分割を決めます。企画内容そのものは変えません（スコープや優先度を変えるなら PLAN に差し戻します）。

## 永続ドキュメントは書き換えない

architect が作るのは「これから作るもの（to-be）」で、それは `design-delta.md` に書きます。`overview` や `constraints` は「実装済みの現実（as-is）」なので触りません。並行して走る別サイクルが、まだ動いていない設計を現実として読む事故を防ぐためです。

例外は ADR だけです。決定した時点で記録するのが ADR 本来の思想なので、`status: accepted`（決定済み・未実装）で追記します。`implemented` への更新は close-cycle が行います。

## 進み方

### 並行サイクルの確認

他に走行中のサイクルがあれば、`cycle-scanner` がそれぞれの設計差分を読んで重複を報告します。重複が見つかったら、設計を分けるか、どちらかに寄せるか、そのまま進めるかを聞かれます。

全走行サイクルの本文を本セッションで読むと大規模リポジトリでコンテキストが破綻するため、軽量モデルのエージェントに委任し、返ってきた重複箇所だけを扱います。

### 既存コードの調査

探索は `code-explorer` に委任されます。ただし設計判断に必要な Key Files は本セッション自身が読みます。要約だけで設計を進めると、規約やインターフェースの解像度が落ちるためです。

`overview` が登録されていれば、調査は差分だけになります。今回のスコープに関係する箇所、`overview` に無い詳細、`overview` とコードのズレだけを調べ、既にあることは再確認しません。`overview` が無ければ全体調査になるので、初回サイクルのコストは高くなります。2周目からは close-cycle が作った `overview` が効きます。

結果は `design/codebase-survey.md` に書かれます。`overview` に既にある内容は書きません。書いてしまうと2周目以降も初回と同じコストがかかり、`overview` を持つ意味が失われます。

`thorough` ではここで確認が入ります（G2）。他のプロファイルでは止まりません。

### 設計に関する質問

技術選定、データ設計、インターフェース設計、非機能要件、既存コードとの整合について、不明点が1回にまとめて聞かれます。`codebase-survey.md` や `constraints` に書かれていることは聞かれません。記録は `design/design-questions.md` に残ります。

### 設計案の選択

主要な技術判断を列挙し、それぞれについて「妥当な代替案が複数あり、トレードオフが非自明か」を評価します。既存規約から自明なもの、合理的な選択肢が1つしかないものは分岐なしとして扱われ、ADR も作られません。

分岐がある判断では `code-architect` が2〜3並列で起動し、異なる観点の案（Minimal / Clean / Pragmatic など）を返します。トレードオフ表と推奨案が提示され、選択を求められます（G3）。

`express` だけはこのゲートが外れ、推奨案がそのまま採用されます。その場合もトレードオフ表と推奨理由は破棄されず、ADR の「検討した案」「採用理由」に残り、採用案と退けた案が PR 本文にも出ます。承認を省いた以上、判断を後から追える場所を残すためです。

確定した案は ADR に追記されます。`repo` 管理の ADR なら既存形式に合わせます。連番なら連番、独自テンプレートならそれに従い、status 欄が無い既存形式に勝手に欄を足すことはしません。

### 設計ドキュメントの承認

`design-delta.md` が作られ、承認を求められます（G4。`express` では省略）。**承認観点は「反映の正しさ」に限定されます。**

- 選択した案が `design-delta.md` に正しく反映されているか
- 分岐なしとして ADR に記録しなかった判断に見落としがないか
- doc-reviewer の指摘への対処は妥当か

技術選定の是非は設計案の選択で決着済みなので、ここで問い直しません。同じことを二度聞くのが承認ラウンドの冗長さの正体だからです。

### ビルド分割

設計に基づいてビルドの論理的な単位を整理し、`build-manager` が BP を見積もって分割します。tasklist の変更差分、依存グラフ、issue.md の内容が提示され、承認を求められます（G6）。**このゲートはどのプロファイルでも省略されません。**

BP の考え方は [BUILD](build.md#ビルドポイントbp) にあります。

## 成果物

```
cycles/{NNN}-{slug}/
├── design/
│   ├── codebase-survey.md    既存コードがある場合
│   ├── design-questions.md   質問が発生した場合
│   ├── design-delta.md
│   └── retrospective.md
├── tasklist.md
└── build-{NN}/issue.md
```

`design-delta.md` には、このサイクルで作るもの、永続ドキュメントのどこを更新する予定か、既存構造への影響を書きます。実装コードやビルド分割（`tasklist.md` が正）、恒久的な設計判断（ADR が正）、既に永続側にある内容は書きません。

「永続ドキュメントのどこを更新する予定か」は close-cycle と cycle-scanner の入力になります。

## 終わり方

PR はドキュメントのみです。**速やかにマージしてください。** `tasklist.md` がデフォルトブランチに入らないと、builder が依存ビルドの完了を判定できません。

次は新しいセッションで [BUILD](build.md) に進みます。依存関係のないビルドは並行して進められます。
