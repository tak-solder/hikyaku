# ARCHITECT — 設計

```
/hikyaku:architect [{cycle}]
```

企画成果物と既存コードを入力に、このサイクルの設計差分とビルド分割を決めます。企画内容そのものは変えません（スコープや優先度を変えるなら PLAN に差し戻します）。

## 永続ドキュメントは書き換えない

architect が作るのは「これから作るもの（to-be）」で、それは `design-delta.md` に書きます。`overview` や `constraints` は「実装済みの現実（as-is）」なので触りません。並行して走る別サイクルが、まだ動いていない設計を現実として読む事故を防ぐためです。

例外は ADR だけです。決定した時点で記録するのが ADR 本来の思想なので、`status: accepted`（決定済み・未実装）で追記します。`implemented` への更新は close-cycle が行います。

## 進み方

設定の解決、企画成果物の読み込み、ブランチの確認は、セッションを始めるたびに architect が行います。その先の手順は `hikyaku step next` が1手ずつ決めます。並行サイクルの確認が要るか、どのゲートやレビューが有効かは、profile と設定、それにサイクルの状態から導かれるので、architect が自分で手順を組み立てることはありません。ビルド分割を担う build-manager も同じ仕組みで進みます。

進捗は `design/progress.jsonl` に1手ずつ追記され、成果物と一緒にコミットされます。build-manager の記録も同じファイルに入ります。中断して別のセッションで再開すると、続きの1手がそのまま返ります。G2 と G4 の承認は、差し戻すか前のステップを報告し直すまで有効です。承認したあとに `codebase-survey.md` や `design-delta.md` を直しても自動では無効にならず、変更は Git の履歴とレビューで追います。

再設計の回で差し戻しを解決したあと、同じブランチでもう一度差し戻されたら、architect は前の回のまま進めずに止まり、新しい再設計の回を区切るよう案内します。追加設計の回では、足したビルドがまだ完了していないことをビルド分割の報告のときに確かめます。足したビルドがあとで PR まで進んでも、ビルド分割には戻りません。

### 並行サイクルの確認

他に走行中のサイクルがあれば、`cycle-scanner` がそれぞれの設計差分を読んで重複を報告します。重複が見つかったら、設計を分けるか、どちらかに寄せるか、そのまま進めるかを聞かれます。

全走行サイクルの本文を本セッションで読むと大規模リポジトリでコンテキストが破綻するため、軽量モデルのエージェントに委任し、返ってきた重複箇所だけを扱います。

### 既存コードの調査

探索は `code-explorer` に委任されます。ただし設計判断に必要な Key Files は本セッション自身が読みます。要約だけで設計を進めると、規約やインターフェースの解像度が落ちるためです。

`overview` が登録されていれば、調査は差分だけになります。今回のスコープに関係する箇所、`overview` に無い詳細、`overview` とコードのズレだけを調べ、既にあることは再確認しません。`overview` が無ければ全体調査になるので、初回サイクルのコストは高くなります。2周目からは close-cycle が作った `overview` が効きます。

結果は `design/codebase-survey.md` に書かれます。`overview` に既にある内容は書きません。書いてしまうと2周目以降も初回と同じコストがかかり、`overview` を持つ意味が失われます。

調査のあと、変えるパスを `hikyaku areas dormant --paths` に渡します。長く触られていなかった領域があれば、結び付いた rule・ADR・constraints の項目が示されるので、設計の前に前提が今も成り立つかを確かめます。長く触られていなかったこと自体が、前提が変わったかもしれないという信号です。`codebase-survey.md` には休眠の事実と基準の所在だけを書きます（[領域の開発頻度](../configuration/persistence.md#領域の開発頻度)）。

`thorough` ではここで確認が入ります（G2）。他のプロファイルでは止まりません。

### 設計に関する質問

技術選定、データ設計、インターフェース設計、非機能要件、既存コードとの整合について、不明点が1回にまとめて聞かれます。`codebase-survey.md` や `constraints` に書かれていることは聞かれません。記録は `design/design-questions.md` に残ります。実装で確かめるまで決めきれずに暫定で決めた判断は、いつ・誰が確かめるかとともに未決事項（`design/decisions.jsonl`）に残ります。

### 設計案の選択

主要な技術判断を列挙し、それぞれについて「妥当な代替案が複数あり、トレードオフが非自明か」を評価します。既存規約から自明なもの、合理的な選択肢が1つしかないものは分岐なしとして扱われ、ADR も作られません。

分岐がある判断では `code-architect` が2〜3並列で起動し、異なる観点の案（Minimal / Clean / Pragmatic など）を返します。トレードオフ表と推奨案が提示され、選択を求められます（G3）。

`express` だけはこのゲートが外れ、推奨案がそのまま採用されます。その場合もトレードオフ表と推奨理由は破棄されず、ADR の「検討した案」「採用理由」に残り、採用案と退けた案が PR 本文にも出ます。承認を省いた以上、判断を後から追える場所を残すためです。

ルート設定で `[app]` を宣言しているワークスペースでは、案を作ったあとに、提示する案のうち最も重い害と、全案が触れるパスを申告します。その害が AI に任せてよい上限を超えるか、パスが重い領域に当たるか、申告が欠けていれば、G3 は同意になり、`express` でも止まって選択を求められます。G4 では申告の裏取りが行われ、`design-delta.md` とこのサイクルの ADR が、申告に無かった重い領域に触れていれば、G4 も同意になって止まります。このとき、当たった領域と触れたパスが示されます（[プロファイル](../configuration/profiles.md#承認ゲート)）。

確定した案は ADR に追記されます。`repo` 管理の ADR なら既存形式に合わせます。連番なら連番、独自テンプレートならそれに従い、status 欄が無い既存形式に勝手に欄を足すことはしません。

### 設計ドキュメントの承認

`design-delta.md` が作られ、承認を求められます（G4。`express` では省略）。**承認観点は「反映の正しさ」に限定されます。**

- 選択した案が `design-delta.md` に正しく反映されているか
- 分岐なしとして ADR に記録しなかった判断に見落としがないか
- doc-reviewer の指摘への対処は妥当か

技術選定の是非は設計案の選択で決着済みなので、ここで問い直しません。同じことを二度聞くのが承認ラウンドの冗長さの正体だからです。

提示の中身は `hikyaku gate brief G4` が組み立てます。ルート設定の [`[boundaries]`](../configuration/config-file.md#app-と-boundaries) で境界のパスを宣言していると、`design-delta.md` とこのサイクルの ADR が触れるパスを境界と照合し、外との境界の変更と内部の境界の変更に分けて示します。外との境界の変更は同意が要る変更で、G4 は同意になり、`express` でも止まります。外との境界はユーザーが同意するものなので、事後同意を選んでいても後に回しません。内部の境界の変更は確かめる変更として示され、G4 は確認のままです。境界は、作業ツリーの宣言と、ユーザーがマージした基準のブランチの宣言の和で照合するので、作業中のブランチで境界を消しても同意は外れません。基準を1つも読めず、作業ツリーにだけ境界の宣言があるときも、狭められていないかを確かめられないので同意になります。境界を宣言していなければ、従来どおり `design-delta.md` と指摘への対処が提示されます。全文は、求めたときに `--full` で出ます。

サイクルで [事後同意](../configuration/config-file.md#consent) が有効なら、設計案の選択（G3）とこの承認（G4）が上限を超えるリスクの受け入れになる回でも、ここでは止まりません。設計案の生成や `design-delta.md` の完了を報告するときに、`step report` が退けた安全側の案の利点（`--loses`）を求め、受け入れを拠り所の前提と一緒に未決事項の記録に積みます。積んだ受け入れは、PR を作る直前の同意ゲートでユーザーがまとめて同意します。その回の G3・G4 は確認として扱われ、プロファイルに従います。レビューで設計の文書が変わり、積んだ事項に無い重い領域に触れたときは、G4 はその場の同意に戻ります。

フィードバックがあれば設計に関する質問に戻り、そこから設計案・ADR・`design-delta.md`・レビュー・G4 をやり直します。既存の成果物は残っているので、答えに沿って見直すだけで済むところはそのまま進めます。

### ビルド分割

設計に基づいてビルドの論理的な単位を整理し、`build-manager` が各ビルドの予測ピークを見積もって分割します。`tasklist_review` が有効なら、書き込み前に `doc-reviewer`(`context: tasklist`)が予測ピークの成分の乖離や設計との網羅漏れを確認します。レビューは1回だけで、指摘を反映して見積もりからやり直しても、もう一度は回りません。その後、tasklist の変更差分、依存グラフ、issue.md の内容が提示され、承認を求められます(G6)。レビューのあとに変えたところがあれば、レビューを経ていない変更として分けて示されます。**このゲートはどのプロファイルでも省略されません。**

分割の前提は、各ビルドの PR をマージした時点で既存機能に影響せず、本番でどんな操作が起きてもデータが壊れたり不整合を起こしたりしないことです。データの形を変える設計では、`design-delta.md` に追加 → 書き込みの切り替え → 既存データの移行 → 旧形式の削除のような移行の段階が書かれ、分割はその段階に沿います。予測ピークが見積もりの上限（既定 540k）を超えるのに安全な分割が見つからないときは、超えたまま1ビルドにするか、設計に戻って移行の段階を足すかを聞かれます。安全でない分割（リリースしてはいけない中間状態で区切ること）が選択肢に出るのは、サイクルがそれを宣言していて、base_branch がリリースされるブランチでないときだけです（[`[data_integrity]`](../configuration/config-file.md#data_integrity)）。選んだビルドの `issue.md` には「マージ時点で残る危険」の節が付き、何が壊れうるか、なぜ安全に分けられなかったか、それを解消するビルドが書かれます。G6 ではこの節も提示されます。G6 でユーザーが受け入れたこと（マージ時点で残る危険など）は、ユーザーの言葉とともに受け入れたリスクとして未決事項の記録に残ります。`hikyaku validate` は、緩和が許されていないサイクルにこの節が無いか、解消するビルドが実在してこのビルドに依存しているかを確かめます。

各ビルドの `issue.md` には、そのビルドに効く永続ドキュメントの節へのポインタが「参照する設計ドキュメント」として書かれます。builder は `overview` / `decisions` / `constraints` の全文を読まず、ここが指す節だけを読むので、全文を読んで設計した architect が選ぶ必要があります。本文は写さず、論理名と節で指します。ビルドを後から分割したときは、ポインタも移した範囲に合わせて引き継がれます。

各ビルドの `issue.md` には、そのビルドで満たす受け入れ基準の番号も書かれます。分割のあとに `hikyaku validate` が、どのビルドにも割り当てられていない受け入れ基準が無いかを確かめます。漏れがあれば、既存のビルドに割り当てるか、満たすビルドを足します。

予測ピークの考え方は [BUILD](build.md#予測ピーク) にあります。

## 差し戻されたとき

builder から差し戻された場合は、`/hikyaku:architect {cycle} build-NN` のように差し戻し元のビルドを指定して起動します（差し戻しの流れは [BUILD](build.md#設計の前提が崩れたらarchitect-への差し戻し) にあります）。進み方は通常の設計とほぼ同じですが、いくつか違いがあります。

作業するのは、差し戻し元のビルドのブランチです。architect 用のブランチは切らず、設計の変更はそのビルドの PR に入ります。入力には、企画成果物と既存の `design-delta.md` に加えて、差し戻しの記録（サイクル直下の `return.md`）とビルドの `questions.md` を読みます。`design-delta.md` は書き換えるだけでなく、どの判断をなぜ撤回したかを残します。後からビルドの PR を読む人が、設計が変わった理由を追えるようにするためです。影響を受けるビルドは、新しいビルドを足すより既存のビルドの更新で扱い、G6 で承認を求められます。

差し戻しは委任の前提が崩れた出来事なので、再設計の回の最初に、委任を続けるかを尋ねられます（`delegation`）。プロファイルに関わらず、conductor で進めていてもユーザーが答えます。この回では G3 と G4 もユーザーが行います。

`design/progress.jsonl` には通常の設計の記録が完了済みで残っているので、再設計は `hikyaku step restart architect {cycle} --round return --reason "<理由>"` で再設計の回を区切ってから始めます。`step next` は通常の設計と同じ順に手順を返しながら、PR の代わりに差し戻しの解決（`return.md` などの削除）を返します。差し戻し中なのに回を区切っていなければ、`step next` はこのコマンドを示して止まります。`return.md` に試したこと、問題を変える選択肢とそれぞれで失うもの、推奨のどれかが欠けていれば、`step restart` は回を区切らずに欠けを示します。`return.md` を直してから区切り直してください。

最後に PR は作らず、`return.md` と差し戻し元のビルドの `plan.md`・`test-spec.md` を削除してコミットします。この削除が差し戻しの解決の記録になり、同じブランチで builder を起動し直せば実装計画からやり直せます。

## 全ビルドのあとに指摘を受けたとき

全ビルドを終えたあとにレビューで指摘を受け、対応するビルドを足したいときは、`/hikyaku:architect {cycle} add {指摘}` のように `add` に続けて指摘の内容を渡して起動します。指摘を渡さずに起動すると、指摘を添えて起動し直すよう案内されて終わります。完了していないビルドがあるあいだは使えません。指摘はそのビルドの中で扱います。

作業するのは architect のブランチで、全ビルドを取り込んだブランチ（通常はデフォルトブランチ）から切ります。並行サイクルの確認と既存コードの調査は済んでいるので行わず、指摘に関わるファイルだけを読みます。指摘への対応に設計の変更が要るときだけ、通常の設計と同じく質問・設計判断・承認（G3・G4）を経て、`design-delta.md` にどの指摘を受けて何を変えたかを残します。そのうえで、指摘に対応するビルドを build-manager が追加し（G6）、通常どおり PR を作ります。完了したビルドは更新しません。追加したビルドの `issue.md` には、対応する指摘が書かれます。

追加設計も、`hikyaku step restart architect {cycle} --round add --reason "<指摘の要約>"` で追加設計の回を区切ってから始めます。この回では並行サイクルの確認と調査が返らず、最初に設計の変更が要るかを判断します。要らなければ、そのままビルドの追加へ進みます。

## 成果物

```
cycles/{NNN}-{slug}/
├── design/
│   ├── codebase-survey.md    既存コードがある場合
│   ├── design-questions.md   質問が発生した場合
│   ├── design-delta.md
│   ├── progress.jsonl        手順の進捗
│   └── retrospective.md
├── tasklist.md
└── build-{NN}/issue.md
```

`design-delta.md` には、このサイクルで作るもの、永続ドキュメントのどこを更新する予定か、既存構造への影響を書きます。実装コードやビルド分割（`tasklist.md` が正）、恒久的な設計判断（ADR が正）、既に永続側にある内容は書きません。

「永続ドキュメントのどこを更新する予定か」は close-cycle と cycle-scanner の入力になります。

`user-stories.md` の「スコープ外」に挙げたものは設計に含めません。設計の途中でそれが必要だと分かったら、設計に入れずに企画フェーズへの差し戻しが提案されます。

## 終わり方

設計フェーズのマージの前にユーザーが同意すると記録された項目（`merge@architect` の受け入れたリスク・異議）があると、PR を作る直前に同意ゲートが現れます。扱いは builder と同じで、事後同意を選んだサイクルでは、ほかの作業単位で記録された項目だけがあるときも現れます（[事後同意](build.md#マージの前の同意事後同意)）。設計フェーズで記録した項目を退けると、ゲートが戻り先を示します。G3 で記録した項目なら設計案の生成から、G4 なら `design-delta.md` の作成から作り直します。企画フェーズなど前のフェーズで記録した項目を退けたときは、そのフェーズで作り直し、ユーザーが解決を記録するまで進みません。差し戻しからの再設計の回は PR を作らないので現れません。PR の本文には `hikyaku pr body` の節が貼られます。

PR はドキュメントのみです。**速やかにマージしてください。** `tasklist.md` がデフォルトブランチに入らないと、他のサイクルからも外からもこのサイクルの進捗が見えません。PR は Draft で作られ、`[pr] auto_ready` が true（既定）ならすぐに Ready for Review になります（[設定](../configuration/config-file.md#pr)）。conductor の子として動くときは Ready にせず、監督が取り込む前に Ready にします。

マージ前に builder を始めることはできます（このブランチから積めば、着手判定は成果が履歴に在るかで行うため通ります）。ただし `completed` の判定はデフォルトブランチを見るので、マージするまでサイクルは締められません。

次は新しいセッションで [BUILD](build.md) に進みます。依存関係のないビルドは並行して進められます。
