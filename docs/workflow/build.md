# BUILD — 実装

```
/hikyaku:builder [{cycle}] [{buildID}]
```

1ビルド = 1セッションで、実装から PR 作成までを完結させます。

## 対象ビルドの決まり方

buildID を省略すると、着手可能なビルドから選ばれます。着手可能とは、依存するビルドの成果が**いま居るブランチの履歴に在る**ということで、判定には `HEAD` の `tasklist.md` の `PR` 列を使います。待機中と表示されたビルドには着手しません。

`PR` 列の更新は実装と同じコミットに同梱されるため、`HEAD` で `PR` 列が非空であることが、そのまま実装が履歴に在ることを意味します。作業ツリーのファイルではなく `HEAD` を読むのは、未コミットの編集を数えないためです。`tasklist done` を実行してからコミットするまでのあいだ、そのビルドは未完了に見えます。

```bash
hikyaku next
```

同じサイクルでも、どのブランチに居るかで答えが変わります。デフォルトブランチに居るなら先行ビルドはマージされている必要があり、先行ビルドのブランチに居るならその成果は既に手元にあるので着手できます。ブランチを切り替えたあとに `next` をもう一度実行するのはこのためです。縮退は常に安全側で、手元に無いコードの上に実装を始めることはありません。

依存関係のないビルドは並行して進められます。ただし「着手中」と表示されたビルドは他のセッションが作業している可能性があるため、選ぶ前に確認されます。着手中の判定はブランチの存在から導出しています。待機中の行に「ブランチあり」が付く場合も同じで、他のセッションが積んで作業している可能性があります。

## マージを待たずに積む（スタック）

先行ビルドの PR がマージされるのを待たずに、そのブランチから後続ビルドを始められます。先行ビルドの成果はブランチの履歴に入っているので、`next` は着手可能と判定します。

この場合、後続ビルドの PR のマージ先は**デフォルトブランチではなく先行ビルドのブランチ**です。デフォルトブランチ宛てに作ると先行ビルドの差分まで含んだ PR になってしまうため、builder は PR を作る直前に `hikyaku pr base` でマージ先を導出します。コードレビューの差分基準も同じ値を使います。

積んだかどうかはどこにも記録されません。同じサイクルの Hikyaku ブランチのうち「現在のブランチの履歴に含まれていて、まだデフォルトブランチに取り込まれていない、最も近いもの」として毎回導出されます。先行ビルドがマージされれば、同じコマンドが自然にデフォルトブランチを返すようになります。

積んだブランチから離れると、後続ビルドは待機中に戻ります。先行ビルドの成果が手元から消えるためで、これも安全側の縮退です。

## 永続ドキュメントは書き換えない

builder は永続ドキュメントを読むだけです。実装中に設計とのズレや新たに判明した制約があれば `handoff.md` の「永続化すること」に記録し、close-cycle がそれを反映します。

過去の ADR を実装中に覆さないのも同じ枠組みです。覆す必要が生じた場合は、覆した ADR・理由・影響範囲を `handoff.md` に書きます。ADR 自体の更新は close-cycle の仕事です。

## 実装で得た知見は、そのビルドで片づける

落とし穴や失敗の回避策は、見つけたビルドが最もよく知っています。後続のビルドが同じものを踏まないよう、builder は重要度と置き場を決めて、できるものはそのビルドの PR の中で片づけます（[知見の置き場](../configuration/persistence.md)）。

機械で防げるものは、テスト・共通ヘルパー・設定として実装に含めます。回避のために入れた実装には、消されないよう理由をその場のコメントで書きます。一部のファイルを触るときだけ効く注意は、パス指定の rule（`.claude/rules/`）として同じ PR に含めます。rule は永続ドキュメントではなく、そのビルドの成果物です。それ以外（スキルにする手順、`conventions` や `constraints` に入れる内容）は `handoff.md` に書いて close-cycle に預けます。すぐ失敗して、すぐ直せる程度の知見は、どこにも書きません。

## マージした時点で本番データを壊さない

各ビルドの実装は、PR をマージした時点で既存機能に影響せず、本番でどんな操作が起きてもデータが壊れたり不整合を起こしたりしないようにします。builder は `plan.md` の非機能要件に「マージ時点のデータ安全」として根拠を書き、コードレビューの前に、スキーマ・マイグレーション・保存形式・API の契約に触れる差分をその根拠と突き合わせます。組み込みのレビュー機能は、このビルドの後に何がマージされるかを知らないためです。

例外は、architect がやむを得ず安全でない分割を選び、`issue.md` に「マージ時点で残る危険」を書いたビルドだけです（[ARCHITECT](architect.md#ビルド分割)）。その場合も、書かれた範囲を超える危険は残しません。書かれていない危険を残さないと作れないと分かったら、builder は自分で緩めず、[architect への差し戻し](#設計の前提が崩れたらarchitect-への差し戻し) と同じ確認をします。

## 進み方

コンテキストの復元とブランチの確認は、セッションを始めるたびに builder が行います。その先の手順は `hikyaku step next` が1手ずつ決めます。どのレビューが有効か、どのゲートで止まるかは、profile と設定、それにビルドの進捗から導かれます。builder が自分で手順を組み立てないので、「小さなビルドだから」とレビューを省くことは起きません。スキップできるのはテストシナリオのようにスキップを許したステップだけで、そのときも理由が記録に残ります。

進捗は `build-{NN}/progress.jsonl` に1手ずつ追記され、成果物と一緒にコミットされます。現在地は保存されず、毎回この記録と成果物から導き直されます。中断して別のセッションで再開すると、続きの1手がそのまま返ります。G8 の承認は、差し戻すか前のステップを報告し直すまで有効です。実装中に `plan.md` のチェックボックスを更新するような変更では巻き戻りません。スコープが変わって `plan.md` を直したときは、builder が `plan` から報告し直し、G8 の承認を取り直します。

### コンテキストの復元

読むものは2層で返ります。サイクル（このサイクルが作ろうとしている差分）と、ビルド（同一サイクル内の先行ビルドの `handoff.md`）です。

`overview` / `decisions` / `constraints` は候補に並びません。builder が読むのは、`issue.md` の「参照する設計ドキュメント」が指す節だけです。どの節がそのビルドに効くかは、全文を読んで設計した architect が選んでいます。builder が全文を読み直すと、実装のセッションが設計のときと同じ量を読むことになります。architect の選び漏れは、plan のレビューで `doc-reviewer` が `overview` / `decisions` / `constraints` の全文と突き合わせて拾います。実装中に指されていない制約に関わりそうだと感じたときに、builder が自分でその節を読むことは妨げません。

`conventions` は扱いが違います。コードを書くたびに効く取り決めなので、節を選んで渡すものではありません。AGENTS.md や CLAUDE.md に登録されていればホストが自動で読み込みます。`docs/conventions.md` のような別のファイルに登録されている場合は自動では読み込まれないので、builder の読む候補として返り、plan のレビューにも渡されます。

依存ビルドの `handoff.md` は `tasklist.md` の依存グラフから自動で辿られます。直接依存する分だけが返るので、全ビルド分を読むことにはなりません。

### 実装計画とテストシナリオ

`plan.md` には依存パッケージの選定、クラス設計（メソッドシグネチャ）、非機能要件を書きます。詳細な実装コードやテストコードの書き方は書きません。

`plan.md` には予測ピークの見積もりも書きます。architect 段階の予測は `issue.md` のスコープ記述からの見積もりでしたが、この時点ではクラス設計と実装ステップまで具体化しているので、成分を見直して見積もり直します。読むファイルと作成するファイルを名前で列挙し、ガイドに沿って5つの成分のトークンと根拠を決め、`hikyaku tokens estimate` に渡して、返ってきた内訳表をそのまま貼ります。合計と判定はコマンドの仕事で、builder が決めるのは成分の見積もりだけです。

`doc-reviewer` によるレビューが有効なプロファイル（express / standard / thorough）では、`plan.md` の完成直後に `context: plan` でレビューが入ります。**このレビューには予測ピークの成分の妥当性も含まれます。** 列挙したファイルとクラス設計が合っていない、計画から見て見通せない作業があるのに未知の領域が 0 になっている、といった食い違いが指摘されます。見積もり直した予測ピークが `split_above`（既定 450k）を超えた場合は、`build-manager` を呼び出して分割を検討します。

`thorough` では、その直後に `plan.md` 単独の人間承認も入ります（G7）。他のプロファイルでは人間の承認は次のゲートにまとめられます。

テストシナリオの洗い出しはサブエージェントに委任され、`test-spec.md` として返ります。Given/When/Then の形式で、正常系・異常系・境界値を具体的な値で書きます。各シナリオには、検証する受け入れ基準の番号（`US-1.1` など）が添えられます。`test-spec.md` の完成直後には、`doc-reviewer` によるレビューがどのプロファイルでも同じ位置（`context: test-spec`）で入ります。

`plan.md` と `test-spec.md` がまとめて提示され、承認を求められます（G8）。**このゲートはどのプロファイルでも省略されません。** 観点は実装ステップの妥当性、受け入れ基準の網羅性、テストのカバー範囲、不要なテストの有無です。

### コンテキストの区切り

1ビルドのセッションでは、自動コンパクションを起こさないことを前提にしています。そのため、G8 の提示・実装開始前・レビュー前の3つの区切りで、`step next` がメインセッションのコンテキストを実測し、目安と比べます。目安の既定値は順に 250k・300k・400k トークンで、1M のウィンドウを前提にしています（[`[context]`](../configuration/config-file.md#context)）。

目安を超えていても、自動では止まりません。builder が残りの作業を見て、継続するか分割するかを判断します。継続した場合は、そのことと理由が次のゲートの報告で伝えられます。G8 なら承認の提示の中、実装開始前とレビュー前ならレビュー結果の提示の中です。指摘が0件でレビュー結果の提示が無いときは、完了の案内で伝えられます。G8 は差し戻されて提示し直すたびに測り直されます。

Codex でウィンドウが 500k 未満と記録されているときは、狙いの 400k 前後で自動コンパクションに当たるため、ウィンドウを上げる方法が注意として出ます。記録が読めない環境（Codex のクラウドなど）では「計測不可」と理由を示し、見積もりだけで進みます。区切りの値は `progress.jsonl` に残り、`hikyaku tokens history` で予測と実測のピークと並べて見られます。

### 実装と検証

`plan.md` のステップに沿って実装し、リポジトリの規約に従って lint / test / build を実行します。全部パスするまで push しません。エラーが続く場合は試行回数の上限で止まり、判断を求められます。

### コードレビュー

レビューの前に、実装はローカルでコミットされます（push はまだしません）。レビューはコミット済みの差分を対象にするためです。

コードレビューは **どのプロファイルでも実行されます。** コードは差分が大きく、人間の承認ゲートが拾える粒度を超えるためです。レビューそのものは Claude Code の `/code-review` か Codex の `codex exec review` が行い、バグと規約違反を見ます。どちらを使うか、どのモデルとエフォートで何回まで回すかは `[review]` で決まります（[.hikyaku.config](../configuration/config-file.md#review)）。組み込みのレビュー機能は plan.md を読まないので、計画やスコープから外れた変更がないかは builder 自身が差分のファイル一覧と plan.md・issue.md を突き合わせて確かめます。

セキュリティレビューの起動はプロファイルによります。

| 設定値 | 挙動 |
|---|---|
| `on`（thorough） | 常に起動する |
| `recommended`（express / economy / standard） | 判定基準に該当する場合のみ、起動するか確認する |
| `off`（個別キーで明示したときだけ） | 起動しない |

既定の判定基準は個人情報・秘密情報、認証・認可、決済の3カテゴリです。プロダクト固有の基準は `[review.security].triggers` で置き換えられます（[.hikyaku.config](../configuration/config-file.md#reviewsecurity)）。該当すると判断された場合は根拠が一行で示されるので、外れていれば断ってください。

Claude でセキュリティレビューを行うときは `/security-review` を使います。ただし `/security-review` は origin のデフォルトブランチとの差分を見るため、スタックしたビルドでは先行ビルドの差分が混ざります。origin/HEAD が無いリポジトリでは、エラーにならずに空の結果を返します。そこでこの2つの場合と Codex では、観点と差分の基準を書いた指示文を渡す形で代えます。

2つのレビューは別のプロセスとして並列に動き、生の出力は `.git` の中に保存されます（コミットはされません）。レビューが失敗したり空の結果を返したりしたときは、指摘0件として扱わずに報告されます。

同じ箇所への重複指摘は1件に束ねられ、セキュリティの指摘が優先されます。builder はコードと承認済み仕様・スコープに照らして妥当性を判断し、不採用の指摘には理由を残します。確度の低い懸念は「要確認」ラベル付きで別枠になります。

`max_rounds = 1` なら、妥当で承認済みスコープ内の指摘を自動修正し、検証を通して追加でコミットします。対応確認や再レビューは挟まず、申し送りと PR 作成へ進みます。自動修正できない指摘は理由とともに申し送りに残します。

`max_rounds` が2以上なら、最終回より前は妥当な指摘を自動修正し、検証・追加コミット後に再レビューします。同じ指摘が繰り返されても途中で対応確認は挟みません。最終回に未解決の指摘がある場合だけ、「修正して再レビューせずに進める」「新ビルド化」「そのまま進める」から対応を選びます。途中で自動修正できなかった指摘も、最終回まで未解決ならこの確認に含まれます。指摘が解消した時点で、上限より前でもレビューを終了します。設計の前提が崩れた場合は、回数に関わらず設計方針を確認します。

`max_rounds = 0`（無制限）では、従来どおり初回に対応を確認し、`auto_fix = true` のときだけ2回目以降の確認を省いて修正します。確度の低い懸念や、同じ指摘が繰り返されて打ち切る場合は確認します。`auto_fix` は無制限の場合にだけ適用されます。新ビルド化を選ぶと `build-manager` がビルドを追加し、そのまま進める指摘は `handoff.md` の「残したこと」に記録します。

### 申し送り

`handoff.md` に書くのは、PR の diff を読んでも分からないことだけです。節は3つあります。

| 節 | 書くこと |
|---|---|
| 後続ビルドが前提にすること | 採った判断とその理由、`design-delta.md` の予定から変えた点、使い方に罠があるインターフェース、diff に現れない手作業 |
| 残したこと | スコープ外として残した作業、そのまま進めたレビュー指摘、入れられなかった機械的な対策 |
| 永続化すること | close-cycle が反映する知見。宛先・重要度・そのまま書ける文面・根拠を1件1行で |

実装内容の要約は PR 本文、公開インターフェースはコード、環境変数やマイグレーションは diff が正なので、ここには写しません。

「永続化すること」は、振り返りと同じ行の形で書きます。形が決まっているので、close-cycle は `hikyaku promotions` でサイクル全体の分を集められます。そのビルドの PR で書いた rule も、ここに控えておきます。

### PR と完了記録

振り返りは PR を作る前に済ませ、`retrospective.md` までコミットしてから push します。そのあと PR を作り、`tasklist.md` の `PR` 列を埋めて同じブランチへ push します。PR を作らないと URL が無いのでこの順序になりますが、push した分は同じ PR に載るので同梱されることは変わりません。

振り返りの記録は PR 作成前の push にまとめます。作成後は完了記録を push し、公開のステップで Ready への切り替えとレビュアー依頼を行います。公開の報告もコミットして push するため、再開時に未実施として戻ることはありません。

PR は Draft で作られ、既定では完了記録を push してから Ready for Review に切り替わります。`[pr] auto_ready = false` にすると Draft のまま残るので、内容を確認してから自分で `gh pr ready <PR>` を実行してください。conductor の子として動く builder は、この設定に関わらず PR を Ready にしません。監督が取り込む前に Ready にします。リポジトリが Draft PR に対応していない場合は通常の PR で作られ、そのことが完了時に伝えられます。Ready にする操作に失敗したときも PR は Draft のまま残るので、表示されたコマンドで Ready にしてください。

**この更新は必ずこのビルドの PR に同梱してください。** 先にデフォルトブランチへ入れると、実装が入っていないツリーで `PR` 列だけが埋まった状態になります。`PR` 列が非空であること自体が「その実装がこのツリーに在る」ことを意味するのは、この同梱が守られているからです。

PR のマージ先は `hikyaku pr base` が導出します。通常はデフォルトブランチですが、先行ビルドのブランチから積んでいる場合はそのブランチです。

このビルドに依存する後続ビルドは、この PR がマージされてから開始するのが既定です。待たずに進める場合は、このブランチから積みます。

## 実装中にスコープが変わったら

`build-manager` を呼び出してビルドを追加・更新・分割します。呼び出しの契機は主に4つです。

- `plan.md` を書いたら、見積もり直した予測ピークが `split_above` を超えていた → 分割
- 実装中に想定外の複雑さや未定義の依存が判明した → 追加・更新
- レビュー指摘を「新ビルド化して後で対応」にした → 追加
- 意図的に先送りした作業がある → 追加

現在のビルドのスコープが変わった場合は `plan.md` を修正して承認からやり直します。新ビルドが追加されただけなら、そのまま作業を続けます。

## 設計の前提が崩れたら（architect への差し戻し）

設計どおりに作ると受け入れ基準を満たせない、あるいは設計が前提にしている事実が実際のコードと食い違っていて設計の判断が変わる、と分かることがあります。builder はこのとき自分で設計を変えず、何と何が矛盾しているかを示して、設計に合わせる（要件を改める）、このビルドの中で設計を改める、architect に差し戻す、のどれにするかを確認します。ビルドの分割や追加で済むスコープの問題は、上の build-manager の経路で扱います。

差し戻す場合、builder はサイクル直下に `return.md` を書き、このビルドのブランチにコミットして push してから止まります。`handoff.md`・振り返り・PR・`tasklist done` はどれも行いません。どれもビルドの完了の印として読まれるためです。このブランチで `hikyaku cycle status` を実行すると、フェーズは `building` のまま「差し戻し中: build-NN」と表示され、再開コマンドとして `/hikyaku:architect {cycle} build-NN` が案内されます。

再設計は、architect がこのビルドのブランチ上で行います。architect 用のブランチは切らず、設計の変更はこのビルドの PR に入ります。積んでいる場合も、連鎖は一直線のまま保てます。architect は再設計の最後に `return.md` と、古い設計の上で書かれた `plan.md`・`test-spec.md` を削除します。そのあと同じブランチで `/hikyaku:builder` を起動し直すと、実装計画からやり直しになります。

`return.md` は差し戻し元のブランチにしか無いので、他のブランチやチェックアウトからは差し戻しが見えません。差し戻しに気づく必要があるのは、差し戻しを受けた人と、そのブランチで動くスキルだけだからです。積んでいる後続ビルドがあれば、それも同じ設計の上に作られているので、再設計が終わるまで止めてください。

## PR レビュー指摘への対応

PR にレビューが付いたら、同じサイクル・同じビルドで `/hikyaku:builder` を呼び出します。`plan.md` を読んでコンテキストを復元し、修正・検証・振り返りの追記を済ませてから、まとめて1回 push します。

更新してよいのはサイクルドキュメントだけです（`plan.md`, `issue.md`, `test-spec.md`, `handoff.md`, 設計レベルの変更があれば `design-delta.md`）。永続ドキュメントは更新せず、昇格が必要な内容は `handoff.md` の「永続化すること」に記録します。

## 予測ピーク

予測ピークは、ビルドを1つのセッションで実装から PR まで進めたとき、メインセッションのコンテキストがどこまで膨らむかの予測（トークン）です。1ビルドのセッションでコンパクションを起こさないことを、ビルド設計の絶対条件にしています。コンパクションが起きると、セッションは失敗するより品質が落ちる形で崩れ、しかも崩れたことに気づきにくいためです。一方で、小さすぎるビルドは PR と引き継ぎを増やすだけなので、上限ではなく狙いの帯で判定します。

| 予測ピーク | 判定 |
|----|------|
| 300k 未満 | 統合を検討（推奨のみ） |
| 300k〜450k | 狙いの帯 |
| 450k 超 | 分割を検討（原則として分割する） |

予測ピークは、固定費・読み込み・実装・テスト・未知の領域の5つの成分の和です。各成分は build-manager と builder が見積もりのガイドに沿って見積もり、`hikyaku tokens estimate` が合計して判定します。ガイドはプラグインの標準のものか、リポジトリが置いた `{HIKYAKU_ROOT}/token-guide/guide.md` で、実績で補正していきます（[予測ピークと見積もりのガイド](../configuration/token-guide.md)）。帯の境目は `.hikyaku.config` の [`[context]`](../configuration/config-file.md#context) の `merge_below` と `split_above` で変えられます。

450k を超えても分割せずに済ませてよいのは、分割するとマージコンフリクトが避けられない場合と、分割の一方がビルドとして成立しない場合だけで、その理由は `issue.md` に残ります。分割すると途中のビルドのマージ時点でデータの安全を保てない場合は、上限を超えたまま1ビルドにするか、設計に戻って移行の段階を足すかを聞かれます。統合の検討は推奨にとどまります。統合すると PR が大きくなり、並行して進められるビルドが減るためです。

見積もりは外れるので、「コンパクションを起こさない」ことは実行時の実測でも確かめます（[コンテキストの区切り](#コンテキストの区切り)）。

### 予測と実測

予測ピークは architect（`issue.md` のスコープから）と builder（`plan.md` の実装計画から）の2段階で見積もられ、ビルドの振り返りで実測と突き合わせられます。実測は `hikyaku tokens session` がホストの記録から読んだ、そのビルドのメインセッションのピークです。あわせて `hikyaku tokens history build-NN` が PR の base からの差分を数え（ワークフロー成果物と生成物は除きます）、書いた量の記録として残します。

結果は `retrospective.md` の「予測ピークの振り返り」に、2段階の予測・セッションの実測・差分の集計・1セッションで完結したか・乖離の要因として残ります。**乖離を責めるための記録ではありません。** 乖離の要因は、どの成分をどちらへ、なぜ読み違えたかとして書かれます。サイクルを終えるとき、同じ向きに大きく外れたビルドが複数あれば、close-cycle が `/hikyaku:token-guide` を呼んで見積もりのガイドの見直しを別の PR にします。

振り返りでは、以後に効く知見（とくに、ユーザーから受けたスキル外の指示）と、読み込まれたが役に立たなかった記述も記録します。後者は「古い」「自明」「無関係」の理由を付けて書き、close-cycle が文書を削る根拠になります（[消すこと](../configuration/persistence.md#消すこと)）。

`retrospective` が `skip` のプロファイル（`economy`）では、実績もこれらの記録も行われません。

## 成果物

```
cycles/{NNN}-{slug}/build-{NN}/
├── issue.md          architect が作成
├── questions.md      質問が発生した場合のみ
├── plan.md
├── test-spec.md      テスト対象があるビルドのみ
├── handoff.md
├── progress.jsonl    手順の進捗（hikyaku step report が追記する）
└── retrospective.md
```

## 終わり方

未完了のビルドがあれば、新しいセッションで次の `/hikyaku:builder` に進みます。全ビルドが完了したら [CLOSE](close.md) です。

**完了したまま放置しないでください。** 実装は main に入っているのに `overview` は古いままなので、この期間に他サイクルの architect が走ると、古い現実を信じて設計します。
