# conductor — ARCHITECT 以降を任せる

`/hikyaku:conductor` は、PLAN を終えたサイクルを ARCHITECT から最後のビルドまで進めます。あなたが開いているセッションが監督になり、各フェーズは監督が起動する非対話の子セッション（`claude -p`）が、いつもの architect / builder / close-cycle のスキルのまま実行します。

子が承認や確認を求める箇所で止まると、監督が成果物を読んで答えます。ユーザーが答えるのは、要件のすり合わせ（PLAN）と、監督が自分で答えてはいけない問いだけです。

```
/hikyaku:planner      → ユーザーと要件をすり合わせる（いつもどおり）
/hikyaku:conductor    → architect → build-01 → build-02 … を子が実行し、監督が問いに答える
                         各フェーズの PR は conductor ブランチに向け、監督が取り込む
（ユーザーが conductor ブランチ → デフォルトブランチの PR をマージ）
/hikyaku:conductor    → close-cycle を子が実行する
```

## 使う前に

監督は自分のセッションの Bash で `claude -p` を起動します。この起動が許可ルールで止められないよう、監督を動かすリポジトリの `.claude/settings.json`（または `settings.local.json`）で許可してください。

```json
{
  "permissions": {
    "allow": ["Bash(claude -p:*)"]
  }
}
```

監督自身は、フェーズの PR を conductor ブランチに取り込むために `git merge` / `git push` / `git branch -d` などを実行します。普段どおり、許可を求められたら確認してください。

子に許可するツールは `hikyaku conductor launch` が決めます。既定はファイルの読み書きと検索、サブエージェント、`ls` / `cat`、スキルが使う `git` のサブコマンド、Hikyaku CLI の実行、PR の作成と参照（`gh pr create` / `gh pr view`）だけです。`node` は Hikyaku CLI を動かす形でしか許可せず、`git` も `git -c` や `git config` で始まる形は許可しません。どちらも、任意のコマンドを実行してほかの許可を迂回できる形だからです。テストの実行コマンド（`npm test` や `node --test` など）は既定に含まれないので、`.hikyaku.config` の `[conductor] allowed_tools` に足してコミットしておきます。許可が無いと、builder はローカル検証の段階で止まります。監督も起動前にこれを確かめ、足りなければ案内して止まります。

```toml
[conductor]
allowed_tools = ["Bash(npm test:*)"]
```

子のモデルは、既定では Claude Code の既定のモデルです。フェーズごとに変えたい場合（設計は opus、実装は sonnet など）は `[conductor] model` と `[conductor.models]` で指定します。モデルの指定も起動時に合意する設定に含まれるので、途中で変わることはありません。

```toml
[conductor]
model = "sonnet"

[conductor.models]
architect = "opus"
```

子は既定で auto モード（`--permission-mode auto`）で起動します。許可したツールに当たらない操作は Claude Code の安全判定にかかり、依頼の範囲を超える操作、知らない宛先への送信、読んだ内容に誘導されたように見える操作は止まりやすくなります（判定は安全を保証するものではありません）。ただし、許可したツールに当たる操作（`git push` や `gh pr create` など）は判定より先に許可されますし、ファイルの読み取りと作業ディレクトリの中の編集は判定にかかりません。auto モードを使えないモデルや、組織の設定で無効にされている環境では、Claude Code が Manual で起動し、許可したツールに当たらない操作は拒否されます。判定のぶんトークンと待ち時間が増えるので、従来の挙動に戻したいときは `[conductor] permission_mode = "acceptEdits"` にします。

```toml
[conductor]
permission_mode = "acceptEdits"
```

子に `bypassPermissions` は渡しません。`permission_mode` でも選べません。監督の目が届かないところで何でもできる状態を作らないためです。ただし、ツールの許可だけで子を完全に閉じ込めることはできません。子はファイルを書けるので、`.git/hooks` に置いたスクリプトは `git commit` のときに実行されますし、許可したテストのコマンドは子が編集したコードを実行します。信頼できないリポジトリや、秘密情報のある環境で動かすなら、サンドボックスやコンテナの中で動かしてください。設定キーの一覧は [.hikyaku.config](../configuration/config-file.md#conductor) にあります。

## 始める

PLAN を終えたら、サイクルを指定して起動します。

```
/hikyaku:conductor 002-billing
```

サイクルがまだ `planning`（user-stories.md が無い）なら、監督は `/hikyaku:planner` を案内して止まります。要件のすり合わせはユーザーと対話で行うもので、conductor の対象ではありません。

起動すると、監督は1回だけ確認を求めます。user-stories.md を承認済みの要件として扱うこと、監督が答える問いとユーザーに上げる問いの一覧、PR はマージしないこと、の3点です。同意ゲートはこの確認で監督に委任されることはなく、常にユーザーに上がります。一覧は `hikyaku conductor asks` が、サイクルのプロファイルと設定から計算します。

## 監督が答える問い、ユーザーに上げる問い

子が止まる箇所には、スキルの中で ID が付いています（`G8` や `review-findings` など）。監督は子の出力から ID を取り出し、既定の振り分けに従って答えるかユーザーに上げるかを決めます。

| 種別 | 例 | 既定 |
|---|---|---|
| 確認ゲート・経路の判断 | G3 / G4 / G6 / G8、`branch`、`overlap` | 監督 |
| 同意ゲート | `decisions`・`constraints` の変更を含む回の G10、差し戻しからの再設計の回の G3 / G4、`[app]` の宣言で上限を超える回の G3 / G4、`delegation`（差し戻しや設計と要件の衝突のあと、委任を続けるか） | 常にユーザー |
| 仕様の確認 | `questions`、`design-conflict`、`unsafe-split`、`review-findings` | 監督 |
| 障害 | `retry-limit` | ユーザー |
| サイクルの中止・分類できない問い | `abandon`、`other` | 常にユーザー |

既定で監督が答える種別でも、issue と承認済みの成果物から導けない回答や、スコープを広げる回答が必要なら、監督はユーザーに上げます。たとえば builder が「設計どおりでは要件を満たせない」と止まったとき、監督は architect への差し戻しを選べますが、要件のほうを改める判断はしません。

監督が答えた判断は、子がその作業単位の未決事項の記録（`decisions.jsonl`）に、決めた人を監督として残します。後から誰が何を根拠に決めたかを `hikyaku ledger list` で追えます。

監督が答えてよいのは、受け入れを増やさない安全側の答えだけです。これは監督の判断に任せず、子を再開する `hikyaku conductor launch` が検査します。値の決まった問いでは、安全側の値（承認か差し戻し、G3 なら推奨案、`design-conflict` なら architect への差し戻し、`unsafe-split` なら1ビルドにまとめる、など）しか受け付けません。`questions` への答えや `review-findings` の「そのまま進める」のようにリスクを受け入れうる答えには、受け入れる害と拠り所の前提か、リスクが無いことの申告が要り、`[app]` の宣言で決まる上限を超える申告は拒まれます（事後同意を選んだサイクルの例外は [次の次の節](#事後同意を選んだサイクル)）。拒まれた問いは、監督が答えを変えて通すのではなく、ユーザーに上げます。申告は子の決定の記録に残り、最後の PR の本文の「監督が答えた問い」の節に、`hikyaku ledger answers` がそのまま並べます。

子の中で決定を記録する `hikyaku ledger` も、答えの出どころで縛られます。ユーザーの判断として記録できるのは、ユーザーの答えで再開された子が、その答えで閉じる事項に書くときだけです。監督の答えをユーザーの答えとして記録する取り違えを防ぐためで、子が自分で環境変数を付けるような偽装までは防ぎません。

## ユーザーに上げる問いを積み、走りきる

監督がユーザーに上げる問いに出会っても、その場では尋ねません。子に問いを記録させてから終えさせ、その問いに依存しないビルドを先に進めます。問いを出したビルドと、それに依存するビルドだけが答えを待ちます（ARCHITECT の問いなら全ビルドが待ちます）。着手できるビルドが無くなったところで、監督は待っている問いをまとめて尋ねます。席を外していても、答えの要らないところまでは進んでいる、という形です。

どのビルドが何を待っているかは保存せず、`hikyaku conductor waiting <cycle>`（`hikyaku next --json` の `waiting` も同じ）が、作業ツリーと各ビルドのブランチにある記録から毎回導きます。答えると、監督は conductor ブランチをそのビルドのブランチへ取り込んでから、答えを渡して子を再開します。子のセッションが残っていなければ、新しく起動して答えを渡します。

障害で子が止まったとき、規約違反が2回続いたとき、フェーズの PR の確認に通らなかったときは、従来どおりその場で尋ねます。積んでも先に進めないか、取り込む前に判断が要るものだからです。

振り分けは問いの ID ごとに変えられます。G8 だけは自分で見たい、という場合は `escalate` に並べます。

```toml
[conductor]
escalate = ["G8"]          # 監督が答える問いをユーザーに上げる
delegate = ["retry-limit"] # ユーザーに上げる問いを監督に任せる
```

同意ゲート、`abandon`、`other` は設定でも監督に任せられません。G3 / G4 のように回によって同意になるゲートは、監督が子の手順の位置からその回の種類を読み、同意の回なら `delegate` に書いてあってもユーザーに上げます。表に無い ID はエラーになります。全体の振り分けは `hikyaku conductor asks <cycle>` で確認できます。

振り分けと許可は、起動時の確認で合意したときのものに固定されます。子は `.hikyaku.config` を書き換えられるので、途中で `allowed_tools` や `delegate` が変わると、ユーザーが合意していない権限や振り分けが次の起動で効いてしまいます。監督は合意したときの設定のダイジェストを、以後の子の起動と結果の解析のたびに CLI に渡し、設定が変わっていれば止まってユーザーに確認します。ダイジェストには `.hikyaku.config`（ルートとサイクル）の内容そのものが入るので、`base_branch` や `[branch]` のように PR の向き先を変えるキーが書き換えられた場合も止まります。途中で振り分けを変えたいときは、監督を起動し直して合意からやり直してください。

## 事後同意を選んだサイクル

サイクルで事後同意（[設定ファイル](../configuration/config-file.md#consent) の `[consent] deferred`）を選んでいて、それが有効なら、AI に任せてよい上限を超える受け入れの同意を、各フェーズでは取らずに最後のビルドの同意ゲートでまとめて取ります。有効かどうかと理由は、起動時の確認に `hikyaku conductor asks` の出力として出ます。選んだだけでベースブランチにマージされていない、`[app]` に `merge_gate = "user"` が無い、といった理由で有効でなければ、従来どおりその場でユーザーに上がります。

有効なサイクルでは、architect と最後以外のビルドは、上限を超える受け入れ（G3・G4 で積んだリスクや、`ledger object --defer` で回した異議）があっても止まらずに PR を作ります。監督が答える問いでも、上限を超える受け入れの申告を、前提が `[app]` の宣言だけなら受け付けます。このとき子は答えを記録するのと同時に、その受け入れを「マージの前にユーザーが決める」リスクとして記録します。最後のビルド（ほかの全ビルドが完了を記録したビルド）の子は、PR を作る直前の同意ゲートで止まり、サイクル全体の項目が一覧になります。監督はその一覧を要約せずに示し、項目ごとにあなたの決定を受け取って子に渡します。同意しなかった項目は、そのビルドの中で作り直すか、architect へ差し戻します。

同意を遅らせるだけで、省くわけではありません。最後のビルドの同意ゲートで決めていない項目が残っていれば、監督は最後の PR を作らずにあなたに上げます。最後のビルドの同意ゲートを過ぎたあとの architect（最後の PR への指摘からの追加設計など）と close-cycle には、後ろに同意を取る場面が無いので、上限を超える受け入れは従来どおりその場であなたに上がります。

プロファイルは今までどおり効きます。プロファイルが決めているのは子がどこで止まるかなので、conductor のもとでは「監督がどれだけ確かめるか」に読み替わります。express なら G3 / G4 で止まらず、監督が設計を見るのは G6 からになります。ただし、差し戻しからの再設計の回は、どのプロファイルでも G3 / G4 で止まり、ユーザーに上がります。ルート設定で `[app]` を宣言していれば、AI に任せてよい上限を超える案がある回の G3 と、設計が G3 の申告に無い重い領域に触れる回の G4 も、同じようにユーザーに上がります（[プロファイル](../configuration/profiles.md#承認ゲート)）。止まる回数が増えるほど、子の再開の回数と費用も増えます。

## 監督が確かめること

監督は子の報告をそのまま信じません。子が done を出しても、子の `progress.jsonl` の記録から導いた手順がまだ途中なら、監督は子を再開して続けさせます。ゲートで止まったという報告も、手順がそのゲートに居ることを確かめてから扱います。plan.md と test-spec.md を承認する前（G8）には、issue.md の受け入れ基準をすべて網羅しているかを読みます。ビルドが終わったら、テストを自分で再実行し、差分が plan.md の範囲に収まっているかを確かめます。昇格（G10）のうち `decisions`・`constraints` の変更を含む回は同意なので、監督は承認せずユーザーに上げます。

監督が下した判断は、子が根拠とともに記録します。architect では `design/design-questions.md`、builder では `build-NN/questions.md`、tasklist の変更（G6）ではコミットメッセージです。PR をレビューするときに、どの承認をユーザーではなく監督が下したかを追えます。

昇格（G10）には記述の削除と置き換えも含まれます。ユーザーは G10 で、close の PR では本文に分けて書かれた追加・置き換え・削除で、それを確かめます。見積もりのガイドの見直しとフックの提案は、子が別のブランチの PR にします。どちらも監督は承認も取り込みもせず、採るかどうかはユーザーがマージで決めます。

## conductor ブランチに集め、最後に1本の PR にする

監督はまず、サイクルの統合ブランチ（`hikyaku/002-billing/conductor` のような conductor ブランチ）をデフォルトブランチから切ります。plan の PR がまだマージされていなければ、plan のブランチから切ります。各フェーズのブランチは conductor ブランチから切り、子が作る PR も conductor ブランチに向きます（`hikyaku pr base` が導出するので、特別な指定は要りません）。

子のフェーズが終わり、監督が検証を済ませると、監督はその PR を conductor ブランチに取り込み、フェーズのブランチを消します。取り込む前の確認は [次の節](#レビューのアサインと取り込み前の確認) にあります。次のフェーズは、取り込んだ後の conductor ブランチから切ります。ビルドの着手判定は「依存ビルドの成果がいま居るブランチの履歴にあるか」なので、conductor ブランチの上ならそのまま次のビルドに進めます。

最後のビルドを取り込むと、監督は conductor ブランチからデフォルトブランチへの PR を1本作って止まります。本文には取り込んだフェーズの PR が順に並び、監督が答えた問いの一覧（問い・答え・リスクの申告）が `hikyaku ledger answers` の出力のまま載ります。全フェーズで受け入れたリスクと、それへの同意・退けの決定（答えがあなたのものか監督のものか）は `hikyaku ledger pr-section <最後のビルド> --all` の出力のまま、サイクルの中で `[app]` の宣言を変えていれば、変わったキーとそれを拠り所にした受け入れが `hikyaku ledger premises --changed-from <ベースブランチ>` の出力のまま載ります。ユーザーがレビューしてマージしたあと、もう一度 `/hikyaku:conductor <cycle>` を実行すると、サイクルの状態が `completed` になっているので CLOSE から再開します。conductor ブランチ上で取り込まれただけではサイクルは `completed` にならないので、未マージの実装が「実装済みの現実」として永続ドキュメントに書かれることはありません。

外部連携が有効なら、最後の PR の本文にもサイクルの GitHub issue への参照（`Refs`）が入ります。issue を閉じるのは CLOSE の PR です。

conductor ブランチがマージされるまで、PLAN と ARCHITECT の成果物はデフォルトブランチに入りません。並行して走っている他のサイクルからは、このサイクルの設計が見えないということです。conductor は1サイクルずつ回す前提で、`hikyaku next` が複数のビルドを返しても1件ずつ実行します。

builder が architect へ差し戻した場合、監督は状態導出に従って、差し戻されたビルドのブランチのまま architect を起動します。再設計はそのビルドの PR に入り、ビルドが終わってから一緒に conductor ブランチへ取り込まれます。

最後の PR に付いた指摘へ、ビルドを足して対応することもできます。最後の PR を開いたまま `/hikyaku:conductor <cycle>` を実行し直すと、監督はビルドを足して対応するかを尋ねます。対応する指摘を伝えると、監督は architect を [指摘からの追加設計](architect.md#全ビルドのあとに指摘を受けたとき) として起動します。architect の PR と追加したビルドの PR は、ほかのフェーズと同じく conductor ブランチへ取り込まれ、最後のビルドを取り込んだところで、最後の PR の本文にその PR が追記されます。どの指摘に対応するかは、監督ではなくあなたが選びます。

## レビューのアサインと取り込み前の確認

PR を作るスキル（conductor を使わずに自分で実行する planner や builder も含みます）は、PR を作った直後に `[pr] reviewers` のレビュアーをアサインします。設定が空なら何もしません。conductor の子も同じスキルで PR を作るので、子の PR にも自動でアサインされます。conductor ブランチに向かうフェーズの PR だけは、人間のレビュアーを入れると取り込みのたびに止まってしまうため、別の一覧 `[conductor] phase_reviewers` を使います。Copilot のような Bot を入れておくのが想定の使い方です。

```toml
[pr]
reviewers = ["alice", "@copilot"]   # デフォルトブランチ向けの PR（通常のフローと、conductor の最後の PR）
reviewers_skip = ["init", "token-guide"] # アサインをオフにするスキル

[conductor]
phase_reviewers = ["@copilot"]      # conductor ブランチ向けのフェーズの PR
review_timeout = 15                 # レビューや CI を待つ上限（分）
```

監督は、フェーズの PR を取り込む前に `hikyaku conductor check-pr` で次を確かめます。PR のマージ先が conductor ブランチであること、PR が開いていること、Draft でない（Ready for Review の）こと、レビューの依頼が残っていないこと、未解決のレビュースレッドが無いこと、CI が失敗も待機もしていないことです。取り込みはローカルの `git merge` と push で行うので、GitHub のブランチ保護や必須チェックは働きません。この確認がその代わりです。監督が取り込むのは、この確認をしたときの PR の head のコミットです。手元のフェーズのブランチやリモートの先端がそのコミットと食い違っていれば、確認していないコミットが混ざるので、取り込まずにユーザーに確認します。

CI の実行中や、レビューの依頼が残っているあいだは、`review_timeout` で決めた時間（既定 15 分）だけ待って確かめ直します。Copilot のレビューが付くと依頼が消えるので、そこで次の確認に進みます。Draft、未解決のレビュースレッド、CI の失敗、マージ先の食い違いは待っても解消しないので、見つけた時点で止まります。

止まったとき、監督は取り込まずにユーザーに確認します。レビューの指摘が残っている場合も、監督が自分で対応したり、子を再開して直させたりはしません。あなたが対応するか、同意して resolve したあとで、監督が確認をやり直します。Draft を外したり、レビューの依頼を取り下げたりもしません。承認は既定では求めません。`[conductor] require_approval = true` にすると、1人以上の承認があり、変更の要求が残っていないことも条件になります。変更を要求したレビュアーがそのあとコメントだけを返しても、要求は残ったままと判定します。子の PR はあなたの `gh` の認証で作られるので、承認できるのはあなた以外のレビュアーです。

CI が1つも無い場合（`paths` フィルタで走らない、CI の無いリポジトリなど）は確かめるものが無いので止まりませんが、その旨は最後の PR の本文に残ります。PR を作った直後はチェックがまだ登録されていないことがあるため、最初の1分はチェックが現れるのを待ってから、CI が無いと判定します。一方、`gh` の応答に必須のフィールドが無い、型が違うなど、状態を取得できなかった場合は、CI なし・依頼なし・Ready として合格させず、エラーで止まります。最後の PR（conductor ブランチからデフォルトブランチへの PR）には `[pr] reviewers` がアサインされますが、ユーザーがレビューする PR なので、監督は待ちません。監督が最後の PR を作った直後に落ちて再実行された場合は、同じ向きで開いている PR が既にあれば、新しく作らずにその PR を案内します。

## 中断と再開

監督は状態を保存しません。次に何をするかは毎回 `hikyaku cycle status` と `hikyaku next` から導くので、監督のセッションが落ちても、同じコマンドで起動し直せば続きから進みます。止まっていた子の会話は引き継がれませんが、子は `step next` で `progress.jsonl` と成果物から続きの1手を導きます。

子が予算超過や利用上限で途中終了した場合、監督はユーザーに再開してよいかを尋ね、同じ子のセッションを再開します。呼び出し1回ごとの費用に上限を設けたいときは `budget_per_run` を使います（既定は 0 で上限なし）。

ビルドの G8 のあとで、完了時点の見込みが上限を超えるときは、子が実装に入る前にセッションの切り替えを記録して終えます（[コンテキストの区切り](build.md#コンテキストの区切り)）。監督はユーザーに上げずに、同じビルドを新しい子のセッションで起動し直し、新しい子は実装から続けます。

子には、非対話でどう止まるかを定めた規約が system prompt として渡ります。規約のうち、答えの記録やセッションの切り替えのように場面が限られる節は、その場面の起動にだけ入ります。子のセッションごとに読む量を抑えるためです。子はバックグラウンドの実行を無効にして起動されます（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`）。非対話の子はターンを終えると完了の通知を待てないので、レビューやサブエージェントは前景で完了まで待ちます。子が `gh` で PR を作れない環境では、子が PR の本文をファイルに書いて止まり、監督が代わりに PR を作ってから子を再開します。

## Draft PR の公開

子が先へ進めずに blocked で終えるときは、試したこと、問題を変える選択肢とそれぞれで失うもの、推奨を本文に書く決まりです。欠けていれば `conductor parse` は violation を返し、監督は欠けた節を添えて子を一度だけ再開します。2回目も欠けていればユーザーに上げます。判断の材料を欠いた報告で、ユーザーが選ばされることを防ぐためです。

子が作った PR は Draft のまま監督へ渡ります。監督は取り込む前に `hikyaku pr ready` で公開し、そのあと `check-pr` でレビュー・CI・マージ先を検証します。公開に失敗した場合は取り込みません。検証の途中で Draft に戻された場合も、公開し直さずユーザーに上げます。

監督の統合 PR と CLOSE の PR は、ユーザーがマージするため、[`[pr] auto_ready`](../configuration/config-file.md#pr) に従います。CLOSE が別のブランチで作る見積もりのガイドやフックの PR は、それぞれの手順に従い、監督は取り込みません。
