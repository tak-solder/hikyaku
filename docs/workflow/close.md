# CLOSE — サイクル終了

```
/hikyaku:close-cycle [{cycle}]
```

実装済みの成果を永続ドキュメントへ昇格させ、サイクルを締めます。

## なぜ独立したフェーズなのか

昇格は PR がマージされて初めて真になるので、実装が全部終わってから行います。最終ビルドに混ぜないのは、builder のコンテキストが実装だけに集中できなくなるためです。

一方で、全ビルド完了（`completed`）から昇格完了（`closed`）までの間には危険な空白があります。実装は main に入っているのに `overview` はまだ古い。この期間に他サイクルの architect が走ると、古い `overview` を現実として信じます。**だから CLOSE は速やかに実行してください。**

## 永続ドキュメントを書ける唯一のスキル

| スキル | 永続ドキュメント |
|---|---|
| planner | ✗ |
| architect | ADR の追記のみ |
| builder | ✗ |
| close-cycle | ✓（唯一） |

`{HIKYAKU_ROOT}/instructions.md` も同じ扱いで、書き換えるのは close-cycle だけです。永続ドキュメントではありませんが、走行中の他サイクルの planner / architect が読むため、フェーズ途中で書き換えると前提が途中で変わります。

## 進み方

### 振り返り

昇格より先に実行します。後に回すと、この回の振り返りで出た学びを昇格させる機会が永久に無くなります（次の close-cycle は別のサイクルを見るため）。`economy` では実行されません。

### 素材の収集

昇格候補の抽出はサブエージェントに委任されます。サイクルが長いとコンテキストが厳しくなるためです。素材は `design-delta.md`、`codebase-survey.md`、全ビルドの `handoff.md`、各フェーズの `retrospective.md` です。

`retrospective.md` から拾うのは「リポジトリ固有の学び（L-N）」と、対象が `doc:` の改善提案だけです。`workflow` 分類は本セッションが直接捌き、`記録のみ` は読みません。

### 昇格候補の整理

| 昇格先 | 何を昇格させるか | 主な素材 |
|---|---|---|
| `overview` | アーキテクチャに影響した変更。責務・境界・データフローの変化 | design-delta / handoff |
| `learnings` | 再現条件が明確な落とし穴 | handoff / retrospective の L-N |
| `constraints` | 実装中に判明した新たな制約（数値で書けるもの） | handoff |
| `conventions` ほか規約系 | 以後の書き方・進め方の取り決め | retrospective の `doc:` 分類 |
| `instructions.md` | このリポジトリで Hikyaku を回すときの手順・前提 | retrospective の `workflow` 分類 |
| ADR | `status: accepted` → `implemented` に更新 | design |
| document-guide | このサイクルで新規作成したドキュメントの行を更新 | — |

昇格先は `document-guide.md` が宣言する論理名だけです。そこに無い論理名へは昇格させません（勝手にドキュメントを作らないため）。「未作成」で登録されている論理名へ昇格させる場合は新規作成になるので、その旨も併せて承認を得ます。

同じ提案が複数フェーズの `retrospective.md` に出ていたら1件に束ねられ、出典は全部残ります。言われた回数は優先度そのものだからです。

### 昇格させないもの

`overview` にテーブル一覧・エンドポイント一覧・依存パッケージのバージョンは書きません。これらはコードが正で、書いた瞬間に腐り、しかも腐っていることに誰も気づけません。代わりに「正がどこにあるか」のポインタを書きます。

`learnings` には一般的なプログラミング知識や、「気をつける」だけの曖昧な注意を書きません。以後の取り決めも書きません（それは `conventions` か `instructions.md` です）。`learnings` は踏んだ地雷の記録であって、取り決めではありません。

`constraints` には実現方法を書きません（それは ADR か `overview` です）。`instructions.md` にはこのリポジトリに固有でないことを書きません（一般的な進め方は各スキルが持っています）。

`repo` 管理のドキュメントには形式を強制しません。既存形式に合わせて追記するだけで、既存記述の削除や整理はしません。

### 承認

昇格候補が昇格先ごとに提示されます。昇格させないと判断されたものも理由付きで並ぶので、拾い漏らしがあればここで戻せます。

```
overview に昇格:
  + 「請求」セクション: 請求は API → キュー → ワーカーの順で処理される
  + ポインタ追加: 請求スキーマの正は db/migrations/

learnings に昇格:
  + 請求バッチのテストは並列実行で落ちる（build-03 で判明、2026-09-01）

conventions（AGENTS.md）に昇格:
  + マイグレーションは1PR1ファイルに保つ（design#R-1, build-02#R-3 の2件）

instructions.md に反映:
  + 環境変数を足したら .env.example にも同じキーを足す（build-01#R-2）

ADR:
  ~ 20260825-payment-provider.md: accepted → implemented

昇格させないもの（参考）:
  - handoff にあった「invoices テーブルを追加」→ マイグレーションが正のため書かない
  - build-03#R-1「テストは1ファイル1クラス」→ conventions に既に同じ記述があるため書かない
```

**この承認はどのプロファイルでも省略されません。** 不可逆だからではなく、何を昇格させるかの取捨選択が人間の判断だからです。自動化すると精度が落ちます。

### 書き込みとクローズ

承認された内容が永続ドキュメントへ書き込まれ、新しいドキュメントを作った場合は `document-guide.md` と AGENTS.md の索引も更新されます。最後に `cycles.md` の status が `closed` になり、完了日が記録されます。

未完了のビルドを残したまま締めるのは、サイクルを中止する場合だけです。その場合は `abandoned` として記録されます。

サイクルディレクトリは残ります。PR 履歴から辿れることに価値があるためです。

## 終わり方

PR を作って完了です。次のサイクルは `/hikyaku:create-cycle` から始めます。
