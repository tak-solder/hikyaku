# CLOSE — サイクル終了

```
/hikyaku:close-cycle [{cycle}]
```

サイクルで得た知見を永続化し、サイクルを締めます。足すだけでなく、役に立たなかった記述や古くなった記述を消し、置き換えます。

## なぜ独立したフェーズなのか

昇格は PR がマージされて初めて真になるので、実装が全部終わってから行います。最終ビルドに混ぜないのは、builder のコンテキストが実装だけに集中できなくなるためです。

一方で、全ビルド完了（`completed`）から昇格完了（`closed`）までの間には危険な空白があります。実装は main に入っているのに `overview` はまだ古い。この期間に他サイクルの architect が走ると、古い `overview` を現実として信じます。**だから CLOSE は速やかに実行してください。**

## 誰が何を書くか

知見の置き場は読み込まれ方で選び、書く人は置き場で決まります（[知見の置き場](../configuration/persistence.md)）。コードとパス指定の rule は、見つけたビルドの builder がその PR で書きます。close-cycle が書くのは、永続ドキュメント、`{HIKYAKU_ROOT}/instructions.md`、スキルです。永続ドキュメントと `instructions.md` を書けるのは close-cycle だけで、例外は architect による ADR の追記です。走行中の他サイクルの planner や architect が読む文書なので、フェーズの途中で書き換えると前提が途中で変わります。

## 進み方

設定・ブランチ・全ビルドの完了の確認は、セッションを始めるたびに close-cycle が行います。その先の手順は `hikyaku step next` が1手ずつ決めます。進捗はサイクルのディレクトリ直下の `progress.jsonl` に1手ずつ追記され、変更と一緒にコミットされます。CLOSE の成果物はサイクルの外にあり、フェーズ専用のディレクトリを持たないため、記録はサイクル直下に置きます。

CLOSE 自身の振り返りは行いません。昇格の素材にするには昇格より先に行う必要があり、その時点では振り返る中身がまだ無いためです。

### 候補の収集

```bash
hikyaku promotions {cycle}
```

候補はスクリプトが集めます。各ビルドの `handoff.md` と各フェーズの `retrospective.md` は、同じ見出しと行の形で「永続化すること」を書くので、集めて宛先ごとに束ねるところまでは機械的にできます。`design-delta.md` の「永続ドキュメントの更新予定」と、振り返りの「役に立たなかった記述」も併せて返ります。書式が崩れていた行は捨てられず、読めなかった行として返ります。

候補はいつでも同じコマンドで再現できるので、承認の前にセッションが切れても、やり直しにはなりません。

### 整理

close-cycle は集まった候補を次の観点で整理します。

- 同じ知見が複数のビルドやフェーズから出ていたら1件に束ね、出どころを全部残す。挙がった回数は根拠になる
- マージ済みのコードと照合し、既に機械で防がれているものと、後のビルドで事実でなくなったものを落とす
- 重要度を見直し、低に当たるものを落とす
- 置き場が合っているかを確かめる。`conventions` に一部のファイルにしか効かない注意を入れない、`overview` にテーブル一覧を書かない、など
- 「役に立たなかった記述」を理由ごとに扱う（[消すこと](../configuration/persistence.md#消すこと)）
- このサイクルで実装された ADR を `accepted` から `implemented` にする。覆された判断は旧エントリを `superseded` にし、新エントリを起こす

昇格先は `document-guide.md` が宣言する論理名だけです。「対象外」の論理名へは昇格させず、「未作成」の論理名へ昇格させる場合は新規作成になるので、その旨も併せて承認を得ます。`repo` 管理のドキュメントには形式を強制せず、既存の形式に合わせて書きます。ADR の本文は書き換えません。

### 承認

置き場ごとに、追加（`+`）・置き換え（`~`）・削除（`-`）が分けて提示されます。採らなかったものも理由付きで並ぶので、拾い漏らしがあればここで戻せます。

```
overview:
  + 「請求」: 請求は API → キュー → ワーカーの順で処理される（design-delta / build-02）
  ~ 「通知」: 「同期で送る」→「キュー経由で送る」（build-04 で変更）

constraints:
  + [高] 請求 API は 1 分あたり 100 件まで（build-03）

conventions（AGENTS.md）:
  + [中] マイグレーションは 1 PR 1 ファイルに保つ（design・build-02 の振り返り、2件）
  - 「DTO の fixture は3ファイルを直す」: 自明（build-02・build-05 の振り返り、2件）

rules:
  ~ .claude/rules/backend.md「テレメトリ」を別ファイルに分ける（無関係 3件: build-01・02・05）

スキル:
  + release-db: 破壊的な移行の公開手順（build-02 と build-05 で同じ手順）

ADR:
  ~ 20260825-payment-provider.md: accepted → implemented

フック（別の PR にする）:
  + .env の編集を止める（build-01・build-03 で2回、誤って編集しかけた）

採らないもの（参考）:
  - 「invoices テーブルを追加」→ マイグレーションが正のため書かない
  - 「型検査の前に生成コマンドを実行する」→ このサイクルでスクリプトに組み込まれた
```

**この承認はどのプロファイルでも省略されません。** 何を残し、何を消すかの取捨選択が人間の判断だからです。

削除と置き換えを提案できるのは、このサイクルの記録に根拠があるものと、このサイクルのビルドが書いた rule に限ります。それ以外で気づいた点は、手を入れずに PR の本文に書き残されます。

### 書き込みとクローズ

承認された内容が書き込まれます。スキルが承認されていれば `.claude/skills/` に作られ、rule の整理が承認されていれば反映されて `hikyaku rules check` で確かめられます。新しいドキュメントを作った場合は `document-guide.md` と AGENTS.md の索引も更新されます。最後に `cycles.md` の status が `closed` になり、完了日が記録されます。

未完了のビルドを残したまま締めるのは、サイクルを中止する場合だけです。その場合は `abandoned` として記録されます。サイクルディレクトリは残ります。PR 履歴から辿れることに価値があるためです。

PR の本文には、追加・置き換え・削除が分けて書かれます。[conductor](conductor.md) の配下では承認を監督が行うので、人間が削除を確かめる場はこの PR になります。

### 別の PR になるもの

close の PR を作ったあと、次の2つは別のブランチの PR になります。close の PR に混ぜると採否を分けて判断できなくなるためで、どちらも採るかどうかはマージで決めます。承認は求められません。

見積もりのガイドの見直しは、そのサイクルで予測ピークが同じ向きに大きく外れたビルドが複数あったときに行われます。判定は `hikyaku tokens history {cycle}` が行い、該当すれば close-cycle が `/hikyaku:token-guide` を呼びます（[予測ピークと見積もりのガイド](../configuration/token-guide.md#誰がいつガイドを書き換えるか)）。未マージの token-guide の PR が残っているときは、ブランチが衝突するので見送られます。

フックの提案は、承認でフックにすると決まった知見があるときに作られます。フックは設定を誤ると、そのリポジトリで動く全セッションを止めます。そのため close-cycle は、スクリプトにサンプルの入力を与えて、止めるべき入力を止め、通すべき入力を通すことを確かめてから PR にし、確かめた結果を本文に載せます。

## 終わり方

PR を作って完了です。別の PR を作った場合はその URL も案内されます。次のサイクルは `/hikyaku:create-cycle` から始めます。
