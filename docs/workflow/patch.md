# patch — サイクルを作らない小さな変更

```
/hikyaku:patch 一覧の並び順を変更したい
/hikyaku:patch --cycle 002-billing この QA の FB をまとめて対応して
```

ビルドを完走したあとの QA では、バグ修正に加えて、軽い仕様変更や使い勝手の改善がフィードバックとして出てきます。これを1件ずつサイクルやビルドにすると、準備と成果物の手間が変更の大きさに見合いません。patch は、こうした小さな変更を、依頼のすり合わせから実装・検証・コードレビュー・PR の作成まで1つのセッションで進めます。QA に限らず、単独の小さな修正にも使えます。フィードバックが複数件あれば、まとめて1つの patch で受け取れます。

1セッションで進めるといっても、対話や確認を省くわけではありません。patch はまず現状を確かめ、項目ごとに期待する挙動と対応範囲をユーザーと合意してから作ります。

AI が自然文の依頼から勝手に patch を始めることはありません。使うときは明示的に起動します。

## 何を残すか

patch は `planning/` や `design/`、`build-{NN}/` のような作業管理の文書を作りません。今回の依頼・合意した挙動・検証結果は PR の本文に集めます。合意を取った直後に Draft PR を作って本文に書くので、セッションが途中で落ちても合意は失われません。検証結果とドキュメントの更新は、公開の直前に本文へ足します。

リポジトリに残るのは、手順の記録（`progress.jsonl`）だけです。置き場は `patches/{YYYYMM}/{slug}/` で、サイクルに属さない patch は `{HIKYAKU_ROOT}` の下に、進行中のサイクルに属す patch はそのサイクルのディレクトリの下に置きます。ブランチ名は `hikyaku/patch/{YYYYMM}/{slug}` で、ブランチ名から記録の場所が一意に決まります。年月を名前に含めるのは、別の月に同じ slug を使っても区別できるようにするためです。

サイクルに属さない patch の記録は、マージのたびに `{HIKYAKU_ROOT}/patches/` に増えていきます。記録は手順の現在地を導くためのもので、PR がマージされたあとは使いません。ときどき古い月をまとめて消してください。

```bash
hikyaku patch prune --before 202605 --dry-run
```

消すのは、指定した月より前で、PR を作った記録があるもの（と、通常のサイクルへすべて引き継いだもの）です。デフォルトブランチにある記録は PR がマージされた patch のものだけなので、公開の記録を push する前にマージされた patch でも消せます。いま居るブランチの patch は消しません。消したあとのコミットと PR は自分で行います。

今後の開発で参照する仕様・制約・設計判断・落とし穴は、必要なときだけ永続ドキュメントに反映します。毎回新しい文書を作ることはなく、変更の影響が無い文書も更新しません。

## サイクルに属すかどうか

patch がサイクルに属すかは推測されません。`--cycle` を渡したときだけ、そのサイクル（進行中のものに限る）に属します。属すかどうかで、PR の向き先と永続ドキュメントの扱いが変わります。

| 場面 | サイクル | PR の向き先 | 永続ドキュメント |
|---|---|---|---|
| 単独の小さな変更、閉じたサイクルの後の QA | 属さない | `base_branch` | この PR で直す（承認あり） |
| 統合 PR のマージ前の QA | 属す | 統合ブランチ（未マージの conductor ブランチ、またはサイクルの `base_branch`） | 書かない。`handoff.md` に残す |
| 全ビルドのマージ後・CLOSE 前の QA | 属す | `base_branch` | 書かない。`handoff.md` に残す |

サイクルに属さない patch は、コードと永続ドキュメントの更新を同じ PR に入れます。マージした時点で両方が揃うので、未実装のものが実装済みの現実として読まれることがありません。何を足し・置き換え・消すかは、提示された候補をユーザーが承認してから書きます。置き換えや削除を提案できるのは、この変更で事実でなくなった記述だけです。閉じたサイクルを再開したり、新しいサイクルを作ったりする必要はありません。

サイクルに属す patch は、永続ドキュメントを書きません。統合ブランチはまだデフォルトブランチに入っておらず、そのサイクルの close-cycle が後で同じ文書を書くためです。残すものは `patches/{YYYYMM}/{slug}/handoff.md` の「永続化すること」に書き、close-cycle がビルドの申し送りと同じく昇格させます。patch の変更がサイクルの `design-delta.md` の予定と食い違う場合は、変更の結果のほうを候補として書きます。サイクルの `user-stories.md` や `design-delta.md` は書き換えず、合意の記録として残します。

統合ブランチ宛ての patch を始めるとき、作業ツリーの `tasklist.md` に PR 列が空のビルドが残っていれば、patch はそれを伝えて、進めるかを確かめます。残りのビルドで扱うべき内容なら、builder で進めるほうが筋がよいためです。

## 手順

ブランチを決めたあとの手順は、ほかのフェーズと同じく `step next` が1手ずつ返します。

| ステップ | すること |
|---|---|
| start | 記録を始め、ブランチを push する |
| survey | 依頼を項目（P-1, P-2, …）に分け、項目ごとに現状を確かめる。コードはまだ変えない |
| scope | 項目ごとに、現状・期待する挙動・対応範囲・検証方法と、マージ時点のデータ安全を書く。予測ピークを見積もる |
| fit | patch で進めるかを判定する（下記） |
| P1 | 対応方針の合意。どのプロファイルでも省かない |
| pr | Draft PR を作り、依頼と合意を本文に書く |
| implement / verify | 合意した範囲を実装し、リポジトリの規約どおりに検証する |
| review | コードレビュー（code は常に、security は設定に従う）。合意の範囲を外れた変更がないかも確かめる |
| persist | 残す知見と、事実でなくなった記述を仕分ける。無ければスキップ |
| P2 / write | サイクルに属さない patch で、永続ドキュメントに残すものがあるときだけ。承認を得てから書く |
| publish | PR の本文に検証結果とドキュメントの更新を足し、Ready にしてレビュアーを依頼する |

実装中に依頼が広がったり、レビューで方針が変わったりしたら、scope から報告し直して P1 の合意を取り直します。

## patch で進めない変更

patch で扱えるかは、バグ修正か仕様変更かといった種類では決めません。fit で次の観点を見て、どれかに当たる項目があればユーザーに尋ねます。

| 観点 | 当たるとき |
|---|---|
| 1セッションに収まるか | 予測ピークが `[context] split_above` を超える |
| データの形 | スキーマ・マイグレーション・保存形式・公開 API の契約を変える |
| 設計判断 | ADR に残すべきトレードオフがある |
| 要件 | 新しいユーザーストーリーが要る、または期待する挙動のすり合わせが収束しない |
| 検証できるか | テストでも手元の確認でも、変更後の挙動を確かめられない |

選べるのは、それでも patch で進める・当たった項目だけ通常のサイクルへ引き継ぐ・すべて引き継ぐ、の3つです。予測ピークの比較は CLI が行い、それ以外の観点は AI が根拠とともに示します。

引き継ぐときは、patch が create-cycle を呼んで新しいサイクルを作り、調べたことと合意したことを `planning/intake.md` に書きます。planner はこれをチケットと同じく企画の入力として読みます。すべて引き継いだ patch はそこで止まり、そのブランチは PR にしません。

patch はマージした時点で本番データを壊さない形でしか作りません。安全でない分割の緩和（[`[data_integrity]`](../configuration/config-file.md#data_integrity)）は patch には適用されません。

## 承認とレビュー

patch の承認は P1（対応方針の合意）と P2（永続ドキュメントの更新の承認）の2つで、どちらもプロファイルの管轄外です。コードレビューの回数や security の扱いは、サイクルに属すならそのサイクルの、属さなければルートの `.hikyaku.config` の設定に従います。PR を作ったあとのレビュアーのアサインは、`[pr] reviewers_skip` に `patch` を書けばオフにできます。
