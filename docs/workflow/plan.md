# PLAN — 企画

```
/hikyaku:planner [{cycle}]
```

チケットと既存の企画メモを読み込み、そのサイクルのユーザーストーリーとして構造化します。決めるのは「何を作るか」だけで、実現方法は設計フェーズの担当です。

未初期化なら `/hikyaku:init` を、サイクルが未作成なら `/hikyaku:create-cycle` を planner が代行します。代行した create-cycle の成果物は `cycles.md` の1行だけなので、PLAN の PR に畳まれます。

## 進み方

最初にインプットを渡します。企画書、仕様メモ、Issue、Slack の抜粋など、場所を指定してください。指定が無ければ聞かれます。planner が自分でリポジトリを探索することはありません。

次に、読み取った内容が4項目（何を実現したいか / 背景・目的 / 対象画面・対象データ / 制約・要件）に要約されて提示されます。インプットから読み取れず補完した箇所には「（推測）」が付きます。**ここで認識のズレを潰してください。** この後の質問ラウンドは、ここで合意した内容を前提に組み立てられます。

質問は1回にまとめて来ます。目的・対象ユーザー・コア機能・スコープ境界・優先度・制約条件のうち、インプットから読み取れなかったものだけが聞かれます。質問が発生した場合は `planning/questions.md` に記録されます。

## 承認

`user-stories.md` が提示され、承認を求められます（G1）。**このゲートはどのプロファイルでも省略されません。** user-stories が「何を作るか」の唯一の合意点で、後段の承認では代替できないためです。設計も plan も「その要件で正しいか」を前提に置いています。

`standard` / `express` / `thorough` では、承認の前に doc-reviewer が整合性と網羅漏れを見ます。`economy` では起動しません。

## 読むもの

企画では永続ドキュメントをほとんど読みません。実装済みの現実を前提に置く場面ではないためです。読むのは `constraints`（確定済みの非機能要件を再度質問しないため）と `glossary`（語を既存の定義に揃えるため）だけです。

## 成果物

```
cycles/{NNN}-{slug}/planning/
├── questions.md      質問が発生した場合のみ
├── user-stories.md
└── retrospective.md  振り返りを実施した場合
```

このサイクルのスコープに閉じたものだけを書きます。将来やりたいことは書きません（バックログ管理は Hikyaku のスコープ外です）。

## 終わり方

外部連携が有効なら、ここで親 issue が作られます。user-stories があって親の要約として成立し、以降のすべての PR が親を参照できるようになるタイミングだからです。

PR はドキュメントのみです。**速やかにマージしてください。** デフォルトブランチに入っていない情報は、次の設計フェーズからも他のサイクルからも見えません。

次は新しいセッションで [ARCHITECT](architect.md) に進みます。
