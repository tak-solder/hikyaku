# 概念と設計思想

Hikyaku の振る舞いは5つの判断から導かれています。ドキュメントを as-is と to-be に分けること、コピーではなくポインタを持つこと、状態を保存せず導出すること、承認から「確認」だけを省けるようにすること、フェーズごとにセッションを分けること。個々の仕様に疑問を持ったときは、たいていこのいずれかが理由です。

## 用語

| 用語 | 意味 |
|------|------|
| サイクル | PLAN → ARCHITECT → BUILD → CLOSE の1周。1サイクル = 1チケットを想定。`cycles/{NNN}-{slug}/` に対応する |
| フェーズ | サイクル内の4段階（PLAN / ARCHITECT / BUILD / CLOSE） |
| セッション | 1つのAI実行単位（20万トークン目安）。1フェーズまたは1ビルドにつき1セッション |
| ビルド | 1セッションで完結する実装作業の単位。`build-{NN}/` ディレクトリに対応する |
| buildID | ビルドの識別番号。tasklist.md の行と `build-{NN}/` ディレクトリに対応する |
| ステップ | フェーズ内の手順（Step 1〜）。plan.md 内の実装手順もステップと呼ぶ |
| 永続ドキュメント | 実装済みの現実（as-is）を表す。所在は `document-guide.md` が宣言する |
| サイクルドキュメント | これから作るもの（to-be）と作業記録。`cycles/{NNN}-{slug}/` 配下 |
| BP（ビルドポイント） | 1セッションで実装が完了するかを判断する定量指標。詳細は [BUILD](workflow/build.md#ビルドポイントbp) |
| プロファイル | 承認とレビューの量を決めるサイクルの属性。詳細は [プロファイル](configuration/profiles.md) |

## 永続ドキュメントとサイクルドキュメントを分ける

永続ドキュメントは「実装済みの現実（as-is）」だけを書きます。これから作るものは、そのサイクルの `design-delta.md` に書きます。

この区別があるから、並行して走る別のサイクルが、まだ動いていない設計を現実として読む事故が防げます。逆に言えば、区別を守れる仕組みが要ります。Hikyaku では永続ドキュメントを書けるスキルを close-cycle に限定することでそれを担保しています。planner も builder も永続ドキュメントを読むだけで、書き換えません。実装中に判明した制約や、覆した設計判断は `handoff.md` に記録し、close-cycle が昇格させます。

例外は ADR ひとつだけです。決定した時点で記録するのが ADR 本来の思想なので、architect が `status: accepted`（決定済み・未実装）で追記します。`implemented` への更新は close-cycle が行うため、並行サイクルはこの status を見て「決まっているが、まだ動いていない」と判別できます。

全ビルドが完了してから close-cycle が終わるまでの間には、実装は main に入っているのに `overview` はまだ古い、という危険な空白が生まれます。この期間に他サイクルの architect が走ると古い現実を信じてしまうため、CLOSE は速やかに実行してください。`create-cycle` は放置されたサイクルを検出して警告します。

## コピーではなくポインタを持つ

永続ドキュメントに何を書くかは、復元コストと陳腐化速度の比で決めます。

| | 復元コスト | 陳腐化速度 | 判定 |
|---|---|---|---|
| DBスキーマの全テーブル定義 | 低（マイグレーションを読めばよい） | 速い | 書かない |
| 責務・境界・データフロー | 極めて高い（全ファイルを読んで推論） | 遅い | 書く |

`overview` に「主要テーブル: users, orders」と書くと腐ります。しかも腐っていることに誰も気づけません。「スキーマの正は `db/migrations/`」というポインタなら腐らず、パスが消えれば `hikyaku validate` が検出できます。陳腐化を機械が検出できるかどうかが、コピーとポインタの決定的な違いです。

この基準から、`tech-stack` / `db-schema` / `interfaces` を Hikyaku が作ることはありません。リポジトリにあれば俯瞰の手がかりとして読みますが、コードと矛盾したら常にコードを正とします。

## 状態は保存せず導出する

保存する状態は `cycles.md` の `status`（`active` / `closed` / `abandoned`）だけです。これはサイクルの生涯で2回しか変わりません。それ以外はすべてファイル・ブランチ・PR 列から導出します。

| 知りたいこと | 導出方法 |
|---|---|
| フェーズ（planning / architecting / building / completed） | ファイルの存在 |
| ビルドが着手中か | ブランチの存在（`git ls-remote`） |
| ビルドが完了したか | `tasklist.md` の `PR` 列が非空 |
| どこで中断したか | ブランチ上の成果物の有無 |

重複した状態は必ず腐り、しかも腐っていることに気づけないためです。ビルドに `status` 列を持たせないのも同じ理由で、持たせると「status は done だが PR 列は空」という嘘の状態を作れてしまいます。

完了判定が `PR` 列で成立するのは、`PR` 列の更新を当該ビルドの PR に同梱するルールがあるからです。デフォルトブランチ上で `PR` 列が埋まっていること自体が「マージ済み = 完了」を意味します。

例外が1つだけあります。「自分が最後に触ったサイクル」はリポジトリから導出できません。チーム開発では、最後にコミットされたサイクルが他メンバーのものであることが普通だからです。これだけは `{HIKYAKU_ROOT}/.hikyaku.local`（git 管理対象外）に記録します。読むのは対象サイクルを決めるときだけで、`next` や `validate` のような判断からは参照しません。指す先が無効なら黙って捨てて尋ね直すので、消えても支障はありません。

## 承認ゲートは「確認」と「同意」を分ける

プロファイルで省略できるのは原則として確認だけです。人間にしか下せない判断は、どのプロファイルでも省略しません。

要件の合意（planner の G1）は、user-stories が「何を作るか」の唯一の合意点で、後段の承認では代替できません。設計も plan も「その要件で正しいか」を前提に置いているからです。永続ドキュメント昇格の承認（close-cycle の G10）は、何を昇格させるかの取捨選択そのもので、自動化すると精度が落ちます。

設計案の選択（architect の G3）も本来は同じ性質ですが、express だけは外せます。要件を人間が握っている以上、その先のトレードオフは推奨に委ねても引き返せるという判断です。省いた場合も採用理由と退けた案は ADR と PR 本文に残ります。

コードレビューだけはどのプロファイルでも実行します。中間成果物のレビューは人間の承認で代替できますが、コードは差分が大きく、人間の承認ゲートが拾える粒度を超えるためです。

## セッションを分ける

各フェーズは別のセッション（別の AI）が担当し、情報はファイルで引き継ぎます。1セッション20万トークンが目安で、実装は1ビルド = 1セッションに収まる大きさに分割します。この分割の判断に使う定量指標が BP です。

コンテキストを分ける意味は、単に容量に収まることだけではありません。builder のコンテキストが実装だけに集中できるのは、永続ドキュメントの昇格を CLOSE が引き受けているからです。同様に、既存コードの探索や昇格候補の抽出はサブエージェントに委任し、本セッションには結論だけを返させます。
