# 概念と設計思想

Hikyaku はワークフローそのものを目的にしていません。良いシステム開発のための手段です。ここで言う良いシステム開発とは、**合意したものを作り、そのうえで次の変更も確かに行える状態を保つこと**です。AI エージェントと開発すると、この2つを脅かす条件が変わります。このページでは、Hikyaku が置いている前提と、そこから導いた責任の分け方、その分け方を支える仕組みを順に説明します。個々の仕様に疑問を持ったときは、たいていこのどこかに理由があります。

## AI と開発するときの前提

1つ目の前提は、作り手が毎回記憶の無い状態から始まることです。システムについての理解には、コードを読めば分かる部分と、分からない部分（責務の境界、なぜそうしたのか、何を退けたのか）があります。チームでは後者がメンバーの頭の中に残りますが、AI のセッションは前のセッションの理解を持ち越せず、1回に読める量にも上限があります。理解は、セッションが変わるたびに失われます。

2つ目は、ユーザーの時間がいちばん乏しい資源になることです。AI は速く、大量に作れますが、作られたものをユーザーが判断するには時間がかかります。AI の速さに合わせてユーザーがすべてを確かめようとすれば、先にユーザーの時間が足りなくなります。

3つ目は、AI が決まった手順を守ることや数えることを、確実にはこなせないことです。指示文で念を押しても外れることがあり、しかも外れたことに気づけない形で外れます。

4つ目は、AI が結果を引き受けられないことです。セッションが終われば何も覚えておらず、結果の責任を問われることもありません。どれだけ AI に任せても、結果の責任はユーザーに残ります。

この前提のもとで、Hikyaku は次の3つを達成しようとしています。

- 決めたことや分かったことを、セッションが変わっても失わない（[引き継ぎを会話の外に出す](#引き継ぎを会話の外に出す)）
- 書いたものが現実からずれたときに、気づけて、直せる（[ずれに気づけて、直せるようにする](#ずれに気づけて直せるようにする)）
- ユーザーの時間を、ユーザーにしか下せない判断に使う（[委ねる範囲を決める](#委ねる範囲を決める)）

## 責任の分け方

AI とユーザーの役割は、能力ではなく責任で分けます。AI にできることはモデルが変わるたびに広がり、能力で引いた線はそのたびに動きます。一方で、結果を引き受けるのがユーザーであることは、モデルがどれだけ賢くなっても変わりません。手段の設計は、変わらないほうの線を軸にします。

| 担い手 | 責務 |
|---|---|
| ユーザー | 何を、なぜ作るかを決める。リポジトリの外の前提を持つ。リスクを引き受ける。システムの境界を理解している。作り方を設計し、縮める。問題そのものを変える |
| LLM | 判断と生成。設計案・コード・テスト・文書を作り、合意の範囲の中で選ぶ。ユーザーの選択が宣言や記録と食い違えば、異を唱える |
| スクリプト | 手順の並び、実行の条件、完了の判定、数値の比較、形式の検査 |

スクリプトと LLM の線は、決定的に決められることをスクリプトに、取捨選択や文面の作成を LLM に、という分け方です。数えることや手順の順番を指示文で LLM に任せると、外れたときに気づけません。逆に、何が重複しているか、何を残すべきかといった判断をスクリプトに持たせると、機械的な規則が文脈を取りこぼします。

### ユーザーは境界を理解していればよい

ユーザーに、AI が作れないものを自分で作れるほどの理解は求めません。重い領域ほど、それは現実的ではないからです。コードを読めることは責務ではなく、作業を進めるための前提で、全文を読む必要もありません。

ユーザーが理解しているべきなのは、システムの**境界**と、その境界を決めた理由です。境界の内側の実装は、テストが守っていればいつでも書き直せるので、AI の領分です。境界は使う側が依存するので戻しにくく、意図・外の前提・受け入れたリスクが書き込まれる場所でもあります。公開する API、画面の振る舞い、保存するデータの形、外部連携といった外との境界は、ユーザーが同意します。モジュールの分け方や依存の向きといった内部の境界は、戻せますがシステムの成り立ちを変えるので、変わったことをユーザーが確かめます。

ユーザーが AI の説明を確かめるときも、AI が書いた説明を読むだけでは堂々巡りになります。確かめる手段は、境界での振る舞いです。型や契約を読み、テストを動かせば、AI の説明を介さずに実物で確かめられます。

### LLM は黙って従わず、異を唱える

ユーザーが決めた方針は、スクリプトも LLM も黙って切り替えません。ただし、黙って従うのも誤りです。ユーザーの選択が、その人自身の宣言（アプリケーションの状況や制約）、記録（見積もりや差し戻しの履歴）、前提と食い違うとき、LLM は根拠と失うものを示して異を唱えます。好みの違いには異を唱えません。

決めるのはユーザーで、異議と決定はどちらも記録に残します。異議の強さは害の重さに合わせます。重さが中程度なら指摘するだけで、ユーザーがそのまま進めればそれで決まります。害が成果物に残るほど重いものは、ユーザーが「何を受け入れるか」を自分の言葉で書くまで先に進みません。拒否ではなく、失うものを承知で選んだことを記録に残すための手順です。

### AI が変えてよいのは解き方だけ

AI が行き詰まったとき、ユーザーが代わりに解くことは期待できません。ユーザーにできるのは、問題のほうを変えることです。スコープを削る、要件を緩める、前提を変える、やめる。どれも意図か外の前提を変える判断なので、ユーザーの責務です。

そのため、AI は解き方を変えてよくても、問題を変えてはいけません。通らないテストを消す、期待値を緩める、受け入れ基準の一部を黙って実現しない、といった変更は、問題を黙って書き換えることです。こうした変更はスクリプトが差分から事実として並べ、作った本人ではない別のレビューが、合意（issue.md・テストシナリオ）と突き合わせて判断します。行き詰まってユーザーに上げるときは、試したこと、問題を変える選択肢とそれぞれで失うもの、推奨を示します。ユーザーは解き方ではなく、どの問題に変えるかを選びます。

## 引き継ぎを会話の外に出す

1つの長いセッションで開発を進めると、決めたことや前提は会話の中にしか残りません。自動コンパクションが起きれば、モデルが書いた要約に置き換わり、何が落ちたかはユーザーにも次のターンのモデルにも分かりません。問題はコンパクションが起きることそのものではなく、引き継ぎの中身を誰も選べず、誰も確かめられないことです。

Hikyaku は、引き継ぎを `design-delta.md`・`issue.md`・`handoff.md` のようなファイルに出します。何を残すかは書く側が選び、PR でユーザーが読め、別のセッションや別の人が同じものを読んで始められます。

### 境界は、合意・読む範囲・現実かどうかが変わるところに置く

各フェーズは別のセッションが担当します。PLAN → ARCHITECT → BUILD → CLOSE という4つの区切りは、数そのものに必然性があるわけではありません。区切りは、合意の種類、読む範囲、書くものが現実かどうか、のどれかが変わるところに置かれています。

PLAN と ARCHITECT を分けるのは、何を作るかの合意を、どう作るかから独立させるためです。要件と設計を同じセッションで作ると、要件が作りやすい設計に引き寄せられ、ユーザーも2つを分けて見られません。user-stories が設計より先に固まっているから、受け入れ基準の追跡やレビューで「合意どおりか」を確かめられます。読むものも違い、planner はユーザーとの対話が中心で、architect はコードと永続ドキュメントを全文読みます。

ARCHITECT と BUILD を分けるのは、全体を見る判断と、1か所を作る作業を分けるためです。ビルドの切り方、依存の順、ビルド同士の取り決めはビルドより上から見なければ決められず、ビルドの中で決めるとビルドごとに設計が食い違います。全文を読む設計と実装は、コンテキストの面でも1つのセッションに収まりません。実装は1ビルドが1セッションに収まる大きさに分け、その判断には予測ピーク（メインセッションのコンテキストがどこまで膨らむかの予測）を使います。予測は見積もりのガイドに沿って立て、振り返りで実測と突き合わせ、ずれが大きければガイドを補正します。

BUILD と CLOSE を分けるのは、実装済みの現実（as-is）を、実装が揃ってから書くためです。ビルドが1つずつマージされている途中で書けば、半分だけ実装された状態が現実として読まれます。

境界には、引き継ぎのファイルを書いて読む手間がかかります。変更が小さければ、その手間が得られるものを上回ります。サイクルに属さない [patch](workflow/patch.md) は、この場合の形です。依頼のすり合わせから PR までを1セッションで進め、永続ドキュメントもコードと同じ PR で直します。それでも対応方針の合意（P1）は必ず取り、as-is を書くのはマージと同時に現実になるときだけです。境界は減っても、境界が守っていた条件は手放していません。フェーズの数は変更の大きさで決まり、守るべきものは2つの条件で決まります。

### 読む量を絞る

`overview` / `decisions` / `constraints` の全文を読むのは architect だけです。builder には `issue.md` を通じて、そのビルドに効く節へのポインタだけを渡します。本文を写さずポインタで渡すのは、設計から実装までのあいだに永続ドキュメントが変わっても、builder が読む時点の記述を読めるようにするためです。architect の選び漏れは、plan をレビューするサブエージェントが全文と突き合わせて拾います。既存コードの探索もサブエージェントに任せ、メインのセッションには結論だけを返させます。

### 知見の置き場は読み込まれ方で選ぶ

実装で得た知見は、どの文書に書くかではなく、いつ読み込まれる場所に置くかで決めます。読まれる頻度が、その知見が使われる頻度を上回る場所には載せません。落とし穴を1つの文書に溜めていくと、たまにしか使わない知見のために毎セッションのコンテキストを使い、置き場を持たなければ同じ落とし穴を次のビルドがもう一度踏みます。

そこで、まず重要度で残すものを絞ります。害が成果物に残るもの（テストが通ってしまう、本番でだけ壊れる）は必ず残し、セッションの時間を失うだけのものは安く置けるときだけ残し、すぐ直せるものは書きません。残すものには、読むコストが小さい順に置き場を当てはめます。最初に考えるのは、知見そのものを要らなくすることです。いまのコードの形が原因で生まれている条件（呼び出しの順の縛り、循環を避けるための制限など）は、リファクタで消せます。消せなければ機械で防ぎ（テスト・型・lint・共通ヘルパー）、一部のファイルを触るときだけ効くならパス指定の rule に、決まった手順ならスキルに置きます。常時読み込まれる `conventions` に入れるのは、リポジトリのどこを触るセッションでも、知らないと一貫性を壊す取り決めだけです。

この順は、最初に置く場所の規則であるだけでなく、知見が時間とともにたどる道筋でもあります。書かれた基準は、機械の検査へ移り、やがてリファクタで要らなくなるのが健全です。同じ rule がレビューで何度も引かれる、どのファイルにも一致しなくなった、といった移すきっかけは、スクリプトが記録から見つけます。

知見の寿命は、領域がどれだけ頻繁に変わるかでも違います。頻繁に変わる領域では、知見はすぐ使われ、すぐ古くなるので、早めに機械の検査へ移します。何年も触らない領域では、知見はめったに使われませんが、使われるときには誰も覚えていません。触るときだけ読まれるパス指定の rule やその場のコメントが向いています。長く触られていなかったこと自体が、外の前提が変わったかもしれないという信号なので、そうした領域に変更が入ったら、まず結び付いた前提と基準を見直します。

コードと rule は、見つけたビルドの builder がその PR で書きます。落とし穴の再発は同じ領域を続けて触るビルドのあいだで最も起きるので、サイクルの終わりを待つと間に合いません。それ以外は close-cycle が、複数のビルドの知見を束ねて判断します。基準と置き場の一覧は [知見の置き場](configuration/persistence.md) にあります。

## ずれに気づけて、直せるようにする

文書や状態が実装からずれることは、ゼロにはできません。Hikyaku が目指すのは、ずれが気づけない形で起きないようにすることと、気づいたら直す経路を持つことです。

### 永続ドキュメントとサイクルドキュメントを分ける

永続ドキュメントは実装済みの現実（as-is）だけを書きます。これから作るものは、そのサイクルの `design-delta.md` に書きます。ずれの中でいちばん害が大きいのは、まだ作っていないものを、もうあるものとして読むことです。この区別があるから、並行して走る別のサイクルが、まだ動いていない設計を現実として読む事故を防げます。

区別を守るために、永続ドキュメントを書けるスキルは close-cycle に限っています。planner も builder も永続ドキュメントを読むだけです。実装中に分かった制約や覆した判断は `handoff.md` に記録し、close-cycle が昇格させます。

例外は2つあります。1つは ADR です。決定した時点で記録するのが ADR 本来の考え方なので、architect が `status: accepted`（決定済み・未実装）で追記し、`implemented` への更新は close-cycle が行います。並行サイクルは、この status を見て「決まっているが、まだ動いていない」と判別できます。もう1つは、サイクルに属さない patch です。コードと永続ドキュメントの更新を同じ PR に入れれば、マージした瞬間に両方が揃って現実になるので、未実装の設計が現実として読まれる時間がそもそも生まれません。逆に、進行中のサイクルに属す patch は永続ドキュメントを書かず、残すものを `handoff.md` に書いて close-cycle に任せます。そのサイクルの close-cycle が同じ文書を後から書くので、二重の更新や食い違いが起きるためです。

全ビルドが完了してから close-cycle が終わるまでのあいだには、実装はデフォルトブランチに入っているのに `overview` はまだ古い、という空白が生まれます。この期間に他サイクルの architect が走ると古い現実を信じてしまうため、CLOSE は速やかに実行してください。`create-cycle` は放置されたサイクルを検出して警告します。

### 永続ドキュメントには、前提・判断・基準を分けて書く

永続ドキュメントを主に読むのは、チームメンバーではなく次の AI セッションです。記憶を持ち越せない AI にとっての長期記憶の代わりなので、品質の基準は「次の AI が良い判断を下せたか」になります。

中身は性質で分けて書きます。性質によって、正しさの決まり方も、古くなり方も、持ち主も違うからです。

| 種類 | 例 | どう古くなるか | 持ち主 |
|---|---|---|---|
| 外の前提 | 外部サービスの上限、利用者の範囲、契約、法令 | 世界が変わり、黙って偽になる | ユーザー |
| 内の前提 | どこに何があるか（`overview`） | コードが変わり、偽になる | AI（コードと照合できる） |
| 判断 | ADR の決定 | 前提が変わり、見直しが要る | 前提・リスクから導かれる |
| 受け入れたリスク | 承知のうえで受ける欠点 | 拠り所の前提が変わり、受け入れてはいけないものになる | ユーザー |
| 基準 | 書き方の取り決め、守る規則 | 使われなくなる | AI が運用し、ユーザーが消す |

いちばん危ないのは、外の前提が黙って偽になることです。AI は正しく推論したうえで誤った結論を出し、誤っているのは推論ではなく前提なので、レビューでも見つかりにくくなります。しかも、外の前提が変わったことはリポジトリの中からは見えません。だから外の前提は、確かめた事実か仮定かを分け、確かめた日を添えて書きます。外の前提は、AI がどれだけコードを読んでも手に入らない情報なので、永続ドキュメントに書く価値も高いものです。

判断には、立っている前提と、推奨と、受け入れたことを書きます。ユーザーが推奨を退けたときは、何を優先したかだけでなく、推奨案の利点のうち何を失うかを書きます。好みで決めたように見える判断の多くは、実際にはユーザーがリスクを引き受けた判断なので、「選好」ではなく受け入れたこととして書きます。どの前提が変わったら見直すかも添えておけば、前提が偽になったときに、それに立つ判断を辿れます。

### コピーではなくポインタを持つ

永続ドキュメントに何を書くかは、復元コストと陳腐化速度の比で決めます。

| | 復元コスト | 陳腐化速度 | 判定 |
|---|---|---|---|
| DBスキーマの全テーブル定義 | 低（マイグレーションを読めばよい） | 速い | 書かない |
| 責務・境界・データフロー | 極めて高い（全ファイルを読んで推論） | 遅い | 書く |

`overview` に「主要テーブル: users, orders」と書くと腐ります。しかも腐っていることに誰も気づけません。「スキーマの正は `db/migrations/`」というポインタなら腐らず、パスが消えれば `hikyaku validate` が検出できます。陳腐化を機械が検出できるかどうかが、コピーとポインタの決定的な違いです。ポインタに件数や範囲を添えるのも同じ理由で避けます。「AD-1〜AD-5」と書いた時点で、それはポインタではなくコピーになります。

この基準から、技術スタック・DB スキーマ・API の一覧は永続ドキュメントとして持ちません。正はコード側にあり、`overview` から所在をポインタで指せば足ります。永続ドキュメントとコードが矛盾したら、常にコードを正とします。

### 状態は保存せず導出する

保存する状態は `cycles.md` の `status`（`active` / `closed` / `abandoned`）だけです。これはサイクルの生涯で2回しか変わりません。それ以外はすべてファイル・ブランチ・PR 列・記録から導出します。

| 知りたいこと | 導出方法 |
|---|---|
| フェーズ（planning / architecting / building / completed） | ファイルの存在 |
| ビルドが着手中か | ブランチの存在（`git ls-remote`） |
| ビルドに着手できるか | **`HEAD` の** `tasklist.md` で、依存ビルドの `PR` 列が非空 |
| サイクルが完了したか | **デフォルトブランチの** `tasklist.md` で、全ビルドの `PR` 列が非空 |
| どのビルドで中断したか | ブランチ上の成果物の有無 |
| フェーズの中のどの手順で中断したか | 作業単位の `progress.jsonl` の記録 |
| 差し戻し中か | `return.md` の有無 |

重複した状態は必ず腐り、しかも腐っていることに気づけないためです。ビルドに `status` 列を持たせないのも同じ理由で、持たせると「status は done だが PR 列は空」という嘘の状態を作れてしまいます。

`PR` 列でこれが成立するのは、`PR` 列の更新を当該ビルドの PR に同梱するルールがあるからです。デフォルトブランチ上で `PR` 列が埋まっていること自体が「マージ済み」を意味します。

着手できるかと、サイクルが完了したかは、別の問いです。前者が問うているのは「依存ビルドの成果が、いま居るブランチの履歴に在るか」であって、マージされたかどうかではありません。マージは成果が履歴に入る経路の1つで、先行ビルドのブランチから積む（スタックする）のがもう1つです。`HEAD` で `PR` 列が非空であることが、そのまま「その実装が自分の履歴に在る」ことを意味するので、どちらの経路でも同じ判定で足ります。

一方、サイクルが完了したかはリポジトリ全体の問いなので、デフォルトブランチを見ます。ここを手元の断面で代用すると、最後のビルドで `PR` 列を埋めた直後に「完了」と出てしまいます。デフォルトブランチを読めないときは「完了」とは言いません。close-cycle は永続ドキュメントへの昇格なので、誤って勧めるほうが害が大きいためです。中断点の特定は逆にツリーローカルの問いなので、`HEAD` を見ます。ここをデフォルトブランチ基準にすると、マージ待ちで完了済みの先行ビルドが「未完了」に混ざり、スタック中に中断点が古いビルドへ戻ります。

例外が1つだけあります。「自分が最後に触ったサイクル」はリポジトリから導出できません。チーム開発では、最後にコミットされたサイクルが他メンバーのものであることが普通だからです。これだけは `{HIKYAKU_ROOT}/.hikyaku.local`（git 管理対象外）に記録します。読むのは対象サイクルを決めるときだけで、`next` や `validate` のような判断からは参照しません。指す先が無効なら黙って捨てて尋ね直すので、消えても支障はありません。

### 基準は少なく保ち、消す経路を持つ

AI が作るコードの品質を決めるのは、書かれた基準だけではありません。周りのコード、機械の検査、モデルが元から持っている判断、そして書かれた基準の4つです。AI は周りの書き方をいちばん強く真似ます。この中で書かれた基準がいちばん高くつきます。毎セッション読まれてコンテキストを使い、基準どうしで食い違い、古くなり、数が増えるほど1つ1つが効かなくなるからです。良いハーネスとは、品質を周りのコード・機械の検査・モデルの既定の振る舞いに担わせ、書かれた基準を、そのどれでも担えない残りだけにするものです。コードが良ければ書く基準は少なくて済み、コードが悪ければ基準は増え続けるので、リファクタは条件だけでなく基準も減らします。

足すだけでは文書は必ず膨らむので、消す経路を持ちます。消すためには、足した理由が残っていなければなりません。理由の分からない柵は、誰も怖くて抜けないからです。そこで基準には、何を防ぐためのものか（実際に起きた失敗）と、何に立っているか（モデルの振る舞い、いまのコードの形、外の前提）を残します。防ぎたい失敗が機械の検査で防がれるようになった、コードの形が変わった、モデルが指示しなくても正しく振る舞うようになった、といった形で理由が消えたら、その基準を消します。

各ビルドの振り返りでは「読み込まれたが役に立たなかった記述」も記録し、close-cycle が削除や置き換えを提案します。ただし、基準がうまく働いて失敗を防いでいるとき、振り返りからは何も起きなかったようにしか見えません。役に立たなかったという信号だけで消すと、働いている柵まで抜いてしまうおそれがあります。そこで、基準を消す変更を別の PR にし、マージしたあとの品質の指標（レビューの重い指摘、差し戻し、重要度が高い落とし穴）を比べ、悪くなったら戻します。害が成果物に残る基準（情報の漏えいやデータの損失を防ぐものなど）は、試しに消す対象にしません。試しが失敗したときの損失が取り返しのつかないものだからです。

## 委ねる範囲を決める

### 承認ゲートは「確認」と「同意」を分ける

ユーザーの時間を、ユーザーにしか下せない判断に使うため、承認を確認と同意に分けます。省いてよいのは確認だけで、ユーザーにしか下せない判断は、どの設定でも省きません。どちらに当たるかを決めるのは、ゲートの番号ではなく、そこで下される判断の種類です。意図を変える判断、外の前提に関わる判断、AI に任せてよい上限を超えるリスクを受け入れる判断が同意で、それ以外の覆せる判断や安全側に倒す判断は確認です。

G1（要件の合意）は、user-stories が「何を作るか」の唯一の合意点で、後段の承認では代替できません。設計も plan も「その要件で正しいか」を前提に置いているからです。G10（永続ドキュメントへの昇格の承認）のうち、`decisions` と `constraints` の変更は、ユーザーが約束した前提とリスクの変更なので同意です。`overview`・`conventions`・`glossary` は、コードから作り直せる理解なので確認として扱います。G3（設計案の選択）は、案の中に上限を超える害を受け入れるものが無ければ確認で、express で省けます。省いた場合も、採用理由と退けた案は ADR と PR 本文に残ります。

読まれない承認は、承認が無いより悪いものです。「ユーザーが確かめた」という記録だけが残り、後でその記録を見た人は確かめられたものとして信じてしまいます。そこで、ユーザーに見せる量は、ユーザーが限られた時間で実際に読める量に合わせます。G4（設計ドキュメントの承認）では、外との境界と内部の境界がどう変わるかを示します。どこが境界かは宣言したパスで判定します。G8（実装の直前に、実装手順とテストシナリオをまとめて承認）では、受け入れ基準から一意に決まらず AI が解釈で決めた振る舞いと、どのシナリオにも対応していない受け入れ基準だけを示します。大枠のシナリオは、G1 で合意したユーザーストーリーがすでに担っているからです。

コードレビューだけはどの設定でも実行します。中間成果物のレビューはユーザーの承認で代替できますが、コードは差分が大きく、ユーザーの承認ゲートが拾える粒度を超えるためです。

### 影響の大きさと、サイクルの複雑さ

リスクは、判断が外れたときの影響の大きさと、外れる見込みの掛け算です。同じ欠点でも、信頼できる数人しか使わないアプリケーションなら受け入れてよく、一般に公開しているサービスなら受け入れてはいけないことがあります。

影響の大きさは、アプリケーションの状況で決まります。公開範囲、扱うデータの重さ、壊れたときの影響を、ユーザーがリポジトリで1回宣言し、認証・課金・マイグレーションのような重い領域はパスで上書きします。この宣言が、AI に任せてよいリスクの上限になります。アプリケーションの状況は、ほぼすべての判断を横断する外の前提で、個人用に作ったものを公開したときのように、黙って偽になります。リスクを受け入れるときに拠り所にした前提を記録しておけば、宣言を変えるときに、その前提に立って受け入れたリスクを見直せます。宣言を変えるのは、受け入れたリスクすべての土台を変えることなので、ユーザーの同意です。

外れる見込みは、サイクルの複雑さで決まります。これを扱うのが [プロファイル](configuration/profiles.md) で、確認をどれだけ挟むかを選びます。プロファイルは、ユーザーが前もって下した委任の判断であり、アプリケーションの状況が決めた上限の中で選びます。複雑さは要件を合意して初めて見えてくるので、G1 の時点で、選んだプロファイルのままでよいかをユーザーが確かめます。複雑なサイクルは、害が無くてもシステムの成り立ちを変えるので、ユーザーが設計を見ておく理由にもなります。

ユーザーが決めた方針は、スクリプトも LLM も黙って切り替えません。差し戻しや、設計と要件の衝突のように、委任の前提が崩れたことを示す出来事が記録に残ったら、委任を続けるかをユーザーに尋ねます。差し戻しからの再設計の回では、システムの成り立ちが変わるので、プロファイルに関わらずユーザーが設計を見ます。委ねる範囲を決めるのは、スクリプトが判定できる宣言と出来事だけです。LLM の判断は、ユーザーに上げる向きにだけ使います。そうすれば LLM の判断がぶれても、起きるのは余計な問いが1つ増えることだけで、上げるべき問いを見逃すことは起きません。

### 同意は、その場でなくマージの前にもできる

上限の表が決めるのは、AI が受け入れてよいか、ユーザーが同意すべきか、という「誰が」です。ユーザーが同意するときに、止まってその場で同意するか、先に進めてマージの前にまとめて同意するか、という「いつ」は別の軸です。本番の運用でも、速度を優先したい場面はあります。

Hikyaku はデプロイを行わないので、マージの前にユーザーが同意すれば、リスクが利用者に届く前にユーザーが引き受けたことになります。そこで、ユーザーがサイクルの設定で明示して選べば、上限を超えるリスクの受け入れを止めずに進め、マージの前にまとめて同意する事後同意を使えます。同意を省くのではなく、遅らせるだけです。代償は、ユーザーが退けたときに、その判断に立って作った部分を作り直すことです。意図を変える判断と外の前提が要る判断は、答えを成果物から導けず、作り直しの範囲も読めないので、事後同意には回さず、その場で止まります。

事後同意が本当の同意になるのは、受け入れたリスクの一覧が、拠り所の前提と失うものを添えて、マージの前に読める量で示されるときだけです。マージが実際にユーザーの関門になっていることも条件で、自動でマージする運用や、マージがそのままリリースになる運用では成り立ちません。そのため、アプリケーションの状況の宣言で、マージがユーザーの関門であるとユーザーが書いているときだけ選べます。一覧はスクリプトが組み立て、そのリスクを受け入れたフェーズの PR に載せます。退けた項目は「未解決の退け」として示し続け、作り直しは差し戻しの経路で行います。

### 後で決めることは、いつ・誰が決めるかを記録する

すべての判断を、問いが出たその場で決められるわけではありません。サイクルの途中で出た未決事項や暫定の決定は、いつ決めるか（フェーズやゲートの開始、PR のマージの前、サイクルの close といった、サイクルの中の出来事）と、誰が決めるか（ユーザー、どのフェーズの AI、監督）を付けて、サイクルの追記型の記録に残します。その時が来たら、スクリプトが手順の中で示し、決まるまで示し続けます。決まったかどうかは保存せず、決定の記録から導きます。ユーザーが決める事項を、AI や監督に付け替える経路は持ちません。異議と決定の記録や、事後同意の一覧も、この記録の上に載っています。

### conductor は、明示した範囲で委任する

[conductor](workflow/conductor.md) は、確認と同意への答えを監督のセッションに任せます。これはプロファイルという設定で黙って外すのではなく、ユーザーが `/hikyaku:conductor` を起動し、委任の範囲を確認したうえで任せる委任です。監督が下した判断は根拠とともに成果物の記録に残るので、PR のレビューで追えます。

監督に任せられないものは、プロファイルと同じ線で決まります。G1（要件の合意）は委任の対象にせず、conductor は PLAN を終えたサイクルからしか始まりません。承認済みの成果物から答えを導けない問い（外の前提が要る問い）と、スコープを広げる問い（意図を変える問い）はユーザーに上げます。リスクについては、監督は安全側にだけ倒してよく、上限を超える害を受け入れる判断や、安全側の推奨を退ける判断はユーザーに上げます。安全側に倒した判断は、間違っていてもあとで緩められます。

それでも conductor は、できるだけ最後まで走りきることを目指します。ユーザーが事後同意を選んでいれば、上限を超えるリスクの問いで止まらずに一覧に積み、ユーザーがレビューする最後の PR（conductor ブランチからベースブランチへの PR）に、全フェーズの分をまとめて載せます。ユーザーに上げる問いが出ても、その問いに依存しないビルドは先に進め、依存するビルドだけが、何の答えを待っているかを示して止まります。走りきるために、監督がユーザーに上げるべき問いに自分で答えることはしません。

## Hikyaku 自身を直す

Hikyaku も、前提が変われば縮めるべき手段です。指示文はいまのモデルに必要な分だけ書き、旧モデル向けの念押しは、必要かを確かめてから残します。

指示文がユーザーのリポジトリで役に立っているかを知るには、ユーザーからのフィードバックが要ります。ただし、非公開のプロジェクトの中身を外に出すことは、取り消せない操作です。そこで、分析は利用者のリポジトリの中で行い、外に出す候補は中身を含まない記録（どの手順で止まったか、ゲートでどれだけ時間がかかったか、Hikyaku 自体の不具合として記録した `upstream` の一覧など）に絞ります。AI は文章を用意するところまでにし、送る前にユーザーが全文を読んで、起票もユーザーが行います。AI に一般化を頼んでも、プロジェクトの固有名が残ることがあるためです。

| フェーズ | サイクル内の4段階（PLAN / ARCHITECT / BUILD / CLOSE） |
| セッション | 1つのAI実行単位。1フェーズ、1ビルド、または1つの patch につき1セッション |
| ビルド | 1セッションで完結する実装作業の単位。`build-{NN}/` ディレクトリに対応する |

| 作業単位 | 手順の記録（`progress.jsonl`）を持つ単位。サイクルの `planning/`・`design/`・`build-{NN}/`、patch の `patches/{YYYYMM}/{slug}/` など |
| ステップ | フェーズの中の手順。並びと実行の条件はスクリプトが定義し、`hikyaku step next` が1手ずつ返す |
| ゲート | ユーザーに承認を求める箇所。確認（省ける）と同意（省けない）に分かれる。一覧は [プロファイル](configuration/profiles.md#承認ゲート) |
| 永続ドキュメント | 実装済みの現実（as-is）を表す。所在は `document-guide.md` が宣言する |
| サイクルドキュメント | これから作るもの（to-be）と作業記録。`cycles/{NNN}-{slug}/` 配下 |
| ユーザー | コーディングエージェントを操作し、Hikyaku でサイクルを回す人。結果の責任を引き受け、同意を下す |
| 利用者 | 作っているアプリケーションを使う人 |
| 外の前提 | リポジトリの外の世界についての事実や仮定（外部サービスの仕様、利用者の範囲、契約など）。コードを読んでも分からない |
| 内の前提 | いまのコードの構造についての事実。コードと照合できる |
| 受け入れたリスク | 判断の際に、承知のうえで受け入れた欠点。拠り所にした前提と一緒に記録する |
| 境界 | 外との境界（公開 API、画面の振る舞い、保存するデータの形、外部連携）と、内部の境界（モジュールの分け方、依存の向き） |
| アプリケーションの状況 | 公開範囲・扱うデータの重さ・壊れたときの影響と、マージがユーザーの関門であるかの宣言。AI に任せてよいリスクの上限を決め、事後同意を選べるかを決める |
| 事後同意 | 上限を超えるリスクの受け入れを、止めずに進め、マージの前にまとめてユーザーが同意すること。同意を省くのではなく遅らせる。ユーザーがサイクルの設定で明示して選ぶ |
| 未決事項 | サイクルの途中で出た、まだ決まっていない事項や暫定の決定。いつ・誰が決めるかを付けて記録し、その時が来たらスクリプトが示す |
| 予測ピーク | ビルドを1セッションで進めたとき、メインセッションのコンテキストがどこまで膨らむかの予測（トークン）。ビルドの大きさの判定に使う。詳細は [BUILD](workflow/build.md#予測ピーク) |
| 上限 | 1ビルドのメインセッションのコンテキストが超えないようにする値（`[context] limit`。既定 500k）。builder の区切りで、完了時点の見込みと比べる。詳細は [BUILD](workflow/build.md#コンテキストの区切り) |
| 見積もりの上限 | 予測ピークがこれを超えたら分割を検討する値。上限に割合（既定 90%）を掛けて求め、見積もりが外れることへの余裕を残す |
| 見積もりのガイド | 予測ピークの成分の見積もり方を書いた文書。標準のガイドか、`{HIKYAKU_ROOT}/token-guide/guide.md`。詳細は [予測ピークと見積もりのガイド](configuration/token-guide.md) |
| 安全でない分割 | 途中のビルドのマージ時点で、本番に出すと既存機能やデータを壊しうる中間状態になるビルド分割。base_branch がリリースされないブランチで、サイクルが宣言したときだけ許される。詳細は [`[data_integrity]`](configuration/config-file.md#data_integrity) |
| プロファイル | 確認をどれだけ挟むかを決めるサイクルの属性。ユーザーが前もって下す委任の判断。詳細は [プロファイル](configuration/profiles.md) |
| 監督 | `/hikyaku:conductor` を実行しているセッション。子セッションを起動し、その問いに答えるかユーザーに上げる。詳細は [conductor](workflow/conductor.md) |
| 子セッション | 監督が非対話（`claude -p`）で起動し、1フェーズまたは1ビルドを既存のスキルのまま実行するセッション |
| パッチ | サイクルを作らずに、小さな変更を依頼のすり合わせから PR まで1セッションで進める作業の単位。`patch-{YYYYMM}-{slug}` で表し、記録は `patches/{YYYYMM}/{slug}/` に置く。詳細は [patch](workflow/patch.md) |
