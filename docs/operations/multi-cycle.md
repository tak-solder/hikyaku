# 複数サイクルの並行運用

1つのリポジトリで複数のサイクルを同時に回せます。ビルドどうしも、依存が無ければ並行して進められます。

## 対象サイクルの決まり方

スキルにサイクルを渡さなかった場合、次の順で決まります。

1. 引数での明示指定
2. 現在のブランチ（そのブランチに居る以上に強い根拠はありません）
3. `.hikyaku.local` の記録（`active` のもののみ）
4. 進行中サイクルが1つだけならそれ

決まらなければ候補を挙げて尋ねます。推測して別のサイクルへコミットする事故を避けるためです。

slug は全履歴で一意ではありません（`closed` になった slug は再利用できます）。明示指定でも複数一致した場合は `active` を採り、それでも決まらなければ候補を挙げて尋ねます。確実に指すには ID かディレクトリ名を使ってください。

```
/hikyaku:builder 002-billing      ← ディレクトリ名
/hikyaku:builder 002              ← ID
/hikyaku:builder billing          ← slug（closed が同名なら active を採る）
```

## .hikyaku.local

「自分が最後に触ったサイクル」だけはリポジトリから導出できません。チーム開発では、最後にコミットされたサイクルが他メンバーのものであることが普通だからです。これを `{HIKYAKU_ROOT}/.hikyaku.local` に記録します。git 管理対象外なので、他のメンバーには影響しません。

```bash
hikyaku cycle use 002-billing
```

これはワークフローの状態ではなく作業の栞です。読むのは対象サイクルの決定だけで、`next` / `validate` / `cycle status` など判断に使う処理は参照しません。消えても、次にどのサイクルで作業するかを尋ねられるだけです。

## 状態を見る

```bash
hikyaku cycle list --active
```

状態は保存されておらず、ファイルから導出されます。

| 表示 | 条件 |
|---|---|
| `planning` | `user-stories.md` が無い |
| `architecting` | `user-stories.md` はあるが `tasklist.md`（またはビルド）が無い |
| `building` | 未完了のビルドがある |
| `completed` | 全ビルドが完了。だが永続ドキュメントへの昇格がまだ |
| `closed` | `cycles.md` に記録された status |

**`completed` のまま放置しないでください。** 実装は main に入っているのに `overview` は古いままなので、この期間に他サイクルの architect が走ると古い現実を信じて設計します。`create-cycle` はこの状態を検出して警告します（ブロックはしません）。

## サイクル間の依存

`create-cycle` の `--depends` でサイクルレベルの依存を宣言できます。依存が満たされた状態とは、依存先サイクルが `closed` になったことです。

ビルドレベルのクロスサイクル依存は扱いません。依存グラフが2次元になって破綻するためです。

## 並行ビルド

```bash
hikyaku next 002-billing
```

依存するビルドがすべて完了しているビルドが返ります。複数返った場合、それらは並行して進められます。

完了判定はデフォルトブランチの tree から読みます。作業ツリーを見ると、ビルドブランチ上では `tasklist done` した直後の自分の `PR` 列が見えてしまい、未マージのビルドを完了とみなして依存ビルドを着手可能にしてしまうためです。一方、ビルドの一覧そのものは作業ツリーから取ります。まだマージされていない tasklist の追加分も候補に出すためです。

「着手中」の表示は origin のブランチ一覧から導出しています。origin に到達できなくても、着手可能・待機の判定には影響しません。マージ後にブランチを削除しない設定のリポジトリでは残存ブランチが着手中に見えるため、`PR` 列が非空のビルドは着手中として扱いません。

## 中断と再開

```bash
hikyaku cycle status 002-billing
```

ブランチ上の成果物の有無から、どこまで進んだかを割り出します。必須成果物と条件付き成果物を区別するので、条件付きのものが無くても未完了とは限りません。

再開するときは、そのサイクル・そのフェーズのスキルをもう一度呼ぶだけです。既存の成果物を読み込んで途中から続きます。

**成果物を1つ作るごとにコミット & push されていることが前提です。** コミットされていなければ他のセッションからは見えず、再開点を検出できません。同じ理由で、`cycle status` はブランチを決めたあとに実行します。デフォルトブランチに居るまま実行すると、別セッションが push 済みの成果物が見えず、最初からやり直すことになります。

## ブランチの衝突を避ける

Hikyaku の規則に従う場合、ビルドブランチの存在が「着手中」の印になります。作成したら早めに push しておくと、他のセッションが同じビルドを掴む事故を避けられます。
