# fit: patch で進めるかの判定

directive の `値` に、scope で見積もった予測ピーク（`peak`）と、分割を検討する上限（`splitAbove`）、
上限を超えたか（`overSplit`）がある。

- [ ] 項目ごとに、次のどれかに当たるかを判定する

| 観点 | 当たるとき |
|---|---|
| 1セッションに収まるか | `overSplit` が true |
| データの形 | スキーマ・マイグレーション・保存形式・公開 API の契約を変える |
| 設計判断 | ADR に残すべきトレードオフがある（複数の案から選ぶ必要がある） |
| 要件 | 新しいユーザーストーリーが要る、または期待する挙動のすり合わせが収束しない |
| 検証できるか | テストでも手元の確認でも、変更後の挙動を確かめられない |

- [ ] どれにも当たらなければ `done` を報告する
- [ ] 当たる項目があれば、当たった観点と根拠を示して、ユーザーに尋ねる。どれが妥当かは示唆しない
  1. それでも patch で進める
  2. 当たった項目だけ通常のサイクルへ引き継ぎ、残りを patch で進める
  3. すべて通常のサイクルへ引き継ぐ
- [ ] 1 なら `done` を報告する。P1 の提示で、当たった観点と進める理由を伝える

## 通常のサイクルへ引き継ぐ（2・3）

- [ ] 引き継ぐ項目の調査結果と、ここまでの合意を `${CLAUDE_PLUGIN_ROOT}/skills/patch/references/templates.md`
  （[templates.md](../references/templates.md)）の「intake.md」の形にまとめる
- [ ] デフォルトブランチ（`patch resolve` の `baseBranch`）に移ってから、`/hikyaku:create-cycle {slug}` を呼ぶ。
  patch からの引き継ぎであることと、まとめた内容を渡す。create-cycle はサイクルを作ったあとに
  `planning/intake.md` を書き、planner はそれを企画の入力として読む
  - 2 のときは、PLAN へ進むかの確認で「いいえ（単独で終える）」を選ぶよう伝える。PR を作り終えたら
    patch のブランチへ戻る
- [ ] 2 なら、残りの項目で `done` を報告する
- [ ] 3 なら、`skipped` を報告する（`--reason` に引き継いだサイクル）。以後 step は止まり、patch のブランチは
  PR にしない。引き継いだサイクルと、次に `/hikyaku:planner {NNN}-{slug}` を実行することを伝える
