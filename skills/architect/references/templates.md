# 設計フェーズ テンプレート集

## design-questions.md

```markdown
# 設計段階の質問

### Q1: （質問内容）
- 案a（推奨）: （案の内容）。欠点: （この案で失うもの・弱点）
- 案b: （案の内容）。欠点: （この案で失うもの・弱点）

**回答**: （ユーザーの回答。推奨どおりなら「案a（推奨どおり）」）
**退けた推奨で失う利点**: （推奨と違う案を選んだときだけ書く。何を優先したかと、推奨案の利点のうち失うもの）
```

- 選択肢のある質問では、各案に欠点を添え、推奨を1つ示す。推奨を示さない質問（事実の確認・ユーザーにしか分からない前提）は、選択肢を書かずに質問と回答だけにする
- ユーザーが推奨を退けたら、「退けた推奨で失う利点」を必ず書く。推奨どおりなら書かない

## ADR（`hikyaku` 管理の場合）

`decisions` が指すディレクトリに、判断ごとに1ファイル（`{YYYYMMDD}-{slug}.md`）で追記する。
`repo` 管理の場合はこのテンプレートを使わず、既存形式に合わせる。

```markdown
---
status: accepted
---

# （判断の要約）

- **決定**: （採用した案）
- **文脈**: （なぜこの判断が必要だったか。背景）
- **外の前提**:
  - （リポジトリの外の事実か仮定）（事実|仮定。確かめた出どころ、YYYY-MM-DD 確認）
- **検討した案**:
  - 案A: （概要）
  - 案B: （概要）
- **推奨**: （AI が推奨した案）
- **採用理由**: （何を重視してこの案を選んだか）
- **受け入れたこと**:
  - （この決定で受け入れたリスク・失うもの）（拠り所: `<前提の参照>`）
  - （拠り所にする外の前提が無いもの）
- **トレードオフ**: （採用案の弱点・将来発生しうるコスト）
- **再評価条件**: （この判断を見直す出来事）
- **退けた推奨で失う利点**: （推奨と違う案を採ったときだけ。推奨どおりなら「なし（推奨どおり採用）」）
- **影響範囲**: （どのコンポーネント・ドキュメントに効くか）
- **領域**: `<glob>`, `<glob>`（任意）
```

**記載ガイドライン:**
- architect Step 4a で「分岐あり」と判定された判断のみ記録する。分岐がなく自明な判断は記録しない
- 欄の順は上のとおり。前提・判断・推奨・受け入れたこと・再評価条件を混ぜずに、それぞれの欄に書く
- 「外の前提」は、リポジトリの中からは分からず、黙って変わりうること（利用者の状況・外部サービスの仕様など）。
  1件1行で、事実か仮定かと、確かめた日を書く。無ければ「なし」
- 「受け入れたこと」は1件1行の箇条書き。外の前提を拠り所にする行は、行末を `（拠り所: \`<前提の参照>\`）` で終える
  （複数ならカンマ区切り）。参照の書式は `app.exposure` / `app.data` / `app.impact` / `app.merge_gate` /
  `area:<name>` / `constraints#<anchor>` / `adr:<file>` / `assumption:<短い文>`（確かめていない前提）。
  拠り所にする外の前提が無い行には付けない。宣言を変える PR で `hikyaku ledger premises` がこの行を読み、
  見直しの対象として示す。書式の崩れた行は `hikyaku validate` が警告する
- 「検討した案」には Step 4b で code-architect が出力した各案を要約して並べる
- 「トレードオフ」は採用案の弱点・将来発生しうるコストを明記する。**「特になし」は禁止**（トレードオフがないなら分岐なしのはず）
- 「領域」は、この判断が効くパス（glob）。任意で、書くなら最後の欄に、バッククォートで囲んだ glob をカンマ区切りで
  1行に並べる。長く触られていない領域に変更が入るとき、この判断を見直しの対象として示すために読まれる
- 外の前提と受け入れたことは、ユーザーの同意なしに書き換えたり消したりしない（変えるときは新しい ADR を起こす）
- 採用案を覆す場合は新しいファイルを追加し、旧エントリの `status` を `superseded` にする。本文は書き換えない（決定の履歴を残すため）
- `status` は architect が `accepted` で書き、close-cycle が `implemented` に更新する
