# design-delta: design-delta.md の作成

- [ ] `cycles/{cycle}/design/design-delta.md` を作成する
  - フォーマットは `${CLAUDE_PLUGIN_ROOT}/skills/architect/references/templates.md` を参照
  - 書く: このサイクルで作るもの（to-be）/ 永続ドキュメントのどこを更新する予定か / 既存構造への影響
  - 書かない: 実装コード / ビルド分割（tasklist が正）/ 恒久的な設計判断（ADR が正）/
    既に永続側にある内容の再掲
  - 「永続ドキュメントのどこを更新する予定か」は close-cycle と cycle-scanner の入力になる
  - データの形や意味を変える設計（スキーマ・保存形式・API の契約の変更）では、移行の段階を書く。
    例: 追加 → 書き込みの切り替え → 既存データの移行 → 旧形式の削除、フィーチャーフラグで未完成の
    機能を隠す、新旧 API を並行稼働させる。段階に分けておくと、ビルド分割で各段階をマージしても
    データを壊さないビルドに分けられる
  - user-stories.md の「スコープ外」に挙げたものは設計に含めない。必要だと判断したら、設計に入れずに
    企画フェーズへの差し戻しをユーザーに提案する
  - 値 `round` が `return`（差し戻しからの再設計）なら、撤回した判断を残す。書き換えるだけでなく、どの判断を、
    なぜ撤回したかを1段落で書く（後からビルドの PR を読む人が、設計が変わった理由を追えるようにするため）
  - 値 `round` が `add`（指摘からの追加設計）なら、どの指摘を受けて何を変えたかを1段落で残す
