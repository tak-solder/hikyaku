# G4: 設計ドキュメントの承認

- [ ] 提示の中身をスクリプトに組み立てさせる

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" gate brief G4 architect {cycle}
```

- [ ] 出力に沿って提示し、承認を得る（G4）
  - `[boundaries]` の宣言が無いと出たら、従来どおり design-delta.md と、doc-reviewer の指摘への対処を提示する
  - 外との境界の変更（同意が要る）があれば、G4 は同意として返る。提示の冒頭に、境界のパスと、それに触れた
    設計の文書のパスを示して同意を得る。内部の境界の変更（確かめる）は、その下に確かめる変更として示す
  - G3 の申告に無い重い領域（値 `undeclaredAreas` と同じ）が出ていれば、領域の名前と触れたパスを示し、G3 の時点では
    申告されていなかったことを伝えて同意を得る。裏取りできなかった（値 `verified` が false）なら、領域が空でも
    同意として、notices の理由を示す
  - ほかにも directive の承認が同意なら、その理由（`approvalReason`）を冒頭に示す。notices に基準の宣言を
    読めなかったことが出ていれば、それも添える
  - 全文は、ユーザーが求めたときに `--full` を付けて出す

承認観点はこれに限定する:

```
- G3 で採用した案（express では推奨案）が design-delta に正しく反映されているか
- 分岐なしとして ADR に記録しなかった判断に、見落としがないか
- doc-reviewer の指摘への対処は妥当か
- （境界を宣言していれば）外との境界・内部の境界の変更が意図どおりか
```

技術選定の是非は G3 で決着済みなので、ここで問い直さない。同じことを二度聞くのが
承認ラウンドの冗長さの正体になる。

- [ ] フィードバックがあれば `rejected` を報告し、設計に関する質問に戻る。答えに沿って質問をし直したら
  `questions` を `done` で報告し直す。そこから後ろ（案の生成・ADR・design-delta・レビュー・G4）が
  やり直しになるので、既存の成果物を答えに沿って見直しながら `step next` に従って進める
