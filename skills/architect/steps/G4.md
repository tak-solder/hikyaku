# G4: 設計ドキュメントの承認

`architecture_gate` が有効なとき（economy / standard / thorough）に返るゲート。

- [ ] design-delta.md と、doc-reviewer の指摘への対処をユーザーに提示して承認を得る（G4）

承認観点はこれに限定する:

```
- G3 で採用した案（express では推奨案）が design-delta に正しく反映されているか
- 分岐なしとして ADR に記録しなかった判断に、見落としがないか
- doc-reviewer の指摘への対処は妥当か
```

技術選定の是非は G3 で決着済みなので、ここで問い直さない。同じことを二度聞くのが
承認ラウンドの冗長さの正体になる（G3 を省く express では G4 も省かれるので、
「選択は省いたのに承認では問う」という中間状態は生じない）。

- [ ] 承認されたら `approved` を報告する（`--input` にユーザーの答え）。承認は design-delta.md の
  ハッシュに結びつく
- [ ] フィードバックがあれば `rejected` を報告し（`--input` にユーザーの答え）、設計に関する質問に戻る
  - 答えに沿って、必要な質問をし直す（`questions.md` の指示。記録は design-questions.md）
  - 設計判断が変わるなら `options.md` の指示で評価し直す。分岐がある判断が新たに出て G3 が有効なら、
    `G3.md` の指示で選択を得てから、`adr.md` の指示で ADR を追記する
  - design-delta.md を直し、`design-delta` を `done` で報告し直す。そこから後ろ（レビュー・G4）が
    やり直しになるので、`step next` に従って進める
  - `questions` や `options` は報告し直さない。design-delta.md が残ったまま前のステップに戻ると、
    step は記録の欠けとして止まる
- [ ] progress.jsonl をコミット & push する
