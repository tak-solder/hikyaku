# Hikyaku Retrospective

セッション全体を振り返り、改善提案を分類・記録する。

このスキルは hikyaku:planner / hikyaku:architect / hikyaku:builder / hikyaku:close-cycle からモデル呼び出しで使用される内部スキルです。
ユーザーが直接呼び出すことは想定していません。hikyaku ワークフロー以外のコンテキストから呼び出された場合は、その旨をユーザーに伝えて終了してください。

## 引数

- `$ARGUMENTS[0]`: cycle — 対象サイクル（`{NNN}-{slug}`）
- `$ARGUMENTS[1]`: SUB_DIR — 出力先サブディレクトリ（`planning`, `design`, `build-{NN}`, `close`）

HIKYAKU_ROOT は受け取らない。`.hikyaku.config` から解決される。

出力先: `{HIKYAKU_ROOT}/cycles/$ARGUMENTS[0]/$ARGUMENTS[1]/retrospective.md`

## 2種類を分けること

振り返りには性質の異なる2種類が混ざる。分けて記録する。

| 種類 | 何か | 行き先 |
|---|---|---|
| 改善提案（R-N） | 以後の取り決め。「次からこう書く / こう進める」 | close-cycle が `conventions` などの永続ドキュメントか `instructions.md` へ反映する |
| リポジトリ固有の学び（L-N） | 踏んだ地雷。再現条件が明確な落とし穴 | close-cycle が `learnings` へ昇格させる |

軸は「提案か、事実か」。提案は R-N、踏んだ地雷は L-N。R-N に `doc:learnings` は
指定しない（落とし穴は L-N で書く）。

L-N には、再現条件（「なんとなく遅い」ではなく「N=1000 でタイムアウトする」）と、どのビルドで
いつ判明したかを書く。書けないもの、一般的なプログラミング知識、「気をつける」だけの曖昧な注意は
L-N にしない。close-cycle がそのまま `learnings` へ昇格させるので、曖昧なものを入れると
永続ドキュメントが濁る。

retrospective.md はコミット対象で、close-cycle が素材として読む。両方の節が無いと、
素材収集で拾うものが無くなる。

実装フェーズ（`build-{NN}`）ではこれに加えて BP見積もりの実績を記録する。
見積もりと実績を並べた事実の記録で、R-N でも L-N でもない（Step 3 と Step 6 を参照）。

## 事実の昇格は handoff.md が担う

`overview` / `constraints` に載るような事実（新しい制約が判明した、責務が動いた）は
`handoff.md` に書く。振り返りで扱うのは提案（R-N）と落とし穴（L-N）だけで、
昇格の経路を二重に持たない。

## 作業ステップ

### Step 0: 設定の確認

- [ ] 設定を解決する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" config $ARGUMENTS[0] --json
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" docs list
```

`docs list` は Step 5 で `doc:` の論理名を選ぶために使う。そこに無い論理名は使わない。

出力の `reviews.retrospective` の値（サイクルの profile が適用済み）に応じて動作を決定する:
- `skip`: 振り返りをスキップし、呼び出し元に制御を返す
- `auto`: ユーザーへの確認をスキップして Step 2 へ進む
- `prompt`: Step 1 へ進む

### Step 1: ユーザーに振り返りの実施を確認

- [ ] ユーザーに振り返りを実施するか確認する（ask: retrospective）

```
振り返りを実施しますか？（y/n）
振り返りではセッション中のスキル外指示を分析し、スキルやインストラクションの改善提案を作成します。
```

→ 実施する場合は Step 2 へ。不要な場合は振り返りをスキップし、呼び出し元に制御を返す。

### Step 2: コンテキストの把握

- [ ] SUB_DIR からどのフェーズの振り返りかを判定する
  - `planning` → 企画フェーズ（ヘッダー: `企画フェーズ 振り返り`）
  - `design` → 設計フェーズ（ヘッダー: `設計フェーズ 振り返り`）
  - `build-{NN}` → 実装フェーズ（ヘッダー: `Build {NN}: {ビルド名} 振り返り`、issue.md からビルド名を取得）
  - `close` → サイクル終了フェーズ（ヘッダー: `サイクル終了 振り返り`）
- [ ] 出力先に既に `retrospective.md` が存在するか確認する（存在する場合は追記モード）

→ SUB_DIR が `build-{NN}` なら Step 3 へ。それ以外のフェーズは Step 3 を飛ばして Step 4 へ。

### Step 3: BP実績の収集（`build-{NN}` のみ）

見積もりと実績を並べて記録する。精度を上げるための素材集めであって、
見積もりの正否を裁く場ではない。 乖離があったときに、どの指標を読み違えたのかが
残っていれば、次のサイクルの見積もりがそこを見るようになる。

- [ ] plan.md の「BP見積もり」から、architect フェーズ段階と builder フェーズ段階の BP、
      および builder 段階の内訳表（`bp estimate` の出力）を読む
- [ ] 実績の指標を集計する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" bp actual $ARGUMENTS[1] $ARGUMENTS[0]
```

新規ファイル数・変更ファイル数・追加行数・削除行数が返る。比較の起点は `pr base` と
同じ導出（スタックしていればスタック元）で、ワークスペース配下のワークフロー成果物は
除かれる。

**数えるのはコマンドの仕事で、あなたの仕事ではない。** 差分を目で見て概算しない。

- [ ] 実績 BP を、見積もりと同じ経路（`bp estimate`）で求める
  - `bp actual` が返した新規ファイル数を `--new-files`、追加行数を `--lines` に渡す（実測）
  - 差分からは測れない指標（API操作数など）と加算要素（影響ファイル数、基盤セットアップ、
    外部API連携、大規模リファクタ、基準表にあればリポジトリ固有の要素）は、実装中に実際に
    発生したものを渡す（申告）。plan.md の見積もり値をそのまま流用しない
  - 変更ファイル数は影響ファイル数そのものではない（読んだだけのファイルは差分に出ない）。
    実装中に実際に読み込んだ範囲を数える

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" bp estimate $ARGUMENTS[0] \
  --new-files {実測} --lines {実測} --impact-files {申告} [--<加算要素>]... --markdown
```

  - 出力の内訳表を「実績の内訳」にそのまま貼る。表への当てはめは自分でしない

- [ ] このビルドが1セッションで完結したかを記録する（BP の定義そのものの検証になる）
  - 完結 / 途中でビルドを分割した / N セッションかかった、のいずれか

`bp actual` がエラーになる場合（Hikyaku の規則外のブランチで作業して base を解決できない、
履歴が浅くて merge-base が取れない等）は、実測をスキップして見積もりだけ記録し、
実績欄に「実測不可」と書く。 推測値で埋めない。

→ Step 4 へ。

### Step 4: 会話履歴の分析

- [ ] 会話履歴を見直し、以下を洗い出す:
  - スキルの手順に含まれていないが、ユーザーから受けた指示・修正・補足
  - スキルの手順通りに進めたが、うまくいかなかった点
  - 実装フェーズの場合: PRレビューで指摘された設計・実装上の見落とし

→ Step 5 へ。

### Step 5: 改善提案の作成と対象の分類

- [ ] Step 4 で洗い出した内容から改善提案を作成する
- [ ] 各提案について、以下の判断フローに従って対象を分類する

分類先はこのリポジトリの中だけにある。「どのファイルに書くか」ではなく
「どの論理名のドキュメントに書くか」で指す。所在を宣言しているのは
`document-guide.md` だけで、パスはそこから引く。

判断フロー:

```
Q1: 以後の書き方・進め方の取り決めか（規約・テスト方針・レビュー観点）？
  → Yes → 対象: doc:{document-guide の論理名}
  → No ↓
Q2: このリポジトリで Hikyaku を回すときの手順・前提か（複数フェーズに効く）？
  → Yes → 対象: workflow
  → No ↓
Q3: 今後、同様の状況が再発する可能性があるか？
  → Yes → Q1〜Q2 を再検討（スコープの見誤りの可能性がある）
  → No → 対象: 記録のみ
```

各分類の詳細:

| 対象 | 意味 | 具体案の記述内容 |
|------|------|---------------|
| `doc:{論理名}` | 規約系の永続ドキュメントの修正（`conventions` / `test-strategy` / `security-model` など） | 論理名を明記し、追記内容の文面案を書く。パスは書かない（`document-guide.md` が正） |
| `workflow` | `{HIKYAKU_ROOT}/instructions.md` の修正 | 追記する内容の文面案を書く |
| `記録のみ` | 一回限りの事象で一般化できない | 記録理由を簡潔に書く |

Hikyaku の手順そのものに穴があると思える場合も、この3つに落とす。
このリポジトリで埋めるなら `workflow` に書く。`instructions.md` は
インストラクションの優先順位で SKILL.md より上位にあり、スキルを上書きするための
正規の場所なので、迂回ではない。どちらにも落ちないものは `記録のみ`。

判断に迷ったときの指針:
- コーディング規約・テスト方針・PR 作成ルール → 多くの場合 `doc:conventions`（または `doc:test-strategy`）
- フェーズの進め方・このリポジトリ固有の前提・技術スタックの癖 → 多くの場合 `workflow`
- `doc:` の論理名が `document-guide.md` に無い → 勝手に作らない。`workflow` に寄せるか `記録のみ`

→ Step 6 へ。

### Step 6: retrospective.md の書き込み

- [ ] retrospective.md を [templates.md](references/templates.md) に従って作成する
  （`${CLAUDE_PLUGIN_ROOT}/skills/retrospective/references/templates.md`）
  - 新規作成なら「新規作成」、PRレビュー対応で既にあれば「追記」のテンプレートを使う
  - フェーズヘッダーは Step 2 で判定したものを使う
  - `build-{NN}` で「BP見積もりの振り返り」が既にある場合は、節を増やさず既存の表を
    Step 3 で集計し直した値に差し替える（見積もり側の行と内訳は変えない）

「BP見積もりの振り返り」は記録であって、乖離そのものを R-N に起こさない（見積もりのやり直しは
次のサイクルの仕事で、以後の取り決めではない）。ただし、乖離の要因がこのリポジトリ固有の
再現条件に落ちる場合は L-N にも書く（例:「このリポジトリでは型定義の変更が必ず全パッケージの
テストに波及する」）。Hikyaku の見積もり手順そのものへの提案になるなら、R-N の `workflow` 分類に落とす。

- [ ] 振り返りをユーザーに提示し、呼び出し元に制御を返す

## 記載ガイドライン

- スキルの手順通りに進んだ部分は書かない。差分だけを記録する
- 「スキル外で受けた指示」が最重要のインプット。ユーザーが追加で指示したことは、スキルに欠けている情報の証拠
- 具体案は、そのまま適用できるレベルの具体性で書く
- 改善提案がなければ「改善提案なし」と記載する
- 同じ提案が前のフェーズの retrospective.md にもあれば、その旨を書く。
  言われた回数は優先度そのものなので、close-cycle が束ねるときの材料になる
- BP の実績は集計コマンドの出力をそのまま書く。見積もりに寄せて丸めない。
  乖離が残っていることが次のサイクルの材料になるのであって、揃った表に価値は無い
- **実測と申告を混ぜない。** 新規ファイル数・追加行数は `bp actual` の値、それ以外は申告。
  申告した値を「実測」と書かない
