# bp-actual: BP 実績とセッションの実測の収集

実装フェーズ（`build-{NN}`）のときだけ、step はこのステップを返す。

見積もりと実績を並べて記録する。精度を上げるための素材集めであって、
見積もりの正否を裁く場ではない。乖離があったときに、どの指標を読み違えたのかが
残っていれば、次のサイクルの見積もりがそこを見るようになる。

- [ ] plan.md の「BP見積もり」から、architect フェーズ段階と builder フェーズ段階の BP、
      および builder 段階の内訳表（`bp estimate` の出力）を読む
- [ ] 実績の指標を集計する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" bp actual build-{NN} {cycle}
```

新規ファイル数・変更ファイル数・追加行数・削除行数が返る。追加行数は実装とテストの内訳も返る。
比較の起点は `pr base` と同じ導出（スタックしていればスタック元）で、ワークスペース配下の
ワークフロー成果物と、生成物（ロックファイル・スナップショット・生成コード。`[bp_actual]` で変更可）は
除かれる。

**数えるのはコマンドの仕事で、あなたの仕事ではない。** 差分を目で見て概算しない。

- [ ] 実績 BP を、見積もりと同じ経路（`bp estimate`）で求める
  - `bp actual` が返した新規ファイル数を `--new-files`、追加行数を `--lines` に渡す（実測）
  - 差分からは測れない指標（API操作数など）と加算要素（影響ファイル数、基盤セットアップ、
    外部API連携、大規模リファクタ、基準表にあればリポジトリ固有の要素）は、実装中に実際に
    発生したものを渡す（申告）。plan.md の見積もり値をそのまま流用しない
  - 変更ファイル数は影響ファイル数そのものではない（読んだだけのファイルは差分に出ない）。
    実装中に実際に読み込んだ範囲を数える

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" bp estimate {cycle} \
  --new-files {実測} --lines {実測} --impact-files {申告} [--<加算要素>]... --markdown
```

  - 出力の内訳表を「実績の内訳」にそのまま貼る。表への当てはめは自分でしない

- [ ] このビルドが1セッションで完結したかを記録する（BP の定義そのものの検証になる）
  - 完結 / 途中でビルドを分割した / N セッションかかった、のいずれか

`bp actual` がエラーになる場合（Hikyaku の規則外のブランチで作業して base を解決できない、
履歴が浅くて merge-base が取れない等）は、実測をスキップして見積もりだけ記録し、
実績欄に「実測不可」と書く。推測値で埋めない。

- [ ] セッションのコンテキストを実測する（BP がコンテキストの消費量を当てられているかの検証素材）

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" bp session build-{NN} {cycle} --markdown
```

  - ビルドのブランチに対応付くセッションから本体（そのブランチでの API 呼び出しが最も多いもの）を
    選び、ピーク・開始時の固定分・呼び出し回数・出力トークン・コンパクション回数・モデル・
    ホストとその版・Hikyaku の版を表で返す。現在のセッションがそのブランチにいれば候補に入る
  - 出力の表を「セッションの実測」にそのまま貼る。値を書き換えない・丸めない
  - 「計測不可（理由）」が返ったら、その表をそのまま貼る（Codex のクラウドなど）。推測で埋めない
  - Hikyaku の欄が「—」なのは、測ったのが現在のセッションでないとき（PR レビュー対応で
    別のセッションから測った等）。分かっていても書き足さない
  - 選ばれたセッションが想定と違う（例: 本体が別プロセスのレビューになった）なら、
    `--json` の `candidates` を見て、乖離の要因と同じ段落に一文で書く

- [ ] 区切りでのコンテキストを確かめる

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" step status build-{NN} {cycle}
```

  - 「区切りでのコンテキスト」に、G8 の最初の提示・実装開始前・レビュー前の値と目安（`[context]`）が
    並ぶ。値は progress.jsonl の報告に記録されたもので、`bp history` も同じ記録を読む。
    retrospective.md に書き写さない（節の形を変えないため）
  - 目安を超えたまま継続した区切りがあれば、どこで膨らんだか（G8 の差し戻しが続いた、実装で
    想定より多くのファイルを読んだ等）を「乖離の要因」に一文で書く。BP の乖離が無くても書く
  - 計測できなかった区切りは表に出ない。推測で補わない

- [ ] `done` を報告する
