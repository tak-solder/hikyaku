# write: retrospective.md の書き込みと提示

- [ ] retrospective.md を以下のテンプレートに従って作成する。出力先は directive の `値` の `output`
  （既にあれば追記モード）

新規作成の場合:

```markdown
# {フェーズヘッダー}

## 予測ピークの振り返り

（`build-{NN}` のときだけ置く。他のフェーズでは節ごと省く）

| 段階 | 予測ピーク | 根拠 |
|------|------------|------|
| architectフェーズ段階 | 〇k | issue.md の内訳 |
| builderフェーズ段階 | 〇k | plan.md の内訳（下表） |

**セッション**: （1セッションで完結 / 途中で分割（build-NN を追加）/ 〇セッション）

**乖離**: （セッションの実測のピーク − builderフェーズ段階。±10% 以内なら「なし」と書いてよい）

**乖離の要因**: （乖離があった場合のみ。成分ごとに、どちらへ、なぜ読み違えたかを書く。
　例:「読み込みを 110k と見たが、共通の型の変更が波及して呼び出し元を 20 ファイル読んだ（+90k）」。
　成分の見積もりは合っていたのに外れたなら、ガイドの見積もり方（換算の目安・固定費）の問題として書く。
　乖離が無ければ「なし」）

### builderフェーズ段階の内訳

（plan.md の内訳表をそのまま転記する。最後の行のガイドの版も消さない）

| 成分 | 予測 | 根拠 |
|------|------|------|
| ... | ... | ... |

### セッションの実測

（`tokens session --markdown` の出力をそのまま貼る）

| 計測項目 | 値 |
|------|------|
| ピーク | ... |
| 開始時の固定分 | ... |
| 呼び出し回数 | ... |
| 出力トークン | ... |
| コンパクション | ... |
| ウィンドウ | ... |
| モデル | ... |
| ホスト | ... |
| Hikyaku | ... |
| セッション | ... |

### 差分の集計

（`tokens history build-{NN} --markdown` の出力をそのまま貼る）

| 差分の集計 | 値 |
|------|------|
| 新規ファイル数 | ... |
| 変更ファイル数 | ... |
| 追加行数 | ... |
| 削除行数 | ... |
| 生成物（数えていない） | ... |

## セッション中にスキル外で受けた指示

（スキルの手順に含まれていないが、ユーザーから受けた指示・修正・補足を列挙する。
　スキル外の指示がなかった場合は「なし」）

## 改善提案

### R-1: （改善タイトル）
- **状況**: （どのステップで、どんな状態のときに発生したか）
- **指示内容**: （ユーザーからどんな指示・修正・補足があったか）
- **提案**: （何をどう改善すべきか）
- **優先度**: Must / Should / Could
- **対象**: （分類から選択）
- **具体案**: （対象ファイルに追記・修正する内容の文面案）

### R-2: ...

## リポジトリ固有の学び（L-N）

（close-cycle が `learnings` へ昇格させる素材。無ければ「なし」）

### L-1: （一行で言い切れる見出し）
- **再現条件**: （「N=1000 でタイムアウトする」のように具体的に。「なんとなく遅い」は書かない）
- **影響**: （何が起きるか、どこまで波及するか）
- **回避策**: （分かっていれば）
- **判明したビルド**: build-{NN}
- **判明日**: YYYY-MM-DD

### L-2: ...
```

**「改善提案」と「リポジトリ固有の学び」を必ず分けること。** 前者は以後の取り決めで
`conventions` などか `instructions.md` へ、後者は踏んだ地雷で `learnings` へ行く。
どちらも close-cycle が読むので、節が無いと素材収集で拾うものが無くなる。

「予測ピークの振り返り」は記録であって、R-N でも L-N でもない。乖離そのものを
R-N に起こさない（見積もりの補正は close-cycle が見積もりのガイドへの昇格として扱う）。
ただし、乖離の要因がこのリポジトリ固有の再現条件に落ちる場合は L-N にも書く
（例:「このリポジトリでは型定義の変更が必ず全パッケージのテストに波及する」）。
Hikyaku の見積もり手順そのものへの提案になるなら、通常どおり R-N の `workflow` 分類に落とす。

再現条件が具体的に書けないものは L-N にしない。一般的なプログラミング知識や
「気をつける」だけの曖昧な注意も対象外。

フェーズヘッダーは呼び出し元のフェーズで決める。

| フェーズ | ヘッダー |
|---|---|
| `plan`（`planning`） | `企画フェーズ 振り返り` |
| `architect`（`design`） | `設計フェーズ 振り返り` |
| `build-{NN}` | `Build {NN}: {ビルド名} 振り返り`（issue.md からビルド名を取得） |
| `close` | `サイクル終了 振り返り` |

追記モードの場合（PRレビュー対応）: 既存の末尾に以下のセクションを追加する。R-N の番号は既存の改善提案の続きから採番する。

`build-{NN}` で「予測ピークの振り返り」が既にある場合は、節を増やさず既存の表を上書きする。
PR レビュー対応で作業が増えれば実測も変わるので、peak-actual で測り直した値（セッションの実測・
差分の集計）に差し替え、乖離と要因を書き直す（予測側の行と内訳は変えない）。

**この節の形（段階表 / セッション行 / 内訳表 / セッションの実測表 / 差分の集計表）は変えない。**
`hikyaku tokens history` が見出し名で読み、close-cycle と `/hikyaku:token-guide` がガイドを補正する素材にする。

```markdown

## PRレビュー対応の振り返り

### セッション中にスキル外で受けた指示

（なければ「なし」）

- **提案**: （何をどう改善すべきか）
- **優先度**: Must / Should / Could
- **対象**: （分類から選択）
- **具体案**: （対象ファイルに追記・修正する内容の文面案）

### リポジトリ固有の学び（L-N）

（なければ「なし」。形式は新規作成時の L-N と同じ）
```
