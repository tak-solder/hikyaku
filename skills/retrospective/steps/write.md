# write: retrospective.md の書き込みと提示

- [ ] retrospective.md を以下のテンプレートに従って作成する。出力先は directive の `値` の `output`
  （既にあれば追記モード）

新規作成の場合:

```markdown
# {フェーズヘッダー}

## BP見積もりの振り返り

（`build-{NN}` のときだけ置く。他のフェーズでは節ごと省く）

| 段階 | BP | 根拠 |
|------|----|------|
| architectフェーズ段階 | 〇BP | issue.md のスコープ記述 |
| builderフェーズ段階 | 〇BP | plan.md の内訳（下表） |
| **実績** | **〇BP** | 実測（新規ファイル数・追加行数）+ 申告（下表） |

**セッション**: （1セッションで完結 / 途中で分割（build-NN を追加）/ 〇セッション）

**乖離**: （実績 − builderフェーズ段階。乖離が 0 なら「なし」）

**乖離の要因**: （乖離があった場合のみ。**入力値の読み違え**か**基準表の問題**かを分けて書く。
　入力値: どの指標を、どちらへ、なぜ読み違えたか。例:「影響ファイル数を3と見たが実際は9で、
　共通型の変更が波及していた（加算 +0 → +3）」。
　基準表: 入力値は合っていたのに1セッションに収まらなかった（または大幅に余った）。
　乖離が無ければ「なし」）

### builderフェーズ段階の内訳

（plan.md の内訳表をそのまま転記する）

| 項目 | 値 | BP |
|------|----|----|
| ... | ... | ... |

### 実績の内訳

（`bp estimate` の出力をそのまま貼る。新規ファイル数・実装行数は `bp actual` の実測値、他は申告）

| 項目 | 値 | BP |
|------|----|----|
| ... | ... | ... |

### セッションの実測

（`bp session --markdown` の出力をそのまま貼る）

| 計測項目 | 値 |
|------|------|
| ピーク | ... |
| 開始時の固定分 | ... |
| 呼び出し回数 | ... |
| 出力トークン | ... |
| コンパクション | ... |
| ウィンドウ | ... |
| モデル | ... |
| ホスト | ... |
| Hikyaku | ... |
| セッション | ... |

## セッション中にスキル外で受けた指示

（スキルの手順に含まれていないが、ユーザーから受けた指示・修正・補足を列挙する。
　スキル外の指示がなかった場合は「なし」）

## 改善提案

### R-1: （改善タイトル）
- **状況**: （どのステップで、どんな状態のときに発生したか）
- **指示内容**: （ユーザーからどんな指示・修正・補足があったか）
- **提案**: （何をどう改善すべきか）
- **優先度**: Must / Should / Could
- **対象**: （分類から選択）
- **具体案**: （対象ファイルに追記・修正する内容の文面案）

### R-2: ...

## リポジトリ固有の学び（L-N）

（close-cycle が `learnings` へ昇格させる素材。無ければ「なし」）

### L-1: （一行で言い切れる見出し）
- **再現条件**: （「N=1000 でタイムアウトする」のように具体的に。「なんとなく遅い」は書かない）
- **影響**: （何が起きるか、どこまで波及するか）
- **回避策**: （分かっていれば）
- **判明したビルド**: build-{NN}
- **判明日**: YYYY-MM-DD

### L-2: ...
```

**「改善提案」と「リポジトリ固有の学び」を必ず分けること。** 前者は以後の取り決めで
`conventions` などか `instructions.md` へ、後者は踏んだ地雷で `learnings` へ行く。
どちらも close-cycle が読むので、節が無いと素材収集で拾うものが無くなる。

「BP見積もりの振り返り」は記録であって、R-N でも L-N でもない。乖離そのものを
R-N に起こさない（見積もりのやり直しは次のサイクルの仕事で、以後の取り決めではない）。
ただし、乖離の要因がこのリポジトリ固有の再現条件に落ちる場合は L-N にも書く
（例:「このリポジトリでは型定義の変更が必ず全パッケージのテストに波及する」）。
Hikyaku の見積もり手順そのものへの提案になるなら、通常どおり R-N の `workflow` 分類に落とす。

再現条件が具体的に書けないものは L-N にしない。一般的なプログラミング知識や
「気をつける」だけの曖昧な注意も対象外。

フェーズヘッダーは呼び出し元のフェーズで決める。

| フェーズ | ヘッダー |
|---|---|
| `plan`（`planning`） | `企画フェーズ 振り返り` |
| `architect`（`design`） | `設計フェーズ 振り返り` |
| `build-{NN}` | `Build {NN}: {ビルド名} 振り返り`（issue.md からビルド名を取得） |
| `close` | `サイクル終了 振り返り` |

追記モードの場合（PRレビュー対応）: 既存の末尾に以下のセクションを追加する。R-N の番号は既存の改善提案の続きから採番する。

`build-{NN}` で「BP見積もりの振り返り」が既にある場合は、節を増やさず既存の表を上書きする。
PR レビュー対応で実装が増えれば実績も変わるので、bp-actual で集計し直した値に差し替える
（見積もり側の行と内訳は変えない）。セッションの実測も `bp session` で測り直して差し替える。

**この節の形（段階表 / セッション行 / 2つの内訳表 / セッションの実測表）は変えない。** `hikyaku bp history` が
見出し名で読み、`/hikyaku:bp-guide` が基準表を調整する素材にする。

```markdown

## PRレビュー対応の振り返り

### セッション中にスキル外で受けた指示

（なければ「なし」）

### 改善提案

#### R-N: （改善タイトル）
- **状況**: （どのステップで、どんな状態のときに発生したか）
- **指示内容**: （ユーザーからどんな指示・修正・補足があったか）
- **提案**: （何をどう改善すべきか）
- **優先度**: Must / Should / Could
- **対象**: （分類から選択）
- **具体案**: （対象ファイルに追記・修正する内容の文面案）

### リポジトリ固有の学び（L-N）

（なければ「なし」。形式は新規作成時の L-N と同じ）
```

- [ ] 振り返りをユーザーに提示する
- [ ] `done` を報告する（retrospective.md が無ければ受け付けられない）。`done` が返ったら呼び出し元に戻る（コミットは呼び出し元が行う）
