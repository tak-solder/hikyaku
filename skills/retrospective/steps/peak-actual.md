# peak-actual: 予測ピークの実測と差分の集計

実装フェーズ（`build-{NN}`）のときだけ、step はこのステップを返す。

予測と実測を並べて記録する。見積もりの精度を上げるための素材集めであって、
見積もりの正否を裁く場ではない。どの成分を読み違えたのかが残っていれば、close-cycle が
それを見積もりのガイドの補正として昇格の候補にする。

- [ ] plan.md の「予測ピーク」から、architect フェーズ段階と builder フェーズ段階の予測ピーク、
      および builder 段階の内訳表（`tokens estimate` の出力。最後の行がガイドの版）を読む
- [ ] セッションのコンテキストを実測する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens session build-{NN} {cycle} --markdown
```

  - ビルドのブランチに対応付くセッションから本体（そのブランチでの API 呼び出しが最も多いもの）を
    選び、ピーク・開始時の固定分・呼び出し回数・出力トークン・コンパクション回数・モデル・
    ホストとその版・Hikyaku の版を表で返す。現在のセッションがそのブランチにいれば候補に入る
  - 出力の表を「セッションの実測」にそのまま貼る。値を書き換えない・丸めない
  - 「計測不可（理由）」が返ったら、その表をそのまま貼る（記録が見つからないときなど）。推測で埋めない
  - Hikyaku の欄が「—」なのは、測ったのが現在のセッションでないとき（PR レビュー対応で
    別のセッションから測った等）。分かっていても書き足さない
  - 選ばれたセッションが想定と違う（例: 本体が別プロセスのレビューになった）なら、
    `--json` の `candidates` を見て、乖離の要因と同じ段落に一文で書く

**数えるのはコマンドの仕事で、あなたの仕事ではない。** 会話の長さから概算しない。

- [ ] 差分を集計し、区切りでのコンテキストを確かめる

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens history build-{NN} {cycle}
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens history build-{NN} {cycle} --markdown
```

  - 新規ファイル数・変更ファイル数・追加行数（実装とテストの内訳）・削除行数が返る。比較の起点は `pr base` と
    同じ導出（スタックしていればスタック元）で、ワークスペース配下のワークフロー成果物と、生成物
    （ロックファイル・スナップショット・生成コード。`[diff]` で変更可）は除かれる
  - `--markdown` の表を「差分の集計」にそのまま貼る。起点を解決できず「計測不可」が返ったら、その表をそのまま貼る
  - 区切りでのコンテキスト（G8 の最初の提示・実装開始前・レビュー前の値と目安）は progress.jsonl の
    記録で、`tokens history` の一覧も同じ記録を読む。retrospective.md に書き写さない（節の形を変えないため）
  - 目安を超えたまま継続した区切りがあれば、どこで膨らんだか（G8 の差し戻しが続いた、実装で
    想定より多くのファイルを読んだ等）を「乖離の要因」に一文で書く。予測の乖離が無くても書く
  - 計測できなかった区切りは出力に出ない。推測で補わない

- [ ] このビルドが1セッションで完結したかを記録する
  - 完結 / 途中でビルドを分割した / N セッションかかった、のいずれか

- [ ] 乖離（実測ピーク − builder 段階の予測ピーク）を求め、要因を成分ごとに考える
  - どの成分を、どちらへ、なぜ読み違えたか。差分の集計（書いた量）と区切りでの値（どこで膨らんだか）が手がかり
  - 例:「読み込みを 110k と見たが、共通の型の変更が波及して呼び出し元を 20 ファイル読んだ（+90k）」
  - 例:「未知の領域を 0 にしたが、docker の環境のデバッグで 120k 使った」
