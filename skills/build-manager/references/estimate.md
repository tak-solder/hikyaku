# 予測ピークの見積もり手順

## 予測ピークとは

ビルドを1つのセッションで実装から PR まで進めたとき、メインセッションのコンテキストが
どこまで膨らむか（トークン）。1ビルドのセッションでコンパクションを起こさないことを、
ビルド設計の絶対条件にする。そのうえで、小さすぎるビルド（分割しすぎ）も避けたいので、
上限ではなく狙いの帯で判定する。

| 予測ピーク | 判定 | すること |
|----|------|------|
| `mergeBelow` 未満（既定 300k） | 統合を検討 | 推奨のみ。依存の近いビルドとまとめられないかを見る。並行して進められるビルドが減る、PR が大きくなりすぎるなら分けたままでよい |
| `mergeBelow`〜`splitAbove`（既定 300k〜450k） | 狙いの帯 | そのまま進める |
| `splitAbove` 超（既定 450k） | 分割を検討 | 原則として分割する |

帯は `.hikyaku.config` の `[context] merge_below` / `split_above`（`hikyaku config {cycle} --json` の
`peakBands`）。directive の `値` にも `mergeBelow` / `splitAbove` として入っている。

## 分担

| 誰が | 何を |
|---|---|
| あなた（LLM） | ガイドに沿って、5つの成分（固定費・読み込み・実装・テスト・未知の領域）のトークンと根拠を見積もる |
| `hikyaku tokens estimate` | 成分を合計し、帯と比べて判定し、記録の表を作る |

**合計と判定を自分でしない。** 表には、見積もりに使ったガイドの版も入る。ガイドを補正した前と後の
予測を混ぜて比べないため（`hikyaku tokens history --group-by guide`）。

## 見積もり手順

1. 有効なガイドを確かめて読む。プロジェクトのガイド（`{HIKYAKU_ROOT}/token-guide/guide.md`）があれば
   それが、無ければ標準のガイドが有効

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens guide {cycle}
```

2. 実績があれば、開始時の固定分と、予測と実測の乖離の傾向を見る（ガイドの固定費の見積もり方に使う）

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens history
```

3. ガイドの見積もり方に沿って、成分ごとのトークンと根拠を決める
   - 読むファイル・作成するファイルを名前で列挙してから数える。列挙は成果物（issue.md / plan.md）に残す
   - 該当しない成分は 0 を渡す。考えなかった成分を省かない
4. 成分と根拠を渡し、`--markdown` の内訳表をそのまま成果物に貼る。転記しない

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens estimate {cycle} \
  --fixed 90k --fixed-basis "実測の固定分 48k + 手順の進行分" \
  --reading 110k --reading-basis "design-delta.md・既存の billing/ 8ファイル・共有型" \
  --implementation 90k --implementation-basis "新規5ファイル・約600行、既存3ファイルの編集" \
  --tests 50k --tests-basis "unit 12 シナリオ" \
  --unknown 40k --unknown-basis "決済 SDK の挙動の調査" --markdown
```

ビルドが複数のワークスペース（パッケージ）にまたがっても、セッションは1つなので1回で見積もる。
ワークスペースごとの内訳は根拠に書く。

## 分割の判断（予測ピークが `splitAbove` 超）

原則として分割する。分割せずに1ビルドのまま進めてよいのは、次のどちらかに当たるときだけで、
当たる理由を issue.md の「予測ピーク」の下に書く。

- 分割したビルド間で同一ファイルの同一箇所を編集する必要があり、マージコンフリクトが避けられない
- 分割の一方がビルドとして成立しない（予測ピークが固定費とほとんど変わらない）

分割するとどちらかのビルドのマージ時点で本番データの安全を保てない場合は、自分で決めずに
build-manager の estimate の指示に従ってユーザーに尋ねる（`unsafe-split`）。

分割の軸の候補:

1. ワークスペースが分離可能 → ワークスペース単位で分割
2. 「基盤セットアップ」と「機能実装」が混在 → 分離（未知の領域が基盤側に集まることが多い）
3. 独立した画面が3つ以上 → 画面単位で分割
4. 独立したドメインが3つ以上 → ドメイン単位で分割
5. 外部連携が2つ以上 → 連携先ごとに分割

分割後の各ビルドを `tokens estimate` で見積もり直し、全ビルドが `splitAbove` 以下になるまで繰り返す。

## ガイドを直したくなったら

このビルドの見積もりの中では直さない。振り返り（retrospective）に予測と実測と乖離の要因を残し、
サイクルの終わりに close-cycle が昇格の候補として補正を提案する。サイクルをまたいで校正し直すときは
`/hikyaku:token-guide` を使う。走行中のサイクルの途中でガイドを動かすと、そのサイクルの中で予測を
比べられなくなるため。
