# Hikyaku Build Manager

対象サイクルの `tasklist.md` と各ビルドの `issue.md` を管理する。

このスキルは hikyaku:architect および hikyaku:builder からモデル呼び出しで使用される内部スキルです。
ユーザーが直接呼び出すことは想定していません。hikyaku ワークフロー以外のコンテキストから呼び出された場合は、その旨をユーザーに伝えて終了してください。

## あなたの責務

BP見積もりと分割単位の判断、issue.md の内容の作成、レビュー、ユーザー承認を行う。

`tasklist.md` の行の更新・依存グラフの再生成・循環依存の検証はスクリプトが行う。
自分で `tasklist.md` を書き換えてはいけない。

> スクリプト = 計算・解析・整形・検証
> LLM        = 判断・生成・対話

## 操作

- ビルドの追加: 新しいビルドを追加し、issue.md を作成する
- ビルドの更新: 既存ビルドのスコープ・依存関係・BPを変更する
- ビルドの分割: 「元ビルドの update + 新ビルドの add」で表現する（専用の操作は無い）

1回の呼び出しで複数の操作を組み合わせてよい。

## 作業ステップ: step に従って進める

手順（読み込み → 変更の整理 → BP見積もり → `--dry-run` → レビュー → G6 → 書き込み → 外部投影）は、
`step next` が設定と進捗から1手ずつ返す。**手順を自分で組み立てない。** どのレビューが有効か、
投影が要るかは step が決める。

呼び出し元のフェーズ（`{phase}`）の作業単位で進める。architect から呼ばれたら `architect`、
builder から呼ばれたら `build-{NN}`。呼び出し元の directive に「呼ばれたスキルの手順」があれば、
そのコマンドをそのまま使う。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" step next {phase} {cycle} --skill build-manager
```

記録は呼び出し元と同じ `progress.jsonl`（architect なら `design/`、builder なら `build-{NN}/`）に入る。
呼び出し元が最後に報告したあとの記録だけが今回の呼び出しの分になるので、呼ばれるたびに最初の手順から始まる。

| 種類 | すること |
|---|---|
| `run` | 「指示」のファイルを読み、そのとおりに行う。終えたら「報告」のコマンドを実行する |
| `gate` | 「指示」のファイルを読み、ユーザーに提示して承認を求める。答えを `approved` / `rejected` で報告する |
| `done` | 手順をすべて終えた。呼び出し元に戻り、行った変更（追加・更新したビルド）を伝える |
| `stop` | メッセージを呼び出し元に伝えて戻る |

- `step report` は記録したあと、次の1手を返す。それに従って続ける
- 報告を受け付けないとき（現在地と違うステップ）はエラーになる。メッセージに従って直す
- 前の手順に戻るとき（G6 のフィードバック、レビューの反映、依存の誤り）は、`scope` を `done` で報告し直す。
  そこから後ろ（見積もり・差分・レビュー・G6）はやり直しになる
- 呼び出し元の報告を挟まずに呼び直されたとき（同じステップの中での2回目の呼び出し。呼び出し元が
  「呼び直し」と伝える。呼ばれた直後の `step next` が `done` を返したときも同じ）は、回を区切ってから
  最初の手順で始める。中断からの再開で途中の手順が返ったときは区切らない

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" step restart {phase} {cycle} --skill build-manager --reason "<呼び直す理由>"
```

- 迷ったら `step next` を呼び直す。同じ状態なら同じ1手が返る

## 共通ルール

### buildID
- 採番はスクリプトが行う（`max(既存) + 1`）
- 既存 buildID のリナンバリングは行わない
- ディレクトリ名はゼロ埋め2桁（buildID 3 → `build-03`）

### 依存グラフ
- `tasklist.md` の dependencies 列と Mermaid グラフはスクリプトが常に一致させる
- 循環依存の検証もスクリプトが行う。検出された場合は書き込まれない

### マージ時点のデータ安全
- 原則: 各ビルドの PR をマージした時点で、既存機能に影響せず、本番でどんな操作が起きても
  データが壊れたり不整合を起こしたりしない。本番データの破壊は取り返しがつかないため
- 確かめる観点: スキーマ・保存形式の変更が後方互換か（追加 → 切り替え → 移行 → 削除の順に
  分けられるか）、旧コードと新コードが同じデータを読み書きしても壊れないか、作りかけの機能が
  利用者から到達できないか（フィーチャーフラグなど）、API の契約を破っていないか
- 例外（安全でない分割）は `unsafeSplit.allowed` が true で、かつ安全な分割が見つからないときだけ。
  base_branch の名前から自分でリリースされるかを判断しない
- 安全でない分割を使ったビルドの issue.md には「マージ時点で残る危険」を書き、
  「解消するビルド: build-NN」を必ず入れる。解消するビルドはこのビルドに依存させる
  （先にマージされると、危険が残る順序を保証できない）

### 完了済みビルドの扱い
- 完了判定は `PR` 列が非空かどうかの一点
- 完了済みビルドのスコープ・依存関係は変更しない（依存グラフの整合性が崩れるため）
