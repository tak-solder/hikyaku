# estimate: 予測ピークの見積もりと分割の判断

このステップの役割は、着手前にビルドのセッションの重さ（メインセッションのコンテキストの予測ピーク）を
予測し、根拠を issue.md に残し、分割するかを判断すること。

- [ ] `${CLAUDE_PLUGIN_ROOT}/skills/build-manager/references/estimate.md` の手順に従い、ガイドに沿って
  成分ごとのトークンと根拠を見積もり、コマンドに渡す
  - 成分は固定費・読み込み・実装・テスト・未知の領域の5つ。該当しない成分は 0 を渡す
  - 読むファイル・作成するファイルは、issue.md のスコープ記述と設計ドキュメントから名前で列挙してから数える

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" tokens estimate {cycle} \
  --fixed 90k --reading 110k --implementation 90k --tests 50k --unknown 40k \
  --reading-basis "..." --implementation-basis "..." --markdown
```

  - 合計と判定はコマンドが行う。自分で足して判定しない
  - 出力の内訳表（`--markdown`）を issue.md の「予測ピーク」にそのまま貼る。
    転記しないのは、レビューが成分を検証するときに根拠が要り、最後の行のガイドの版を振り返りが読むため
  - tasklist の `--peak` には、出力の予測ピークを渡す
- [ ] 判定が「分割を検討」（値 `splitAbove` 超）なら、原則として分割する。次のどちらかに当たる場合のみ、
  分割せずに1ビルドのまま進めてよい。当たる理由を issue.md の「予測ピーク」の下に書く
  - 分割したビルド間で同一ファイルの同一箇所を編集する必要があり、マージコンフリクトが避けられない
  - 分割の一方がビルドとして成立しない（予測ピークが固定費とほとんど変わらない）
- [ ] 判定が「分割を検討」で、マージ時点のデータ安全を保つ分割が見つからない場合は、自分で決めずに止まり、
  ユーザーに尋ねる（ask: unsafe-split）。次の選択肢を、どこで安全が崩れるかの説明とともに示す
  1. `splitAbove` を超えたまま1ビルドにまとめる
  2. 設計に戻り、移行の段階（フィーチャーフラグ、新旧の並行稼働など）を足す（architect の設計に関する質問へ）
  3. 安全でない分割を使う — `unsafeSplit.allowed` が true のときだけ示す。false のときは、
     示さずに `unsafeSplit.message` を添える
- [ ] 判定が「統合を検討」（値 `mergeBelow` 未満）なら、依存の近いビルドとまとめられないかを見る。
  推奨のみで、並行して進められるビルドが減る、PR が大きくなりすぎるなら分けたままでよい。
  まとめるかどうかを G6 の提示に一言添える

`unsafeSplit.allowed` が true でも、安全でない分割は選択肢の1つにすぎない。安全な分割が
見つかるなら、そちらを選ぶ。

分割や統合で範囲が変わったら `scope` を `done` で報告し直してから見積もり直す。
