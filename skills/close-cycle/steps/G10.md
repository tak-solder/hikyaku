# G10: 候補の整理と、昇格の承認

集めた候補を整理し、何を足し・置き換え・消すかを提示して承認を得る（G10）。

承認の種類は directive の `approval` にある。`decisions`・`constraints` の変更（宛先がそれらの候補、
または作業ツリーの差分。`args.consentChanges`）があれば同意で、どのプロファイルでも省かれない。
無ければ確認で、`promotion_gate` が off（express）なら G10 は手順に現れず、write が整理を行う。
このサイクルの ADR を `accepted` から `implemented` にするだけの書き換えは、同意に数えない。

`args.returned` が true なら、書き込みの途中で同意が要る差分が出て戻った回。`args.consentChanges` の
差分を示し、同意として承認を取り直す。`args.consentProblem` があれば、差分を確かめられなかったので
同意の側に倒している。理由を添えて示す。

候補が会話の中に無ければ（セッションが切れて再開した場合）、`hikyaku promotions {cycle}` を
実行し直して整理からやり直す。候補はスクリプトで再現できる。

## 整理

基準は `${CLAUDE_PLUGIN_ROOT}/skills/close-cycle/references/persistence.md`（[persistence.md](../references/persistence.md)）。

- [ ] 重複を束ねる。同じ知見が複数のビルド・フェーズから出ていたら1件にし、出どころを全部残す。
  挙がった回数は根拠になる（スキルは2回以上で候補にする）
- [ ] マージ済みのコードと照合する
  - 既に機械で防がれている（テスト・ヘルパー・設定が入った）ものは落とす
  - 後のビルドで事実でなくなったものは落とす。design-delta.md の更新予定も、実装の結果と違っていれば直す
  - ビルドが `済` で控えた rule は書き直さない。似た rule が複数あれば束ねる対象にする
- [ ] 重要度を見直す。低に当たるものは落とす。中で、機械で防げず狭い rule にもできないものも落とす
- [ ] 置き場を確かめる
  - 論理名は `document-guide.md` が正。「対象外」の論理名へは昇格させない。「未作成」なら新規作成に
    なるので、その旨を併せて承認を得る
  - `overview` にテーブル一覧・エンドポイント一覧・依存パッケージの版を書かない。正の所在へのポインタを書く
  - `constraints` に実現方法を書かない（それは ADR か `overview`）
  - `conventions` に、一部のファイルにしか効かない注意を入れない（それは rule）
  - `workflow` に、このリポジトリに固有でないことを書かない
- [ ] 「役に立たなかった記述」を理由ごとに扱う
  - `古い`: コードと照合し、食い違っていれば削除か置き換えにする
  - `自明`: 削除にする。ただし成果物に害が残る種類（重要度が高）の記述は消さない
  - `無関係`: 消さない。複数のビルドで挙がったら、rule の glob を狭めるか、ファイルを分ける
- [ ] `rules candidates` の移す候補は、機械の検査かリファクタへ移すかを、日数と理由を見て決めて提示する
  （移すならこのサイクルの記録を根拠にした rule の削除と、`refactor` の提案。このサイクルで直せない検査は提案に回す）。
  一致しない rule は、glob を追従させるか消すかを提示する
- [ ] `rules candidates` の試しに消す候補（`removals`）から、試しに消すものを選んで「試しに消す（別の PR）」に並べる。
  close の PR では消さない（followups が別の PR にし、マージ前後の指標で戻せるようにする）。重要度が高の基準は候補に入らない
- [ ] 宛先 `refactor` の候補は文書に書かず、「リファクタの提案」として示す
- [ ] 削除・置き換えの範囲を守る。提案できるのは、このサイクルの記録に根拠があるものと、
  このサイクルのビルドが書いた rule だけ。それ以外で気づいた点は、手を入れずに PR の本文に書く
- [ ] ADR を整理する。このサイクルで実装された `accepted` は `implemented` にする。覆された判断は
  旧エントリを `superseded` にし、新エントリを起こす（本文は書き換えない）。`repo` 管理の ADR に
  status 欄が無くて実装状態が分からない場合は、勝手に欄を足さずユーザーに提案して判断を仰ぐ（ask: adr-status）

`repo` 管理のドキュメントには形式を強制しない。既存の形式に合わせて書く。

## 提示

- [ ] 「同意が要る変更」（`decisions`・`constraints`）と「確認の変更」（それ以外）を分けて示す。`args.consentChanges` は
  すべて同意の側に並べる（ADR の `accepted → implemented` だけなら確認の側）
- [ ] 置き場ごとに、追加（`+`）・置き換え（`~`）・削除（`-`）を分けて示す。根拠（出どころ）を添える
  - 出どころは個別に並べる。件数（「2件」）や ID の範囲（「build-01〜05」）に畳まない。書き込む文書にも件数を写さない

```

constraints:
  + [高] 請求 API は 1 分あたり 100 件まで（build-03）

ADR:
  ~ 20260601-sync-notify.md: accepted → superseded、20261020-queue-notify.md を新しく起こす（build-04 で覆った）

■ 確認の変更

overview:
  + 「請求」: 請求は API → キュー → ワーカーの順で処理される（design-delta / build-02）

conventions（AGENTS.md）:
  + [中] マイグレーションは 1 PR 1 ファイルに保つ（design・build-02 の振り返り）

  ~ .claude/rules/billing-tests.md と billing-batch.md を1つに束ねる（build-03・build-04 が同じ glob に書いた）
  ~ .claude/rules/backend.md「テレメトリ」を別ファイルに分ける（無関係: build-01・build-02・build-05）

リファクタの提案（なくす。PR の本文に載せるだけで、コードは直さない）:
  - 日付の整形を formatDate に寄せれば、表示ごとの書式の規約が要らなくなる（build-02・build-04）

  - 「invoices テーブルを追加」→ マイグレーションが正のため書かない
  - 「テストは1ファイル1クラス」→ conventions に既に同じ記述がある
  - 「型検査の前に生成コマンドを実行する」→ このサイクルでスクリプトに組み込まれた（機械で防がれている）
```

- [ ] 期限が来た・過ぎた未決事項（collect の `ledger list`）を、候補とは別に「未決事項」として並べ、
  それぞれをどう決めるかをユーザーに尋ねる
- [ ] 承認の `--input` には、承認した範囲が分かるように書く。試しに消すと決まった基準は名前を並べる
  （followups が `args.g10Input` からその範囲を読む）
- [ ] 承認を報告したら、未決事項ごとにユーザーの答えを記録する。AI の別フェーズの事項も、付け替えずに
  ユーザーの決定として記録する

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" ledger decide close <ID> {cycle} --decision <decided|consented|rejected> --by user --input "<ユーザーの答え>"
```
- [ ] フィードバックがあれば、候補を直してから提示し直す
