# G10: 候補の整理と、昇格の承認

集めた候補を整理し、何を足し・置き換え・消すかを提示して承認を得る（G10）。
取捨選択は人間の判断なので、どのプロファイルでも省かない。

候補が会話の中に無ければ（セッションが切れて再開した場合）、`hikyaku promotions {cycle}` を
実行し直して整理からやり直す。候補はスクリプトで再現できる。

## 整理

基準は `${CLAUDE_PLUGIN_ROOT}/skills/close-cycle/references/persistence.md`（[persistence.md](../references/persistence.md)）。

- [ ] 重複を束ねる。同じ知見が複数のビルド・フェーズから出ていたら1件にし、出どころを全部残す。
  挙がった回数は根拠になる（スキルは2回以上で候補にする）
- [ ] マージ済みのコードと照合する
  - 既に機械で防がれている（テスト・ヘルパー・設定が入った）ものは落とす
  - 後のビルドで事実でなくなったものは落とす。design-delta.md の更新予定も、実装の結果と違っていれば直す
  - ビルドが `済` で控えた rule は書き直さない。似た rule が複数あれば束ねる対象にする
- [ ] 重要度を見直す。低に当たるものは落とす。中で、機械で防げず狭い rule にもできないものも落とす
- [ ] 置き場を確かめる
  - 論理名は `document-guide.md` が正。「対象外」の論理名へは昇格させない。「未作成」なら新規作成に
    なるので、その旨を併せて承認を得る
  - `overview` にテーブル一覧・エンドポイント一覧・依存パッケージの版を書かない。正の所在へのポインタを書く
  - `constraints` に実現方法を書かない（それは ADR か `overview`）
  - `conventions` に、一部のファイルにしか効かない注意を入れない（それは rule）
  - `workflow` に、このリポジトリに固有でないことを書かない
- [ ] 「役に立たなかった記述」を理由ごとに扱う
  - `古い`: コードと照合し、食い違っていれば削除か置き換えにする
  - `自明`: 削除にする。ただし成果物に害が残る種類（重要度が高）の記述は消さない
  - `無関係`: 消さない。複数のビルドで挙がったら、rule の glob を狭めるか、ファイルを分ける
- [ ] 削除・置き換えの範囲を守る。提案できるのは、このサイクルの記録に根拠があるものと、
  このサイクルのビルドが書いた rule だけ。それ以外で気づいた点は、手を入れずに PR の本文に書く
- [ ] ADR を整理する。このサイクルで実装された `accepted` は `implemented` にする。覆された判断は
  旧エントリを `superseded` にし、新エントリを起こす（本文は書き換えない）。`repo` 管理の ADR に
  status 欄が無くて実装状態が分からない場合は、勝手に欄を足さずユーザーに提案して判断を仰ぐ（ask: adr-status）

`repo` 管理のドキュメントには形式を強制しない。既存の形式に合わせて書く。

## 提示

- [ ] 置き場ごとに、追加（`+`）・置き換え（`~`）・削除（`-`）を分けて示す。根拠（出どころ）を添える

```
overview:
  + 「請求」: 請求は API → キュー → ワーカーの順で処理される（design-delta / build-02）
  ~ 「通知」: 「同期で送る」→「キュー経由で送る」（build-04 で変更）

constraints:
  + [高] 請求 API は 1 分あたり 100 件まで（build-03）

conventions（AGENTS.md）:
  + [中] マイグレーションは 1 PR 1 ファイルに保つ（design・build-02 の振り返り、2件）
  - 「DTO の fixture は3ファイルを直す」: 自明（build-02・build-05 の振り返り、2件）

rules:
  ~ .claude/rules/billing-tests.md と billing-batch.md を1つに束ねる（build-03・build-04 が同じ glob に書いた）
  ~ .claude/rules/backend.md「テレメトリ」を別ファイルに分ける（無関係 3件: build-01・02・05）

スキル:
  + release-db: 破壊的な移行の公開手順（build-02 と build-05 で同じ手順）

instructions.md:
  + [中] 環境変数を足したら .env.example にも同じキーを足す（build-01 の振り返り）

ADR:
  ~ 20260825-payment-provider.md: accepted → implemented

フック（別の PR にする）:
  + .env の編集を止める（build-01・build-03 で2回、誤って編集しかけた）

Hikyaku への報告（PR の本文に載せるだけ）:
  - tasklist add --dry-run が相互依存を評価できない

採らないもの（参考）:
  - 「invoices テーブルを追加」→ マイグレーションが正のため書かない
  - 「テストは1ファイル1クラス」→ conventions に既に同じ記述がある
  - 「型検査の前に生成コマンドを実行する」→ このサイクルでスクリプトに組み込まれた（機械で防がれている）
```

- [ ] 承認の `--input` には、承認した範囲が分かるように書く
- [ ] フィードバックがあれば、候補を直してから提示し直す
