# constraints のテンプレート（`hikyaku` 管理の場合）

`constraints` は設計を縛る条件（性能・可用性・セキュリティ・互換性・外部サービスの上限）を書く。
実現方法は書かない（それは ADR か `overview`）。`repo` 管理の場合はこのテンプレートを使わず、既存形式に合わせる。

1つのファイルに、制約ごとに `##` の見出しで項目を並べる。

```markdown
# 制約

## （制約の要約）

- **制約**: （守る条件。数値があれば数値で）
- **外の前提**:
  - （この制約が立つリポジトリの外の事実か仮定）（事実|仮定。確かめた出どころ、YYYY-MM-DD 確認）
- **受け入れたこと**:
  - （この制約のために受け入れたこと）（拠り所: `<前提の参照>`）
- **再評価条件**: （この制約を見直す出来事）
- **領域**: `<glob>`, `<glob>`（任意）
```

**記載ガイドライン:**
- 欄の順は上のとおり。前提・制約・受け入れたこと・再評価条件を混ぜずに、それぞれの欄に書く
- 「外の前提」は1件1行で、事実か仮定かと確かめた日を書く。無ければ「なし」
- 「受け入れたこと」は1件1行の箇条書き。外の前提を拠り所にする行は、行末を `（拠り所: \`<前提の参照>\`）` で終える
  （複数ならカンマ区切り）。参照の書式は ADR と同じ（`${CLAUDE_PLUGIN_ROOT}/skills/architect/references/templates.md` の「ADR」）。
  拠り所にする外の前提が無い行には付けない。宣言を変える PR で `hikyaku ledger premises` がこの行を読み、
  見直しの対象として示す。書式の崩れた行は `hikyaku validate` が警告する
- 「領域」は、この制約が効くパス（glob）。任意で、項目ごとに最後の欄に1行、バッククォートで囲んだ glob をカンマ区切りで並べる
- 外の前提と受け入れたことは、ユーザーの同意（G10）なしに書き換えたり消したりしない
