# 知見の永続化: 重要度と置き場

実装や振り返りで得た知見を、残すか・どこに置くかを決める基準。builder・retrospective・close-cycle・
doc-triager が同じ基準で判定する。基準の正はこのファイルだけで、各スキルの手順には写さない。

置き場は「いつ読み込まれるか」で選ぶ。読まれる頻度が、その知見が使われる頻度を上回る置き場には載せない。

## 1. 重要度を決める

害がどこに出るかで決める。

| 重要度 | 害が出る場所 | 判定 |
|---|---|---|
| 高 | 成果物 | テストも lint も通ったまま、誤りが成果物に残る。本番でだけ壊れる。情報が漏れる・データが壊れる。エラーメッセージに素直に従うと誤った修正になる |
| 中 | セッション | 失敗として気づけるので成果物は守られるが、原因の特定や正しい直し方に時間がかかり（目安30分以上）、今後も起きる見込みがある |
| 低 | ほぼ無し | すぐ失敗して、メッセージや数分の調査で直せる。一般的な知識。一回限りの事象 |

- 「既に直っているか」ではなく「次に同じ種類のものを足す人が踏むか」で判定する。既存の箇所が正しく
  書かれていても、新しいテスト・新しいコマンドを足す人が同じ罠を踏むなら、防がれていない
- 同じ落とし穴を複数のビルドが踏んでいたら、今後も起きる見込みの根拠になる。回数を添える
- **低は、どの置き場にも書かない。** 高は必ず残す。中は下の表の 1〜2 に当てはまるときだけ残す
  （機械で防げず、狭い rule にもできない中は書かない。rule を読むコストが、守りたいセッションの
  コストを上回るため）

## 2. 置き場を選ぶ

上から順に当てはめ、最初に合ったものを使う。

| 順 | 知見の性質 | 置き場 | 読み込まれるとき | 書く人 |
|---|---|---|---|---|
| 1 | 機械で防げる | コード: lint ルール・テスト・型・共通ヘルパー・スクリプト・設定。回避のために入れた実装の理由は、その場のコメント | 読まれない（違反したときに落ちる） | builder（そのビルドの PR） |
| 2 | 一部のファイル群を触るときだけ効く | パス指定の rule（`.claude/rules/`） | 一致するファイルを読み書きしたとき | builder（そのビルドの PR） |
| 3 | 決まった手順を踏む作業 | スキル（`.claude/skills/`）。既存の手順書があればそこ | 説明文は常時、本文は起動時 | close-cycle |
| 4 | Hikyaku の進め方への、このリポジトリ固有の指示 | `workflow`（`{HIKYAKU_ROOT}/instructions.md`） | Hikyaku の各フェーズ | close-cycle |
| 5 | リポジトリのどの領域を触るセッションでも、知らないと一貫性を壊す取り決め | `conventions` | 常時 | close-cycle |
| 6 | 構造・設計判断・設計を縛る条件 | `overview` / `decisions` / `constraints` | architect が読み、ビルドには必要な節だけを渡す | close-cycle（ADR の追記は architect） |
| 7 | エージェントの操作そのものを止める・補う必要がある | フック（`.claude/settings.json`） | 読まれない（操作のたびに実行される） | close-cycle が別ブランチの PR にする |

判定の補足:

- **1 が直せないとき**: そのビルドで直す。スコープを超えるなら 2 に仮置きし、handoff の「残したこと」に
  何を入れれば防げるかを書く
- **2 と 5 の境目**: リポジトリ全体に効くなら 5。サブプロジェクト（`backend/` など）以下に絞れるなら 2
- **2 と 6 の境目**: 設計を決めるときに要るなら 6。ファイルを触るときに要るなら 2
- **lint が検出するもの**: メッセージから正しい直し方が分かるなら書かない（低）。分からない、または
  従うと誤修正になるなら 2
- **1項目に複数の罠が入っていたら分ける。** 罠ごとに重要度と置き場が違う

リポジトリに書かないもの:

- **個人の実行環境に固有の事象**（そのマシンのスリープ、サンドボックスの書き込み範囲、署名の設定）。
  各自の設定（`CLAUDE.local.md` など）の領分
- **Hikyaku 自体の不具合や制約**。宛先を `upstream` として記録し、close-cycle が PR の本文に並べる
- **期限のある情報**（一度きりのリリース手順）。handoff に残れば足りる
- **既存文書の誤りを補う注記**。注記を足さず、元の文書の置き換えを提案する

## 3. rule の書き方（builder）

- **glob ごとにファイルを分ける。** 既存の広い rule（`backend/**` など）には追記しない。対象の glob に
  合うファイルがあればそこへ、無ければ新しく作る。広いファイルに足すと、関係ない作業でも毎回読み込まれる
- frontmatter は `paths` だけを書く。YAML のリストで、ブレース展開が使える

```markdown
---
paths:
  - "backend/tests/**/*MigrationTest.php"
  - "backend/database/migrations/**"
---

# migration のテスト

- （再現条件。どうなるか。どう避けるか。を2〜3文で）
```

- **1件を2〜3文で書く。** 再現条件 → 起きること → 回避策。経緯や検証の手順は書かず、既存の文書が
  あればパスで指す
- glob は、その知見が効く範囲に合わせて狭く取る。内容で決まる条件（「モックを使うテスト」など）は
  glob で切れないので、広い glob に短く書くか、1 に倒す
- 書いたら `hikyaku rules check` で広さと大きさを確かめる。警告が出たら glob を狭めるか分ける
- 書いた rule は handoff の「永続化すること」に `済` を付けて1行で控える（close-cycle が束ねるため）

## 4. 記録の書式

handoff.md と retrospective.md は、同じ見出しと行の形で書く。`hikyaku promotions` が見出しと行頭を
読むので、形を変えない。該当が無ければ節に「なし」と書く。

### 永続化すること

```markdown
## 永続化すること

- `constraints` [高]: 請求 API は 1 分あたり 100 件まで。バッチの間隔はここから決める（build-03 で 429 を確認）
- `conventions` [中]: マイグレーションは 1 PR 1 ファイルに保つ（ユーザーの指示）
- `skill:release-db` [中]: 破壊的な移行の公開手順（build-02 と build-05 で同じ手順を踏んだ）
- `rule:.claude/rules/billing-tests.md` [高] 済: 請求バッチのテストは並列で実行すると通ってしまう
- `upstream`: tasklist add --dry-run が相互依存を評価できない
```

- 宛先: `overview` / `decisions` / `constraints` / `conventions` / `glossary`（`document-guide.md` の論理名）、
  `workflow`、`skill:<名前>`、`rule:<rule ファイルのパスか glob>`、`hook`、`upstream`
- 重要度: `[高]` か `[中]`。低は書かない。`upstream` には付けない
- `済`: そのビルドの PR で既に書いたもの（rule）。close-cycle は書き直さず、束ねる・見直す対象にする
- 本文: そのまま置き場に書ける文面と、根拠を括弧で。1件1行（続きは字下げして書く）
- `decisions` は、覆した ADR と理由を書く。close-cycle が旧 ADR を superseded にして新しく起こす
- スキルは、同じ手順が2回以上出たときだけ書く。回数と場所を根拠に添える

### 役に立たなかった記述

読み込まれた・読んだ記述のうち、このセッションで役に立たなかったもの。振り返り（retrospective.md）に書く。

```markdown
## 役に立たなかった記述

- `AGENTS.md`「抽出 API の例外」: 古い（該当のルートが既に無い）
- `rule:.claude/rules/backend.md`「テレメトリ」: 無関係（今回触ったのは migration だけ）
- `conventions`「DTO の fixture」: 自明（型検査が場所を示す）
```

- 場所: 論理名、ファイルのパス、`rule:<rule ファイルのパス>` のいずれか。鉤括弧に見出しか冒頭の数語
- 理由は3つから選ぶ
  - `古い` — コードや他の記述と食い違っている。何と食い違うかを括弧に書く
  - `自明` — 知らなくても、すぐ気づいて直せた
  - `無関係` — 読み込まれたが、今回触った範囲に関係がなかった
- 「今回は使わなかった」だけでは書かない。`無関係` は、触ったファイルに対して読み込まれる範囲が
  広すぎるときに書く（close-cycle は消さず、glob を狭める材料にする）

## 5. close-cycle での扱い

- 集めた「永続化すること」は、重複を束ねて出どころを全部残す。回数は根拠になる
- マージ済みのコードと照合し、既に機械で防がれているもの・事実でなくなったものを落とす
- 「役に立たなかった記述」は理由ごとに扱う
  - `古い`: コードと照合して、削除か置き換えを提案する
  - `自明`: 削除を提案する。ただし重要度が高（成果物に害が残る種類）の記述は、踏まなかったセッションには
    役に立たなかったように見えるだけなので、消さない
  - `無関係`: 消さない。複数のビルドで挙がったら、glob を狭めるか、ファイルを分けることを提案する
- 削除・置き換えを提案できるのは、このサイクルの記録（handoff・振り返り）に根拠があるものと、
  このサイクルのビルドが書いた rule だけ。根拠の無い記述には手を入れず、気づいた点は PR の本文に書く
- ADR の本文は書き換えない。覆すときは旧エントリを superseded にして新しく起こす
