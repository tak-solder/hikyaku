## user-stories.md

```markdown
# ユーザーストーリー

## 概要

### 実現したいこと

（ユーザーが何ができるようになる機能か）

### 背景・目的

（なぜこの機能が必要か。解決したい課題など）

### 対象画面・対象データ

（どの画面・どのデータに関わるか。例: セッション一覧、種目マスタ、プロフィール等）

### 制約・要件

（あれば。例: モバイル優先、オフライン対応、既存データとの互換性など。なければ「特になし」）

## スコープ外

（このサイクルでやらないと決めたことと、その理由。なければ「なし」）

- （やらないこと）— （理由。別サイクルで扱う / 要件から外した 等）

## US-1: （ストーリー名）

**ユーザー**: （誰が）
**目的**: （何のために）
**操作**: （何をする）
**優先度**: Must / Should / Could
**受け入れ基準**:
- [ ] US-1.1: （条件1）
- [ ] US-1.2: （条件2）

## US-2: （ストーリー名）

...
```

**記載ガイドライン:**
- 「概要」は Step 3 のすり合わせ内容を反映したもの。インプットから読み取れない点を補完した場合は **「（推測）」** を付記する
- 優先度は MoSCoW法（Must / Should / Could）で分類する。Won't に当たるものはストーリーにせず「スコープ外」に書く
- 「スコープ外」には、すり合わせや質問の中でやらないと決めたことを理由とともに残す。architect の過剰設計の判定と、issue.md の「やらないこと」の根拠になる
- 受け入れ基準はユーザー視点で記述する（実装の詳細は含めない）
- 受け入れ基準には `US-{ストーリー番号}.{連番}` の番号を振る。行の先頭（チェックボックスの直後）に置き、一度振った番号は振り直さない（後続フェーズの issue.md と test-spec.md が番号で参照し、`hikyaku validate` が割り当て漏れを検査する）
