# BUILDフェーズ テンプレート集

## plan.md（実装計画）

issue.md のスコープ定義・受け入れ基準をソースオブトゥルースとし、plan.md では実装固有の情報のみ記載する。

```markdown
# Build {NN}: {ビルド名}

## 依存パッケージ

| パッケージ | 用途 | 備考 |
|-----------|------|------|
| `package-name` | 用途の説明 | 新規追加 / バージョンアップ等 |

（新規追加・変更がなければ「なし」）

## クラス設計

（メソッドシグネチャを含む。既存のものは差分のみ記載）

## 非機能要件

- **セキュリティ**: （認証・認可・入力バリデーション・SQLインジェクション対策等）
- **パフォーマンス**: （N+1防止・ページネーション・キャッシュ等）
- **エラーハンドリング**: （エラー種別・ユーザーへの表示方針等）
- **マージ時点のデータ安全**: （マージ直後の本番で既存データ・既存機能が壊れない根拠。後方互換なスキーマ変更、フィーチャーフラグ等。issue.md に「マージ時点で残る危険」があれば、その範囲を超えないこと）

（該当しない項目は省略）

## 予測ピーク

| 段階 | 予測ピーク |
|------|------------|
| architectフェーズ段階 | 〇k（tasklist.md の値をそのまま転記） |
| builderフェーズ段階 | 〇k |

**読むファイル**（読み込みの根拠。名前で列挙する）

- `design/design-delta.md` の「…」
- `src/.../bar.ts`（約 〇 行）

**作成するファイル**（実装・テストの根拠。名前で列挙する）

- `src/.../foo.ts`（約 〇 行）
- `src/.../foo.test.ts`（約 〇 行）

**builderフェーズ段階の内訳**（`hikyaku tokens estimate {cycle} ... --markdown` の出力をそのまま貼る）

| 成分 | 予測 | 根拠 |
|------|------|------|
| ... | ... | ... |

見積もり直した予測ピークが `split_above`（既定 450k）を超えた場合は、step が build-manager による
分割の検討を返す

## 実装ステップ

- [ ] Step 1: ...
- [ ] Step 2: ...
- [ ] Step 3: ...
- [ ] Step N: ローカル検証（lint / typecheck / test / build）
```

## questions.md（ビルド固有の質問）

実装計画の作成中に判断できない点があれば、このファイルを作成してユーザーに質問する。

```markdown
# Build {NN}: {ビルド名} 質問

## Q1: （質問内容）
**回答**:

## Q2: （質問内容）
**回答**:
```

## handoff.md（申し送り）

後続ビルドのセッションと close-cycle が読む。書くのは、PR の diff を読んでも分からないことだけ。
実装内容の要約は PR 本文、公開インターフェースはコード、環境変数やマイグレーションは diff が正なので、
ここには写さない。各節は該当が無ければ「なし」と書き、節は省かない。

```markdown
# Build {NN}: {ビルド名} 申し送り

## 後続ビルドが前提にすること

（diff を読んでも分からないことだけ。採った判断とその理由、design-delta.md の予定から変えた点、
　使い方に罠があるインターフェース、diff に現れない手作業）

## 残したこと

（スコープ外として残した作業、コードレビューで「そのまま進める」とした指摘、機械で防げるのに
　このビルドでは入れられなかった対策。扱うビルドが決まっていれば番号を書く）

## 永続化すること

（close-cycle が反映する。1件1行で、宛先・重要度・そのまま書ける文面・根拠を書く。
　このビルドの PR で書いた rule は `済` を付けて控える）

- `constraints` [高]: （文面）（根拠）
- `rule:.claude/rules/{名前}.md` [中] 済: （一行の要約）
```

「永続化すること」の宛先・重要度・行の形は
`${CLAUDE_PLUGIN_ROOT}/skills/close-cycle/references/persistence.md` の「記録の書式」に従う。
`hikyaku promotions` が見出しと行頭を読むので、形を変えない。

## return.md（architect への差し戻し）

`cycles/{cycle}/return.md` に置く（ビルドのディレクトリではなくサイクル直下）。差し戻し元のビルドのブランチにだけコミットし、デフォルトブランチにはマージしない。architect が再設計の最後に削除する。

**1行目の見出しは書式を変えない。** `cycle status` がこの見出しから差し戻し元のビルドを読む。

```markdown
# 差し戻し: build-{NN}

## 何が崩れたか

（どの設計記述と、どの要件・事実が両立しないか。根拠のファイルと箇所を挙げる）

## architect で決め直すこと

- （再設計で決める必要のある論点。選択肢が見えていれば併記する）

## このビルドの状態

- 進んだところ: （plan.md / test-spec.md / 実装の有無。どこまでコミット済みか）
- 作り直しが要るもの: （再設計の後に捨てるべき成果物）
```
