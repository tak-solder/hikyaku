# BUILDフェーズ テンプレート集

## plan.md（実装計画）

issue.md のスコープ定義・受け入れ基準をソースオブトゥルースとし、plan.md では実装固有の情報のみ記載する。

```markdown
# Build {NN}: {ビルド名}

## 依存パッケージ

| パッケージ | 用途 | 備考 |
|-----------|------|------|
| `package-name` | 用途の説明 | 新規追加 / バージョンアップ等 |

（新規追加・変更がなければ「なし」）

## クラス設計

（メソッドシグネチャを含む。`interfaces` が登録されていれば、そこに定義済みのものは差分のみ記載）

## 非機能要件

- **セキュリティ**: （認証・認可・入力バリデーション・SQLインジェクション対策等）
- **パフォーマンス**: （N+1防止・ページネーション・キャッシュ等）
- **エラーハンドリング**: （エラー種別・ユーザーへの表示方針等）

（該当しない項目は省略）

## BP見積もり

| 段階 | BP |
|------|----|
| architectフェーズ段階 | 〇BP（tasklist.md の値をそのまま転記） |
| builderフェーズ段階 | 〇BP |

**作成するファイル**（新規ファイル数・実装行数の根拠。名前で列挙する）

- `src/.../foo.ts`（約 〇 行）
- `src/.../foo.test.ts`（約 〇 行）

**builderフェーズ段階の内訳**（`hikyaku bp estimate {cycle} ... --markdown` の出力をそのまま貼る）

| 項目 | 値 | BP |
|------|----|----|
| ... | ... | ... |

（複数ワークスペースにまたがる場合はワークスペースごとに `--workspace` 付きで実行し、表を並べて合計を書く）

見積結果が `bp_max − 2`（既定の `bp_max = 8` なら 6）以上となった場合、
`/hikyaku:build-manager {cycle}` を呼び出してビルド分割を検討すること

## 実装ステップ

- [ ] Step 1: ...
- [ ] Step 2: ...
- [ ] Step 3: ...
- [ ] Step N: ローカル検証（lint / typecheck / test / build）
```

## questions.md（ビルド固有の質問）

実装計画の作成中に判断できない点があれば、このファイルを作成してユーザーに質問する。

```markdown
# Build {NN}: {ビルド名} 質問

## Q1: （質問内容）
**回答**:

## Q2: （質問内容）
**回答**:
```

## handoff.md（申し送り）

前半は後続ビルドのセッションがコンテキストを復元するため、後半は close-cycle が永続ドキュメントへ昇格させる素材として読む。design-delta.md や永続ドキュメントに反映済みの情報は重複して書かない。各節は該当が無ければ「なし」と書き、節は省かない。

```markdown
# Build {NN}: {ビルド名} 申し送り

## 後続ビルド向け

### 実装内容の要約

（このビルドで何を作ったかを数行で。対応した受け入れ基準の番号も添える）

### 公開インターフェース

（後続ビルドが使うもの。永続ドキュメントの `interfaces` に既にあるものは省き、差分・補足だけを書く）

- `ClassName.method(args): ReturnType` — 用途・補足

### 実装中の判断

（ADR にするほどではないが、後続ビルドが前提にする判断。例: エラー型を `Result` で返すことにした）

### 環境変更

（新しい環境変数、DBマイグレーション、設定ファイルの追加等）

### 意図的に残した未対応

（スコープ外として残したこと、コードレビューで「そのまま進める」とした指摘。後続ビルドや新ビルドで扱うなら、その旨も書く）

## 昇格素材（close-cycle 向け）

### overview への影響

（責務・境界・データフローの変化。design-delta.md の予定と違った点を中心に）

### 新たな制約

（実装中に判明した、数値や条件で書ける制約。constraints へ昇格する）

### 踏んだ落とし穴

（再現条件が明確なもの。learnings へ昇格する。「気をつける」だけの注意は書かない）

### 覆した設計判断

（覆した ADR、理由、影響範囲。close-cycle が旧 ADR を superseded にし、新しいエントリを起こす）
```

## return.md（architect への差し戻し）

`cycles/{cycle}/return.md` に置く（ビルドのディレクトリではなくサイクル直下）。差し戻し元のビルドのブランチにだけコミットし、デフォルトブランチにはマージしない。architect が再設計の最後に削除する。

**1行目の見出しは書式を変えない。** `cycle status` がこの見出しから差し戻し元のビルドを読む。

```markdown
# 差し戻し: build-{NN}

## 何が崩れたか

（どの設計記述と、どの要件・事実が両立しないか。根拠のファイルと箇所を挙げる）

## architect で決め直すこと

- （再設計で決める必要のある論点。選択肢が見えていれば併記する）

## このビルドの状態

- 進んだところ: （plan.md / test-spec.md / 実装の有無。どこまでコミット済みか）
- 作り直しが要るもの: （再設計の後に捨てるべき成果物）
```
