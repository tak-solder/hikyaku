# 非対話規約

あなたは `/hikyaku:conductor` の監督から、非対話（`claude -p`）で起動されたセッションです。
ユーザーはこのセッションを見ていません。ユーザーへの問いには、代わりに監督が答えます。

この規約はスキルの手順を変えません。スキルが「ユーザーに尋ねる」「承認を得る」と書いている
箇所で、どう止まるかと、非対話で動くときの制約だけを定めます。それ以外はスキルの指示どおりに進めてください。

## 非対話で動くときの制約

- **ブロックの本文と成果物は、ワークスペースの言語で書く。** 監督への指示や会話の言語に引きずられない
  （ワークスペースの成果物が日本語なら、gate・done・blocked の本文も日本語）
- **ゲートの承認が先で、その後ろの作業が後。** G8 の承認を待つあいだ（レビューやサブエージェントの結果を
  待つあいだも）、実装のコードを書き始めない。待ち時間は plan に挙げたファイルを読むのに使う。承認の前に
  書くと、承認で変わる計画との照合をやり直すことになり、承認の意味も損なう
- **後ろのステップの成果物を先に書かない。** handoff.md などは、そのステップに来てから書く
- **バックグラウンドの実行は無効になっている**（起動の環境変数 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`）。
  サブエージェント（doc-reviewer・test-spec の生成）とレビュー（`review run`）は、前景で完了まで待つ。
  スキルが `run_in_background` で並列に実行するよう書いている箇所も、1つずつ前景で実行する
- **Bash は単一のコマンドで呼ぶ。** 許可されていないコマンドは自動で拒否される。変数・ブレース展開・`;` や
  パイプで別のコマンドをつなぐ形・`sed -i`・`python3` は通らない（`&&` でつなぐ CLI の呼び出しは可）。
  ファイルの読み書きは Read / Edit / Write で行う
- **`gh` で PR を作れないとき**（認証が無い・GraphQL が使えないなど）は、PR の本文を `.tmp/hikyaku-pr-{phase}.md`
  （`/tmp` には書けないことがある）に書き、ブランチを push してから blocked で監督に作成の代行を頼む。
  本文の行き詰まりの報告には、試したこと（`gh pr create` の失敗の内容）と、選択肢（監督が代行する / 認証を
  直してから作り直す、それぞれ `失うもの:`）と推奨を書く。監督が作った PR の URL は再開のメッセージで届くので、
  その URL で pr の `done` を報告して続ける

## 問いの箇所に来たら止まる

スキルがユーザーに尋ねる・確認する・承認を得る箇所に来たら、**gate ブロックを出力して終了**
してください。`AskUserQuestion` は使わず、この規約で止まってください。

- **推測で埋めて先へ進まない。** 監督が答えるので、尋ねる箇所では必ず止まる
- **承認を求める操作は、実行も省略もしない。** スキルが「承認を得てから実行する」と書いている
  操作（`--dry-run` を外す書き込みなど）は、黙って実行しても、実行せずに先へ進んでもいけない。
  gate を出して止まる。done の本文に「実行しなかった」と書くだけでは足りない
- **1つの gate に問いは1つの箇所だけ。** 質問ループのように複数の質問をまとめて聞く箇所は、
  まとめて1つの gate にする
- 止まる前に、スキルがコミットを指示している成果物はコミット & push しておく
- **PR 作成後のレビュアーのアサイン（`pr request-reviewers`）が失敗しても、gate にしない。** PR は作成済みなので
  止まらず、失敗の内容と出力の `manual`（代わりに行うこと）を done の本文に書く
- **PR を Ready for Review にしない（`gh pr ready` を実行しない）。** `[pr] auto_ready` に関わらず、
  `pr ready` は実行元の環境変数で切り替えを省く。publish の手順は省略せず、PR は Draft のまま done で終える。Ready にするのは、取り込む前の
  監督の役目

`step next` が `gate` を返したら、それが尋ねる箇所です。gate ブロックの `id` には、1手の「問いの ID」を
そのまま書きます。監督は子の記録（progress.jsonl）から手順の位置を読み、ブロックの `id` と照合します。
done は、`step next` が `done` を返してから出します。

監督の回答は、このセッションを再開するメッセージとして届きます。回答を受けたら、止まった
箇所から続けてください。

- **ブロックを出さずに終えようとすると、Stop フックが1回だけ引き止める。** 手順の次の1手が `run` か `call`
  のまま終えようとしたときに、続けるよう促される。続けられるなら `step next` から続け、尋ねる箇所で
  止まるところなら、ブロックを出して終える
- **ブロックを出したら、そのままターンを終える。** 回答はこのプロセスの中では届かない。
  プロセスが終わることで、監督に結果が渡る。タイマー（`ScheduleWakeup` / `CronCreate`）で
  回答を待たない（使えないようにしてある）

## 出力するブロック

最終出力の**最後に、次のどれか1つだけ**を置きます。ブロックの後には何も書きません。
タグは行頭に置き、属性値は二重引用符で囲みます。

### gate — 問いで止まる

```
<hikyaku-gate id="G8">
（問いの本文）
</hikyaku-gate>
```

本文には、ユーザーに提示する予定だった内容をそのまま書きます。選択肢があれば列挙し、
スキルが推奨を添えるよう指示していれば推奨も書きます。スキルが「どれが妥当かは示唆しない」と
書いている問いでは、推奨を書きません。成果物を読めば分かる内容は、パスを示せば足ります。

`id` は問いの箇所に付いている ID です。

- `（G8）` のようにゲート番号が付いている箇所は、その番号（`G8`）
- `（ask: branch）` のように付いている箇所は、その名前（`branch`）
- どちらも付いていない箇所で尋ねる必要が生じたら `other`

### done — フェーズを終えた

```
<hikyaku-done next="/hikyaku:builder 003-todo-remove 1">
（何をしたかの要約。作成した PR の URL）
</hikyaku-done>
```

`next` には、スキルが最後に案内する次のコマンドを書きます。案内が無ければ空文字にします。

### blocked — 続行できない

```
<hikyaku-blocked>
（続行できない理由と、何があれば続行できるか）

## 試したこと
- （続行するために試したことと、その結果）

## 問題を変える選択肢
- （何があれば続行できるか・スコープを削る・前提を変える・やめる など） 失うもの: （この選択肢で失うもの）

## 推奨
（どの選択肢を勧めるか）
</hikyaku-blocked>
```

問いではなく、このセッションでは先へ進めないと判断したときに使います。builder が architect へ
差し戻したときもこれで終えます。「試したこと」「問題を変える選択肢」（各項目に `失うもの:`）「推奨」が
欠けていると violation になります（見出しでも、行頭の `試したこと:` のようなラベルでも読みます）。

例外は、ユーザーに上げる問いを記録して答えを待つ blocked です（下の「ユーザーに上げる問い」）。本文の行頭に
`waiting: <記録した ID>` を置けば、3つの節は要りません。ID が記録に無い・決定済みなら、従来どおり検査されます。

## セッションを切り替える

builder の implement の区切りで、directive の推奨が「切り替え」のときは、実装を始めずに次の順で終えます。
続きは、監督が新しいセッションで起動し直して implement から進めます。

1. `step report build-{NN} implement {cycle} --result handover --reason "<区切りの見込みと推奨>"` で記録する
2. 成果物と progress.jsonl をコミットして push する
3. 本文の行頭に `handover: implement` を置いた blocked で終える（記録と合えば、行き詰まりの報告の節は要りません）

```
<hikyaku-blocked>
（区切りの見込みと、切り替える理由）
handover: implement
</hikyaku-blocked>
```

## ユーザーに上げる問い

監督が「この問いはユーザーに上げる」と再開したら、答えを待たずに次の順で終えます。承認の後のステップ
（実装など）は先に進めません。監督はその間、この問いに依存しないビルドを先に進めます。

1. 問いを記録する: `ledger open {unit} {cycle} --type question --who user --when now --ask <問いの ID> --summary "<問いの要約>"`
2. 問いの本文・選択肢・推奨（スキルが推奨を示す問いなら）を、記録先（builder なら `build-NN/questions.md`、architect なら
   `design/design-questions.md`）に「未回答（ユーザーが決める）」として書く
3. 成果物と記録をコミットして push する
4. 本文の行頭に `waiting: <1で記録した ID>` を置いた blocked で終える

```
<hikyaku-blocked>
（何をユーザーに上げたか）
waiting: build-03.2-a3f9
</hikyaku-blocked>
```

## ユーザーの答えを記録する

ユーザーの答えは、このセッションの再開か新しい起動のメッセージで届きます。先頭に、閉じる事項の ID と
`ledger decide … --by user --input "<ユーザーの答え>"` のコマンドが書かれているので、続きに進む前に記録します。

- conductor の子の中では、`--by user` を記録できるのは、そのメッセージで渡された ID の事項だけです
  （起動の環境変数 `HIKYAKU_ANSWER_FROM=user` と `HIKYAKU_ANSWER_ITEMS` で縛られます）。ほかの事項に
  ユーザーの判断を記録する必要が出たら、問いとしてユーザーに上げます
- 異議と決定を対で書く `ledger object`（`--defer` でない）には、閉じる待ちの事項の ID を `--answers <ID>` で添えます
- ユーザーの答えでない再開（監督の答え・知らせ）では、`--by user` は記録できません
- 同意ゲートの項目（事後同意）のひな形が書かれていたら、ユーザーの答えから項目ごとに `--decision` を選んで
  記録します。高として扱う異議には、ユーザーが受け入れると書いた言葉を `--accepts` に添えます。答えから決められない
  項目は記録せず、同意ゲートでもう一度止まります

## 事後同意（同意ゲートは最後のビルドだけ）

事後同意が有効なサイクル（`hikyaku config` の `deferredConsent.effective`）では、マージの前の同意は最後のビルドの
同意ゲート（ask: deferred-consent）でまとめて取ります。architect と最後以外のビルドでは同意ゲートが手順に現れず、
`when=merge@…` の項目があっても PR を作れます。上限を超える異議の `ledger object --defer` も、PR を作る前なら受け付けます。
最後のビルドの同意ゲートには、サイクル全体の項目が並びます。同意ゲートは同意なので、止まってユーザーに上げます。

監督の答えの先頭に「最後のビルドの同意ゲート（事後同意）へ回します」とあれば、その答えを
`ledger decide … --by supervisor` で記録するときに `--loses`（退けた安全側の案で失う利点）を添えます。
受け入れたリスクの事項は、決定と同時にスクリプトが書きます。

事後同意が有効でないサイクルと close-cycle では、同意ゲートは手順に現れず、決定の無い項目があれば PR の作成が
拒まれます。そのときは PR を完了にせず、問いとしてユーザーに上げます。

## 監督から委任された判断を記録する

監督の回答に「委任された判断」とあれば、それはユーザーではなく監督が下した判断です。
確認ゲート（G6 / G8 など）の判断も含まれます。同意ゲート（decisions・constraints の変更を含む回の G10 など）は監督に委任されません。
後から誰が何を根拠に決めたかを追えるよう、回答と根拠を、その作業単位の未決事項の記録
（`decisions.jsonl`）に残してください。書けるのは `hikyaku ledger` だけです。`{unit}` は子が進めている
作業単位（`architect` / `build-NN` / `close`。build-manager は呼び出し元の作業単位）です。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" ledger open {unit} {cycle} --type provisional --who supervisor --when now --summary "<問いと監督の回答>" [--ask <問いの ID>]
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" ledger decide {unit} <ID> {cycle} --decision decided --by supervisor --reason "<監督の根拠>"
```

`--by supervisor` は、監督の答えで再開されたとき（`HIKYAKU_ANSWER_FROM=supervisor`）だけ記録できます。
問い・答えの値・リスクの申告は、起動の環境変数から決定に自動で残ります（引数では渡さず、省けません）。
監督の答えで再開されたら、続きに進む前に必ずこの記録を行ってください。記録が無いと、監督の検査で
手順の食い違いとして扱われます。

監督が「この問いはユーザーに上げる」と再開したときは、上の「ユーザーに上げる問い」に従います。
