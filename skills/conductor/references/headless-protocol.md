# 非対話規約

あなたは `/hikyaku:conductor` の監督から、非対話（`claude -p`）で起動されたセッションです。
人間はこのセッションを見ていません。ユーザーへの問いには監督が答えます。

この規約はスキルの手順を変えません。スキルが「ユーザーに尋ねる」「承認を得る」と書いている
箇所で、どう止まるかだけを定めます。それ以外はスキルの指示どおりに進めてください。

## 問いの箇所に来たら止まる

スキルがユーザーに尋ねる・確認する・承認を得る箇所に来たら、**gate ブロックを出力して終了**
してください。`AskUserQuestion` は使わず、この規約で止まってください。

- **推測で埋めて先へ進まない。** 監督が答えるので、尋ねる箇所では必ず止まる
- **承認を求める操作は、実行も省略もしない。** スキルが「承認を得てから実行する」と書いている
  操作（`--dry-run` を外す書き込みなど）は、黙って実行しても、実行せずに先へ進んでもいけない。
  gate を出して止まる。done の本文に「実行しなかった」と書くだけでは足りない
- **1つの gate に問いは1つの箇所だけ。** 質問ループのように複数の質問をまとめて聞く箇所は、
  まとめて1つの gate にする
- 止まる前に、スキルがコミットを指示している成果物はコミット & push しておく
- **PR 作成後のレビュアーのアサイン（`pr request-reviewers`）が失敗しても、gate にしない。** PR は作成済みなので
  止まらず、失敗の内容と出力の `manual`（代わりに行うこと）を done の本文に書く
- **PR を Ready for Review にしない（`gh pr ready` を実行しない）。** `[pr] auto_ready` に関わらず、
  `pr ready` は実行元の環境変数で切り替えを省く。publish の手順は省略せず、PR は Draft のまま done で終える。Ready にするのは、取り込む前の
  監督の役目

`step next` が `gate` を返したら、それが尋ねる箇所です。gate ブロックの `id` には、1手の「問いの ID」を
そのまま書きます。監督は子の記録（progress.jsonl）から手順の位置を読み、ブロックの `id` と照合します。
done は、`step next` が `done` を返してから出します。

監督の回答は、このセッションを再開するメッセージとして届きます。回答を受けたら、止まった
箇所から続けてください。

- **ブロックを出さずに終えようとすると、Stop フックが1回だけ引き止める。** 手順の次の1手が `run` か `call`
  のまま終えようとしたときに、続けるよう促される。続けられるなら `step next` から続け、尋ねる箇所で
  止まるところなら、ブロックを出して終える
- **ブロックを出したら、そのままターンを終える。** 回答はこのプロセスの中では届かない。
  プロセスが終わることで、監督に結果が渡る。タイマー（`ScheduleWakeup` / `CronCreate`）で
  回答を待たない（使えないようにしてある）

## 出力するブロック

最終出力の**最後に、次のどれか1つだけ**を置きます。ブロックの後には何も書きません。
タグは行頭に置き、属性値は二重引用符で囲みます。

### gate — 問いで止まる

```
<hikyaku-gate id="G8">
（問いの本文）
</hikyaku-gate>
```

本文には、ユーザーに提示する予定だった内容をそのまま書きます。選択肢があれば列挙し、
スキルが推奨を添えるよう指示していれば推奨も書きます。スキルが「どれが妥当かは示唆しない」と
書いている問いでは、推奨を書きません。成果物を読めば分かる内容は、パスを示せば足ります。

`id` は問いの箇所に付いている ID です。

- `（G8）` のようにゲート番号が付いている箇所は、その番号（`G8`）
- `（ask: branch）` のように付いている箇所は、その名前（`branch`）
- どちらも付いていない箇所で尋ねる必要が生じたら `other`

### done — フェーズを終えた

```
<hikyaku-done next="/hikyaku:builder 003-todo-remove 1">
（何をしたかの要約。作成した PR の URL）
</hikyaku-done>
```

`next` には、スキルが最後に案内する次のコマンドを書きます。案内が無ければ空文字にします。

### blocked — 続行できない

```
<hikyaku-blocked>
（続行できない理由と、何があれば続行できるか）

## 試したこと
- （続行するために試したことと、その結果）

## 問題を変える選択肢
- （何があれば続行できるか・スコープを削る・前提を変える・やめる など） 失うもの: （この選択肢で失うもの）

## 推奨
（どの選択肢を勧めるか）
</hikyaku-blocked>
```

問いではなく、このセッションでは先へ進めないと判断したときに使います。builder が architect へ
差し戻したときもこれで終えます。「試したこと」「問題を変える選択肢」（各項目に `失うもの:`）「推奨」が
欠けていると violation になります（見出しでも、行頭の `試したこと:` のようなラベルでも読みます）。

## 監督から委任された判断を記録する

監督の回答に「委任された判断」とあれば、それはユーザーではなく監督が下した判断です。
確認ゲート（G6 / G8 など）の判断も含まれます。同意ゲート（decisions・constraints の変更を含む回の G10 など）は監督に委任されません。
後から誰が何を根拠に決めたかを追えるよう、回答と根拠を、その作業単位の未決事項の記録
（`decisions.jsonl`）に残してください。書けるのは `hikyaku ledger` だけです。`{unit}` は子が進めている
作業単位（`architect` / `build-NN` / `close`。build-manager は呼び出し元の作業単位）です。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" ledger open {unit} {cycle} --type provisional --who supervisor --when now --summary "<問いと監督の回答>" [--ask <問いの ID>]
node "${CLAUDE_PLUGIN_ROOT}/scripts/hikyaku.mts" ledger decide {unit} <ID> {cycle} --decision decided --by supervisor --reason "<監督の根拠>"
```

監督が「この問いはユーザーに上げる」と再開したときは、`--who user` で事項を記録して終えます
（ユーザーの答えは、後の再開で `--by user` として記録します）。
