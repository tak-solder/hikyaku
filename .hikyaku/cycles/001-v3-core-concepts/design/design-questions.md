# 設計段階の質問

### Q1: ゲートの確認と同意の分類
- 案a（推奨）: 同意 = G1、G10 の `decisions`・`constraints`、上限を超える害を受け入れる G3、宣言の変更。確認 = G2・G4・G6・G7・G8・G10 のそれ以外。G6・G8 は全プロファイルで有効のまま、conductor では監督が答えられる。欠点: G8 で AI の解釈が意図を変えていても、conductor では監督が通しうる（解釈は提示と記録に残る）
- 案b: G6・G8 も同意にし、conductor でも人間に上げる。欠点: conductor がビルドごとに止まり、委任の意味がほぼ無くなる

**回答**: 案a（推奨どおり）

### Q2: アプリケーションの状況の宣言の形と、「上限を超える」の判定
- 案a（推奨）: 公開範囲（`personal / internal / public`）・データの重さ（`none / internal / personal-or-secret`）・壊れたときの影響（`low / medium / high`）を3段の順序つきの値で宣言し、重い領域はパスで同じ3軸を上書きする。重い領域のパスに触れる受け入れはスクリプトの判定で人間に上げる。LLM が付けた害の重さが上限を超えるとスクリプトが比べたときも人間に上げる。LLM の重さは人間に上げる向きにしか効かない。欠点: 3段に収まらない事情は表せない
- 案b: 「AI に任せてよい害の重さ」の上限を1つの値で直接宣言する。欠点: 前提の変化（公開した等）と上限の結び付きが見えず、US-13.5 の見直しで受け入れたリスクを辿りにくい

**回答**: 案a（推奨どおり）

### Q3: 異議の強さの段階
- 案a（推奨）: `persistence.md` の重要度を流用する。高（成果物に害が残る）は、人間が「何を受け入れるか」を書くまで進めない。中（セッションの損失）は指摘して記録するだけ。欠点: 重要度の定義を変えると異議の段階も一緒に変わる
- 案b: 異議専用の段階を定義する。欠点: 基準が2つになり食い違いうる

**回答**: 案a（推奨どおり）

### Q4: 差分と合意を突き合わせる新しいレビュー（US-2.4）をプロファイルで省けるか
- 案a（推奨）: code_review と同じく全プロファイルで必ず実行する。欠点: economy の AI 実行コストがビルドあたりサブエージェント1回分増える
- 案b: 中間成果物のレビューと同じく economy では省く。欠点: economy でスコープの確認を誰もしなくなる（現状より後退）

**回答**: 案a（推奨どおり）

### Q5: 境界のパスを、外との境界と内部の境界に分けて宣言するか
- 案a（推奨）: 分ける（例: `external = ["api/**", "db/migrations/**"]`、`internal = ["src/core/**"]`）。G4 では外の変更を「同意が要る変更」、内部の変更を「確かめる変更」として分けて示す。欠点: 宣言の手間が少し増える
- 案b: 1種類だけ宣言し、外か内かは LLM が design-delta から書き分ける。欠点: 区分を LLM が決めることになる（原則1に反する）

**回答**: 案a（推奨どおり）

### Q6: 閾値と期間の既定値（いずれも設定で変更可）
- 推奨: 触られていなかったとみなす期間 180 日（US-5.1）。同じ rule が引かれたら移す候補にする回数 3 回、サイクルをまたいで数える（US-4.2）。基準を消した PR の前後で指標を比べる幅は、マージ前後それぞれ直近 2 サイクル。揃うまでは「比較できない」と示す（US-9.4）

**回答**: 推奨どおり

### Q7: フィードバックの書き出し先（US-16）
- 案a（推奨）: `{HIKYAKU_ROOT}/feedback/{YYYYMMDD}.md` に書き、`.gitignore` の対象にする（コミットしない）。欠点: チームで共有されず手元にしか残らない
- 案b: 同じ場所に書いてコミットする。欠点: 下書きにプロジェクトの固有名が残っていた場合、履歴に残る

**回答**: 案a（推奨どおり）
