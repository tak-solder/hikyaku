# 企画段階の質問

### Q1: 項目が多いが、サイクルを分けずに1サイクルで進めるか
**回答**: 1サイクルで進める。ビルドへの分け方は Hikyaku の見積もりに任せる。

### Q2: バージョンの扱い。base が `feature/v3-core-concepts`（v3.0.0 の前段）なので、PR ごとに上げず `3.0.0` に積むか
**回答**: PR ごとに上げず `3.0.0` に積む。

### Q3: アプリケーションの状況を宣言していないワークスペースをどう扱うか（a: 従来どおり上限を設けない / b: 安全側に倒し、上限を超えるリスクは人間に上げる）
**回答**: a。宣言が無ければ従来どおり、上限を設けない。

### Q4: フィードバックの書き出しの範囲（a: 記録の種類を固定し、文章を用意して終わる / b: 起票の下書き（issue 本文）まで作る）
**回答**: b。起票の下書きまで作る。起票は人間が行う。

### Q5: 既存のワークスペース（アプリケーションの状況を宣言していない、旧形式の ADR・`constraints` を持つ）が、そのまま動き続けることを要件として確定するか
**回答**: 既存のワークスペースは意識しなくてよい。互換を要件にしない（G1 で回答）。

### Q6: 合意に無いと指摘された変更（US-2.6）を、どこで止めるか（PR 本文に示し、builder が直すか人間が受け入れると判断するまで PR を作る手順に進まない、で良いか）
**回答**: 止めない。合意に無い変更は、builder がコードレビューの指摘と同じ扱いで直すか理由を返し、理由を PR 本文に並べる。人間の判断を待って止める手順は作らない（G1 で回答）。

## ARCHITECT の G3 の途中で要件を足したときの質問（US-19〜US-21）

### Q7: 事後確認に回せる判断の範囲（上限を超えるリスクの受け入れだけ / 意図を変える判断・外の前提が要る判断も含める）
**回答**: 上限を超えるリスクの受け入れだけ。意図を変える判断と外の前提が要る判断は従来どおりその場で止まる。G1 と、G10 の `decisions`・`constraints` は対象にしない。

### Q8: 事後確認をどこで選ぶか
**回答**: サイクルの `.hikyaku.config` のキーで選ぶ。conductor を起動したときの委任の範囲の確認にも表示する。リポジトリ全体の既定にはしない。

### Q9: 「マージが人間の関門になっている」をどう確かめるか
**回答**: アプリケーションの状況の宣言に、人間が前提として書く（マージがそのままリリースにならない、自動マージしない）。宣言が無いか成り立たないときは事後確認を選べない。GitHub の設定をスクリプトで調べることはしない。

### Q10: どのマージの前に同意するか
**回答**: conductor を使わないときは、そのリスクを受け入れたフェーズの PR。conductor のときは、人間がレビューする最後の PR（conductor ブランチからベースブランチへの PR）に、全フェーズで受け入れたリスクの一覧を載せる。

### Q11: conductor の「走りきり」の中身
**回答**: (a) 事後確認を選んだ問いは止まらず、マージ前の一覧に積む。(b) 止まる必要がある問いが出ても、その問いに依存しないビルドは先に進める。

### Q12: 未決事項と暫定の決定の記録の置き場
**回答**: サイクルの中で決まるものを、サイクルの追記型の記録に置く。決まったかどうかは決定の記録から導く。サイクルをまたぐもの（ADR の再評価条件や受け入れたリスクの拠り所の前提を、ADR・`constraints` の欄からスクリプトが読んで知らせること）は今回は外す。ADR に再評価条件の欄を書けること自体は US-6 のまま残す。

### Q13: 「いつ」に書けるもの
**回答**: サイクルの中の出来事だけ（フェーズやゲートの開始、PR のマージの前、サイクルの close）。日付と、スクリプトで判定できない自由文の条件は今回は扱わない。

### Q14: 「誰が」の区分
**回答**: 人間・AI（どのフェーズか）・監督（conductor）の3つ。人間が決めるものを AI や監督に付け替える手順は作らない。

### Q15: 通知の方法
**回答**: 期限が来たフェーズの手順の中（`step next` が返すゲートと PR 本文）と、`cycle status`・navigator に示す。外への通知と常駐する仕組みはスコープ外。Hikyaku は外への送信と常駐する仕組みを持たないため。

### Q16: 記録する側のスキル
**回答**: planner（未回答の質問）、architect（暫定の設計判断）、builder（handoff に残す未決）、patch、conductor（監督が預けた判断）、close-cycle。期限が来たかの判定と提示はスクリプトが行う。
