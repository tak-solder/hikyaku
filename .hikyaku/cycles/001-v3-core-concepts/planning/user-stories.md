# ユーザーストーリー

## 概要

### 実現したいこと

`docs/concepts.md` と AGENTS.md「設計の原則（v3）」に先に書いた理想の姿のうち、まだ仕組みが無い方針を、Hikyaku のスクリプト・手順の定義・スキル・テンプレートで実装する。Hikyaku でサイクルを回す人間（以下「利用者」）から見て、次のことができるようになる。

- 人間の選択が自身の宣言・記録・前提と食い違うとき、AI が根拠と失うものを示して異を唱え、異議と決定が記録に残る
- AI が問題を黙って変えた差分（テストの削除・緩和、承認後のシナリオの書き換え、スコープ外の変更）が事実として並び、作った本人ではないレビューが合意と突き合わせる。行き詰まりは、問題を変える選択肢として人間に上がる
- 知見と基準が、なくす → 機械で防ぐ → 書く、の順で扱われ、移すきっかけや消す経路を持つ。領域の開発頻度がその判断に効く
- ADR・`constraints`・設計の質問の記録に、前提・判断・推奨・受け入れたこと・再評価条件を分けて書ける
- 承認が判断の種類で確認と同意に分かれ、ゲートでは人間が判断すべきものだけが示される。アプリケーションの状況の宣言が、AI に任せてよいリスクの上限になる
- 中身を含まないフィードバックと起票の下書きを、利用者のリポジトリの中で作れる
- ワークスペースを作るときに見つかった制約（document-guide.md のアンカー、`gh` が使えない環境）が解消される

### 背景・目的

`feature/v3-core-concepts` では、文書（concepts.md・AGENTS.md）を理想の姿として先に書いた。仕組みが追い付かないままでは文書と実装が食い違い、「指示文で LLM にやらせない」「黙って従わない」といった原則が運用で守られない。文書に書いた v3 の原則を、スクリプトの判定と手順の定義で裏付けることが目的。

### 対象画面・対象データ

- 手順の定義とスクリプト（`scripts/lib/steps/`、`scripts/lib/`、`scripts/commands/`）
- スキルの手順とテンプレート（planner・architect・builder・build-manager・close-cycle・retrospective・conductor・init）
- エージェント定義（`agents/doc-reviewer.md` ほか）
- 知見の基準の正（`skills/close-cycle/references/persistence.md`）
- 設定（`.hikyaku.config`。アプリケーションの状況の宣言は新しいキーになる（推測））
- ワークスペースの記録（`progress.jsonl`、handoff.md、retrospective.md、design-questions.md、ADR、`constraints`）
- 利用者向けの説明（`docs/`）、`plugin.json`・CHANGELOG

### 制約・要件

- `constraints` は未作成のため、確定済みの非機能要件の参照は無い
- AGENTS.md の規約に従う（実行時依存ゼロ、`.mts` と型剥がしで動く構文、書き込みを伴うコマンドの `--dry-run`、`（ask: <id>）` と `ASKS` の同期、挙動の変更と同じ PR での `docs/` の更新）
- バージョンは PR ごとに上げず、`3.0.0` に積む（Q2）
- 既存のワークスペース（アプリケーションの状況を宣言していない、旧形式の ADR・`constraints` を持つ）が、そのまま動き続ける（Q5）

## スコープ外

- 受け入れ基準の層の test-first — 今回の範囲から外した（ユーザー指定）
- patch の記録から元のサイクルの受け入れ基準を指すこと — 今回の範囲から外した（ユーザー指定）
- フィードバックの起票（外部への送信）そのもの — 原則15により人間が行う。Hikyaku は下書きまで（Q4）
- アプリケーションの状況を宣言していないワークスペースに上限を設けること — 宣言が無ければ従来どおり（Q3）

## US-1: 食い違う選択に異を唱え、異議と決定を記録する

**ユーザー**: サイクルを回す利用者
**目的**: 自分の宣言・記録・前提と食い違う選択を、気づかずに下さないため
**操作**: ゲートや問いで、宣言（アプリケーションの状況、`constraints`）・記録（見積もり、差し戻しの履歴）・前提と食い違う選択をする
**優先度**: Must
**受け入れ基準**:
- [ ] US-1.1: 人間の選択がその人自身の宣言・記録・前提と食い違うとき、AI が食い違いの根拠（どの宣言・記録か）と、その選択で失うものを示して異を唱える
- [ ] US-1.2: 好みの違い（宣言・記録・前提のどれとも食い違わない選択）には異を唱えない
- [ ] US-1.3: 害が中程度の食い違いは指摘にとどまり、人間がそのまま進めればそれで決まる
- [ ] US-1.4: 害が成果物に残る食い違いは、人間が「何を受け入れるか」を自分の言葉で書くまで先に進まない
- [ ] US-1.5: 異議と人間の決定の両方が成果物の記録に残り、後のフェーズや PR のレビューで追える。US-1.4 で人間が書いた「何を受け入れるか」は、拠り所にした前提と結び付けて残る

## US-2: AI が問題を黙って変えた差分を、別のレビューが合意と突き合わせる

**ユーザー**: ビルドの PR をレビューする利用者
**目的**: テストやスコープが黙って書き換えられたまま、ビルドが通らないようにするため
**操作**: builder がビルドを実装し、PR を作る前のレビューを受ける
**優先度**: Must
**受け入れ基準**:
- [ ] US-2.1: ビルドの差分にテストの削除・スキップ・期待値の緩和があれば、スクリプトが差分から事実として一覧に並べる
- [ ] US-2.2: G8 の承認後にテストシナリオが書き換えられていれば、その書き換えも一覧に並ぶ
- [ ] US-2.3: スクリプトが、ビルドの差分で変更したファイルと変更の種類を事実として一覧に並べる（スコープの内か外かはスクリプトが判定しない）
- [ ] US-2.4: 作った本人ではないレビュー（doc-reviewer の新しい context）が、一覧を合意（issue.md・テストシナリオ）と突き合わせ、スコープ外の変更を含む合意に無い変更を指摘する
- [ ] US-2.5: builder が自分で行っていたスコープとデータ安全の確認が、このレビューに移る
- [ ] US-2.6: 合意に無いと指摘された変更は PR 本文に示され、builder が直すか、人間が受け入れると判断するまで PR を作る手順に進まない（Q6）

## US-3: 行き詰まったら、問題を変える選択肢として人間に上げる

**ユーザー**: 行き詰まったビルドやフェーズの報告を受ける利用者
**目的**: 解き方ではなく、どの問題に変えるかを選べるようにするため
**操作**: AI が行き詰まって人間に判断を上げる（差し戻し、エスカレーション）
**優先度**: Must
**受け入れ基準**:
- [ ] US-3.1: 上げる報告に、試したことが含まれる
- [ ] US-3.2: 上げる報告に、問題を変える選択肢（スコープを削る、要件を緩める、前提を変える、やめる など）と、それぞれで失うものが含まれる
- [ ] US-3.3: 上げる報告に、AI の推奨が含まれる
- [ ] US-3.4: 3つのどれかが欠けた報告は、手順の完了として受け付けられない

## US-4: 知見を「なくす」から考え、書いた基準を機械の検査やリファクタへ移すきっかけを見つける

**ユーザー**: 知見の置き場を判断する利用者（builder・close-cycle の結果を承認する人）
**目的**: 書かれた基準を増やし続けず、機械の検査やリファクタへ移していくため
**操作**: builder・close-cycle で知見の置き場を決める。サイクルを重ねて記録が溜まる
**優先度**: Must
**受け入れ基準**:
- [ ] US-4.1: 知見の置き場の順の先頭に「なくす（リファクタ）」があり、builder・close-cycle・doc-triager の振り分けで選べる
- [ ] US-4.2: レビューの指摘がどの rule を引いたかが記録に残り、同じ rule が閾値（設定か既定値で決まる）以上引かれていることを、スクリプトがその記録から見つけ、機械の検査やリファクタへ移す候補として示す
- [ ] US-4.3: どのファイルにも一致しなくなった rule を、スクリプトが見つけて示す
- [ ] US-4.4: 移すか消すかの判断は人間と LLM が行い、スクリプトは候補を並べるところまでにとどまる

## US-5: 領域の開発頻度を、置き場と見直しの判断に反映する

**ユーザー**: しばらく触られていなかった領域を変えるサイクルの利用者
**目的**: 長く触られていない間に黙って偽になった前提や基準を、変更の前に見直すため
**操作**: サイクル（設計）やビルドで、変更する領域が決まる
**優先度**: Should
**受け入れ基準**:
- [ ] US-5.1: 変更する領域（パス）がどれだけ最近まで触られていたかを、スクリプトがリポジトリの履歴から判定する。触られていなかったとみなす期間は、設定か既定値で決まる
- [ ] US-5.2: その期間を超えて触られていなかった領域に変更が入るとき、その領域に結び付いた前提と基準（US-5.5）が、見直しの対象として設計の前に示される
- [ ] US-5.3: 知見の置き場を決めるとき、領域の開発頻度が判断材料として示される（頻繁に変わる領域は機械の検査へ早めに移す、めったに触らない領域はパス指定の rule やその場のコメントに置く）
- [ ] US-5.4: 基準を消す判断のとき、領域の開発頻度が判断材料として示される
- [ ] US-5.5: 前提と基準を、領域（パス）に結び付けて記録できる

## US-6: ADR と `constraints` に、前提・判断・推奨・受け入れたこと・再評価条件を分けて書く

**ユーザー**: 判断の拠り所を後から辿る利用者と、次の AI セッション
**目的**: 外の前提が黙って偽になったときに、それに立つ判断と受け入れたリスクを辿れるようにするため
**操作**: architect が ADR を追記し、close-cycle が ADR・`constraints` を昇格させる
**優先度**: Must
**受け入れ基準**:
- [ ] US-6.1: 外の前提を、確かめた事実か仮定かの区別と、確かめた日とともに書ける
- [ ] US-6.2: 判断・推奨・受け入れたこと・再評価条件を、混ぜずにそれぞれの欄に書ける
- [ ] US-6.3: 人間が推奨を退けたとき、何を優先したかと、推奨案の利点のうち失うものを書く
- [ ] US-6.4: 外の前提と受け入れたリスクを、AI が人間の同意なしに書き換えたり消したりする手順が無い
- [ ] US-6.5: 旧形式で書かれた既存の ADR・`constraints` も、引き続き読める（Q5）
- [ ] US-6.6: 受け入れたことに、拠り所にした外の前提（アプリケーションの状況を含む）を結び付けて書ける

## US-7: 設計の質問の記録に、選択肢・欠点・推奨を書く

**ユーザー**: 設計の質問に答える利用者
**目的**: 何を退け、何を失ったかを、決定と一緒に残すため
**操作**: architect の設計の質問に答える
**優先度**: Must
**受け入れ基準**:
- [ ] US-7.1: design-questions.md に、質問ごとの選択肢・各案の欠点・推奨を書く欄がある
- [ ] US-7.2: 人間が推奨と違う案を選んだとき、推奨案の利点のうち失うものが記録される

## US-8: ポインタに件数や範囲を書かない

**ユーザー**: 永続ドキュメントや成果物を読む利用者と、次の AI セッション
**目的**: ポインタがコピーになり、腐ったことに気づけなくなるのを防ぐため
**操作**: スキルやテンプレートに沿って文書を書く
**優先度**: Should
**受け入れ基準**:
- [ ] US-8.1: テンプレートと指示文が、ポインタに件数や範囲（「AD-1〜AD-5」「3件」など）を添えさせない
- [ ] US-8.2: 永続ドキュメントとサイクルドキュメントのポインタに ID の範囲（「AD-1〜AD-5」の形）が添えられていれば、検査（`hikyaku validate`）が警告として示す。既存の文書をエラーにはしない

## US-9: 基準に理由を残し、消して指標を見る経路を持つ

**ユーザー**: 基準を減らしたい利用者
**目的**: 理由の分からない基準を抜けなくなるのを防ぎ、働いている基準を誤って抜いても戻せるようにするため
**操作**: 基準を書く。基準を消す提案を受け、マージ後の様子を見る
**優先度**: Must
**受け入れ基準**:
- [ ] US-9.1: 基準を書くとき、何を防ぐためのものか（実際に起きた失敗）と、何に立っているか（モデルの振る舞い、いまのコードの形、外の前提）と、重要度（害が成果物に残るか）を残す形になっている
- [ ] US-9.2: 理由が消えた基準や、役に立たなかったと記録された基準が、消す候補として示される
- [ ] US-9.3: 基準を消す変更は、フェーズの PR とは別のブランチの PR になる
- [ ] US-9.4: 消す変更がマージされたあと、後続のサイクルの close-cycle で、マージ前後の品質の指標（レビューの重い指摘、差し戻し、重要度が高い落とし穴）を比べた結果が示され、悪くなっていれば戻す判断の材料になる
- [ ] US-9.5: US-9.1 で害が成果物に残ると記録された基準（情報の漏えいやデータの損失を防ぐものなど）は、試しに消す候補にならない

## US-10: 承認を、ゲートの番号ではなく判断の種類で確認と同意に分ける

**ユーザー**: プロファイルを選ぶ利用者
**目的**: 省いてよい確認だけを省き、人間にしか下せない判断はどの設定でも残すため
**操作**: プロファイルを選び、ゲートで承認する
**優先度**: Must
**受け入れ基準**:
- [ ] US-10.1: 意図を変える判断、外の前提に関わる判断、AI に任せてよい上限を超えるリスクを受け入れる判断は同意として扱われ、どのプロファイルでも conductor でも省かれない
- [ ] US-10.2: それ以外の覆せる判断や安全側に倒す判断は確認として扱われ、プロファイルに応じて省ける
- [ ] US-10.3: G3 は、案の中に上限を超える害を受け入れるものが無ければ確認として省け、あれば人間に上がる
- [ ] US-10.4: ゲートの一覧（profiles.md）から、各ゲートの判断が確認か同意かが分かる

## US-11: G10 を、`decisions`・`constraints` の同意と、それ以外の確認に分ける

**ユーザー**: close-cycle で昇格を承認する利用者
**目的**: 人間が約束した前提とリスクの変更だけに、同意の時間を使うため
**操作**: close-cycle の G10 で、永続ドキュメントへの昇格を承認する
**優先度**: Must
**受け入れ基準**:
- [ ] US-11.1: `decisions`・`constraints` の変更は同意として、どのプロファイルでも conductor でも人間の承認を求める
- [ ] US-11.2: `overview`・`conventions`・`glossary` の変更は確認として扱われ、プロファイルに応じて省ける
- [ ] US-11.3: G10 の提示で、同意が要る変更と確認の変更が分かれて示される

## US-12: G4 と G8 で、人間が判断すべきものだけを示す

**ユーザー**: G4・G8 で承認する利用者
**目的**: 限られた時間で読める量に絞り、読まれない承認を作らないため
**操作**: architect の G4、builder の G8 で承認する
**優先度**: Must
**受け入れ基準**:
- [ ] US-12.1: G4 で、外との境界と内部の境界がどう変わるかが示される。どこが境界かは宣言したパスで判定される
- [ ] US-12.2: G8 では、受け入れ基準から一意に決まらず AI が解釈で決めた振る舞い（「（解釈）」の印）と、どのシナリオにも対応していない受け入れ基準だけが示される
- [ ] US-12.3: G4・G8 で示す中身はスクリプトが組み立てる
- [ ] US-12.4: 全文は、利用者が求めたときに見せる
- [ ] US-12.5: 境界のパスを宣言していないワークスペースでは、G4 は従来どおりの提示になる

## US-13: アプリケーションの状況を宣言し、AI に任せてよいリスクの上限にする

**ユーザー**: Hikyaku を導入したリポジトリの利用者
**目的**: 同じ欠点を、公開範囲やデータの重さに応じて受け入れるか判断できるようにするため
**操作**: リポジトリで1回、アプリケーションの状況を宣言する。重い領域はパスで上書きする
**優先度**: Must
**受け入れ基準**:
- [ ] US-13.1: 公開範囲・扱うデータの重さ・壊れたときの影響を、リポジトリで1回宣言できる
- [ ] US-13.2: 重い領域（認証・課金・マイグレーションなど）と境界のパスを宣言でき、そのパスでは領域の宣言が全体の宣言を上書きする
- [ ] US-13.3: 宣言が、AI に任せてよいリスクの上限として、ゲート（US-10）・conductor（US-15）・異議（US-1）の判定に使われる
- [ ] US-13.4: 宣言が無いワークスペースは、従来どおり上限を設けずに動く（Q3）
- [ ] US-13.5: 宣言の変更は同意として扱われ、変更する宣言を拠り所にして受け入れたリスク（US-6.6・US-1.5 の記録）が、宣言を変える PR の時点で見直しの対象として示される

## US-14: 委任の前提を確かめ、崩れたら人間に尋ねる

**ユーザー**: プロファイルで委任を決めた利用者
**目的**: 複雑さや差し戻しで委任の前提が崩れたのに、委任が黙って続くのを防ぐため
**操作**: G1 で要件を合意する。サイクルの途中で差し戻しが起きる
**優先度**: Must
**受け入れ基準**:
- [ ] US-14.1: G1 で、選んだプロファイルのままでよいかを人間が確かめる
- [ ] US-14.2: 委任の前提が崩れたことを示す出来事（差し戻し＝`return.md` の作成、設計と要件の衝突の記録）が記録に残ったら、委任を続けるかを人間に尋ねる
- [ ] US-14.3: スクリプトも LLM も、プロファイルを黙って切り替えない
- [ ] US-14.4: 差し戻しからの再設計の回では、プロファイルに関わらず G3 と G4 を人間が行う

## US-15: conductor の監督は安全側にだけ倒す

**ユーザー**: conductor に ARCHITECT から BUILD を任せる利用者
**目的**: 監督の判断がぶれても、上げるべき問いを見逃さないようにするため
**操作**: `/hikyaku:conductor` でサイクルを任せる
**優先度**: Must
**受け入れ基準**:
- [ ] US-15.1: 監督は、リスクに関わる問いに安全側に倒す答えだけを返す
- [ ] US-15.2: 上限を超えるリスクを受け入れる判断と、安全側の推奨を退ける判断は人間に上げる
- [ ] US-15.3: 監督の LLM の判断は、人間に上げる向きにだけ使われ、上げるはずの問いを委任側へ倒さない
