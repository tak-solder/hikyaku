# Build 06: 事後同意（PR を作る直前の同意ゲート） 質問

## Q1: G8 — plan.md と test-spec.md を承認するか
**回答**: 承認する（実装へ進む）。委任された判断（監督）。
**根拠**: issue.md の受け入れ基準（US-19.5・19.6・20.5・20.7・20.8・20.10）はすべて test-spec.md のシナリオに対応し、範囲外（build-07・16・17）のシナリオは入っていない。conductor の子で同意ゲートを置かず pr / publish の accepts の検査は外さない扱いは issue.md の定めどおりで、決定の無い項目があれば PR は完了せずユーザーに上がる安全側。決定として数えるのを by=user の consented / decided / resolved に限り、受け入れの言葉の無い高の異議を数えない点、decisions.jsonl を読めなければ手順に入れる点も安全側。反映しなかった低の指摘1件（文言とキー名）は実装で決めてよい。

## Q2: review-findings — コードレビュー2回目（最終ラウンド）の未解決の指摘3件をどう扱うか
1. CLI は PR の作成・公開そのものを止められない（ほかの単位で記録した `merge@<この単位>` の事項ではゲートも出ない）
2. `reopens` がほかの単位で記録した決定を見ない
3. 1回の評価で同じ `decisions.jsonl` を2回読む

**回答**: 3件ともそのまま進める。1 は handoff の「残したこと」に、build-16（ゲートの範囲を全体へ広げる）で扱う候補として「確度: 要確認」で記録する。委任された判断（監督）。
**根拠**: 1 を新ビルドにする、または build-16 の issue.md に足すのは、スコープを広げる判断なので監督は選ばない。この build の時点では事後同意の経路（build-16）がまだ無く、上限を超える受け入れが後回しで積まれることは無い。決定の無い項目があれば pr / publish の完了を CLI が拒み、手順には consent-list の確認がある。監督は build-16 の G8 で、この候補が範囲に入っているかを確かめ、入っていなければユーザーに上げる。2 は誤って承認を取り直す向き（安全側）で、設計（単位のファイル1つだけを読む）どおり。3 は性能だけの指摘。
